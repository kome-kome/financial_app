## 接続先と DB セッション・タイムアウト

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「接続先と DB セッション・タイムアウト」。

- **接続先をローカルへ向けるときは、環境変数を `import database` より先に立てる（Issue #481）**: [database.py](../../database.py) は `load_dotenv()` をモジュールトップで呼ぶが、**python-dotenv の既定は `override=False`＝既に立っている環境変数が `.env` に勝つ**。#481 当時はこの性質だけが「`.env` に本番の `DATABASE_URL` が書いてある状態で、ローカルへ向ける」唯一の手段で、**`$env:DATABASE_URL` を立て忘れると黙って本番へ繋がった**。**#503 以降は `FINAPP_DB_TARGET` の既定が `local` で、local では `DATABASE_URL` を読まない**（ローカルの接続先は `DATABASE_URL_LOCAL`）ので、この罠が残るのは `FINAPP_DB_TARGET=prod`（または `RENDER`）が立っているときだけになった。それでも、`init_db()` のように不可逆な DDL を打つ処理では**接続先を表示してから `database._is_local` で止める**こと（`scripts/setup_local_db.py` が実装例。`_is_local` は長らく SSL とプールサイズの分岐にしか使われておらず、ガードとして使う前例が無かった）。
  - **再発（2026-08-01・#411）**: 同じ罠を `scripts/` の検証系ローダで踏んだ。`candidate_bakeoff._load_prices` / `measure_embargo_impact._load_prices` の `_pull_full` は自前で `SessionLocal()` を開き **`commit()` せず `close()` するだけ**だったため、pooler（Supavisor）経由でセッションが `idle in transaction` のまま **3時間15分** 滞留し `companies` の `AccessShare` を掴み続けた。その結果 `init_db()` の `ALTER TABLE companies ADD COLUMN IF NOT EXISTS issued_shares` が `AccessExclusiveLock` 待ちで `statement_timeout=2min` に達し、**バックフィル用ワークフローが起動直後に落ち続けた**（`init_db()` は Render アプリ起動時にも無条件実行されるので同じ場所で詰まる）。ALTER がロック待ちキューに入ると後続の参照も並ぶため影響はテーブル全体に及ぶ。両ローダに読込直後の `db.commit()` を追加済み。**診断は `pg_stat_activity`（`state='idle in transaction'` と `now()-xact_start`）と `pg_locks`（`relation='companies'::regclass` の `granted=false`）を突き合わせる**。滞留セッションは `pg_terminate_backend(pid)` で落とせる（コミット前の読取専用トランザクションなので失うデータはない）。
- **Supabase 既定の `statement_timeout=2min` は「重い1文」に足りない。引き上げは局所に、`lock_timeout` とセットで（#470 / #471・2026-08-09 実測で決着）**: `postgres` ロールの既定は **`statement_timeout=2min` / `lock_timeout=0`（無制限待ち）/ `idle_in_transaction_session_timeout=0`**。2026-08-08 はこの2min が**同じ日に2本のワークフローを落とした**——差分収集は `update_market_data_from_history` で 2分16秒後に非ゼロ終了し（gap-fill と J-Quants catchup は成功済みだったのに**最後の PER/PBR 反映だけで全体が failure** ＝ `workflow_run` の success 条件で繋がる nightly-scores チェーンごと停止）、週次 VACUUM FULL は**きっかり 2分01秒**で打ち切られた。
  - **「前は速かった」は上限に対する余裕の証明にならない**。VACUUM FULL の実測は 43〜92MB で 7.6〜10.4秒（2026-07-18〜08-01）だったが、2026-08-09 に 79MB を手動実行すると **37.4秒**＝**同じ規模で4倍に伸びていた**（79MB → 49MB / DB 426MB → 395MB）。所要が上限へ寄っていく前提で、文に固定の上限は置かない。#446 の「所要は据え置かず伸びる」と同じ話。**時間の歯止めは親の締切から導く**（#868）: 月次バッチの `vacuum` は締切までの「残り − 60秒」を `statement_timeout` に入れる。**クライアントを kill しても PostgreSQL 側の文は止まらない**——文の実行中にクライアントが消えても、サーバーは次に返事を送ろうとするまで気付かない（`client_connection_check_interval` は Windows で使えない）ので、予算超過の `kill_tree` だけでは ACCESS EXCLUSIVE ロックを握った VACUUM FULL が残りうる。GHA の `timeout-minutes` も同じで、止めるのはクライアントだけ（締切の無い手動の `vacuum-maintenance.yml` は無制限のまま）。
- **`init_db()` は「冪等」だがロックは取る（Issue #597・ADR-0048）**: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` は**列が既に存在しても ACCESS EXCLUSIVE を取る**（Postgres はロックを取ってから存在を確認する）。`DROP VIEW` も同じ。呼び出し元は `api.py::lifespan`（**画面を開くたび**）・`_pipeline_incremental.py`（**毎晩 17:20**）・`_pipeline_gh.py`・`scripts/setup_local_db.py` の4つあり、長時間バッチが AccessShareLock を握っている間に呼ぶと**無言で待ち続ける**（2026-09-02 実測: M-1 探索が `financial_records`/`companies`/`plugin_tuned_params`/`financial_metrics` のロックを**2時間56分 idle in transaction** で保持。#411 で実害の前例）。しかも待機中の ACCESS EXCLUSIVE の**後ろに後続のロック要求が並ぶ**ので、同じ表に触る新しいクエリまで詰まる。**M-1（最長 16:07）と日次（17:20）の余裕は73分しかない**。対策は指紋ゲート＝`_schema_fingerprint()` が一致し実体（テーブル／VIEW／`security_invoker`）も揃っていれば **DDL を1本も発行しない**（実測 76本→0本・ロック保持者が居ても 0.07秒で返る）。移行が実際に要る回は `db_timeouts(lock=DDL_LOCK_TIMEOUT)` が 5秒で `LockNotAvailable` にする＝ハングではなく失敗として現れる。**指紋は移行を決める入力すべて**（関数ソース＋`_NEW_COLS` 等の定数＋VIEW SQL＋`Base.metadata` の全列）から作るので、DDL を足せば自動的に変わる（ゲートの更新忘れが構造的に起きない）。手で DB をいじった場合の自己修復は失われるため、直したいときは `app_settings` の `schema_fingerprint` 行を消してから再実行する。

## 大量 UPDATE と SQL の書き方

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「大量 UPDATE と SQL の書き方」。

- **大量 UPDATE は「1件1文」をやめる。ただし `bulk_update_mappings` では直らない（#464）**: `update_market_data_from_history` は ORM 属性代入 + `commit()` で **ダーティ1件につき UPDATE 1文**を発行しており、42,289件で **GHA 143.1分**かかっていた（finalize 355分予算の最大項目）。律速は転送量ではなく**往復回数**で、ローカル往復 17.4ms なら同じ処理が約12分＝**同じコードが実行場所で10倍以上変わる**（GHA ランナーは米国・Supabase は東京）。
- **`ORDER BY` の無いクエリ結果を「最大値の走査」に使わない（#464）**: `latest_by_ec` は `db.query(...).all()` の結果を `year >` で走査して社ごとの最新 annual を選んでいたが、**同一 `(edinet_code, year)` の annual が本番に58組あり、うち12社は最大 year で同点**だった。行順は `ORDER BY` が無い限り保証されないため、**同一データで2回走らせるだけで「最新株価で上書きされる行」が入れ替わる**（checksum が ±370〜520 動くことで発覚）。`financial_metrics` VIEW は annual しか見ないので、どちらが勝つかで画面の per/pbr が変わる。`_fetch_latest_fin_by_ec` は `ROW_NUMBER() OVER (ORDER BY year DESC, period_end DESC)` で正しく解決しており、**2経路で規則が食い違っていた**。`UniqueConstraint(edinet_code, year, period_end, period_type)` があるので `(year, period_end)` まで見れば一意に決まる。**同種の「最新を選ぶ」処理は全経路で同じ tie-break を使う。**
- **学習行の並びを読み出し順のままにしない（#954）**: `build_snapshots` は各月の行を `prices_by_co` の挿入順で積んでいた。挿入順は株価の読み出し順で、計測（`candidate_bakeoff._pull_full`）も本番（`load_data` の社一覧）も `ORDER BY` が無いので、夜間の書き込みや週次株価キャッシュのフルロードで変わる。XGBoost は `random_state=42` でも、subsample と early stopping の検証集合（学習集合の末尾 20%）を「何行目か」で選ぶので、**並びが変わると別の木になり、エラーは出ない**。同じ `gate:fin-nan` を 10/14 と 10/15 に回すと、行数も M-6 の値（小数4桁）も一致したまま M-2 の drop の rank-IC だけが 0.0982 → 0.1117 と動き、short_side_spread の有意判定（p=0.002）が消えた（p=0.233）。同じキャッシュで社の並びだけを変えると 0.1117 / 0.1046 / 0.1010 と動き、本番の週次株価キャッシュは 10/03 と 10/15 のフルロードで 4,029 社中 1,085 社の位置が違っていた。M-6（ElasticNetCV）は並びの影響が小さい（0.1524 → 0.1518）。**`_build_snapshots_impl` で社を `edinet_code` 順に回して直した**——読み出し側に `ORDER BY` を足しても、キャッシュの差分ロードが新しい社を末尾へ足すので並びは保証できない。並びを固定しても「どの並びか」で M-2 は ±0.005〜0.01 動き、M-2 で比べてきた条件の差（0.01〜0.03）と同じ程度なので、**1 つの並びでの M-2 の有意判定は偶然に左右されうる**。`momentum_gate` は M-2 を既定で 5 個の種で回し、行ごとに予測を平均してから測る（`--seeds`・#955・ADR-0050 の 2026-10-15 追記）。

## Egress（転送量）の計測と削減

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「Egress（転送量）の計測と削減」。

- **VIEW を ORM で引くと「使わない列」まで毎回転送される（Issue #441）**: `db.query(FinancialMetric)` は `financial_metrics` の**全97列 × 全社**（最新年度 4,430行）を SELECT する。本番実測（warm 中央値・2026-08-04）は `SELECT fm.*` = **3.00s**、実際に使う19列だけなら **1.16s**、`count(*)`（転送なし）が **1.03s** ＝ **VIEW の計算自体は約1秒で、残りは行転送**。Render Free の 30秒リクエスト上限は**有料プランでも変わらない**が、**実運用はローカルPCから本番 Supabase を引く形が主**なので、この転送はそのまま毎朝の待ち時間になり、Supabase Egress（5GB/月）にも直接効く。毎朝必ず踏む経路（`/api/recommend`・`/api/morning`）ほど列を絞る。列絞りのローカル実測（2026-08-04・バランス型・top_n=30・各4回）は **warm 中央値 5.93s → 4.34s**、**プロセス起動直後の初回 38.70s → 14.88s**（候補4,249件・上位の顔ぶれは前後で完全一致＝スコア不変の確認になる）。絞るときは `db.query(*cols)` で **Row タプル**にする＝「絞っていない列を後から読む」ことが構造的に起きない。`options(load_only(...))` は ORM インスタンスが残るため、未ロード列へのアクセスが**行ごとの遅延ロード＝N+1** に化けうる。**列集合は指標リスト（`METRICS`）から導出し、キー許可集合の検証（`coerce_params` の membership）とセットで入れる**——検証が無いと範囲外キーが `getattr(row, key, None)` で**黙って None** になり、スコアとカバレッジが静かに変わる（同じ経路が weights・動的プリセットの2本あるので両方塞ぐ）。

## 株価の保存（日次・週次の2本立て）と全件ロード

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「株価の保存（日次・週次の2本立て）と全件ロード」。

- **`legacy_stock_price_history_2026_02` は遡及調整が入っていない**（#490・2026-08-21 に検証）。#481 B-0 で旧開発 DB から温存した日次 OHLCV（2024-05-17〜2026-02-20・163万行・3,960社・**478MB＝ローカル DB 834MB の 57%**）で、**現行 `stock_price_daily` に存在しない O/H/L を持つ唯一の資料**。ただし収集当時の生値で、以後の株式分割・併合が反映されていない。重複3営業日（2026-02-18〜20・11,267行）の突合で **96.53% が完全一致・乖離 130社は比率がすべて分割比**（2.0=51社 / 3.0 / 5.0 / 4.0 / 10.0 …、非整数は コタ 1.05・地域新聞社 1.8・**ピクセラ 0.1＝10:1 逆併合**の3社のみ）。比率は日ごとに揺れない＝値のノイズではなく係数のズレ。**無検証で現行データと接合すると 130社ぶんの段差が「実際の値動き」として分析へ流れ込む**。使うときは重複期間の比率で係数を求めてから当てること（2026-02-20 以降の分割も別途要る）。消費者は現時点で存在しない（`backtest.py` も週次ベース）。
- **`stock_price_weekly` の全件ロードは分割 fetch する**（Issue #311）：本番 Supabase の `stock_price_weekly` は ~95万行あり、`db.query(...).order_by(...).all()` の**単一クエリ全件取得**は pooler（`aws-*.pooler.supabase.com`）経由で `statement_timeout=2min` を超過し `QueryCanceled`、または大結果セットで `lost synchronization with server`（接続破損）を起こす（インデックスは効いており原因は純粋なデータ量＝転送＋ORM materialization）。M-1/M-2/M-3 の週次ロードは **`macro_snapshots.load_weekly_prices_chunked`**（`edinet_code` を 500 社ずつ IN 句で分割・各クエリは PK インデックスで数秒）へ集約済みで、全件でも実測 ~30秒で安定完走する（3モデル比較 E2E で全モデル OK を確認）。新たに週次株価を全件走査する処理を足すときは必ずこのヘルパー経由にする（生の `.order_by().all()` を書かない）。`SET statement_timeout` の緩和や直接接続への切替では接続破損は直らないため分割が正攻法。
  - **取りこぼし（2026-08-02・#418）**: この教訓は M-1/M-2/M-3 にしか適用されておらず、`plugins/recommend.py::compute_momentum_z` だけが**下限日付なしの生クエリ**のまま残っていた（`z_momentum: 0.5` はバランス型プリセットの既定重み＝ユーザーが毎朝押すボタンで必ず走る経路）。**全履歴が要るとは限らない用途では、チャンク分割よりまず下限日付を掛ける**：`get_momentum_return` は `long_months=12`＝`as_of − 360日` までしか参照しないため、余裕1ヶ月を足した 400 日下限で情報損失はゼロ。実測 EXPLAIN で単一クエリの推定行数は **853,669 → 26,978/チャンク**（本番実測レイテンシ 5〜10秒）。下限は `trade_date`（nullable・非インデックス列）ではなく **PK 第2列の `week_start`** へ掛けること＝`(edinet_code, week_start)` の Index Cond に入り範囲スキャンになる（`trade_date` はリークガードの上限側だけに使う）。<br>**副作用として winsorize の母集団が変わる点は必ず実測する**：本番では「最終週次バーが下限より古い＝1年以上株価が止まった 113 社」が母集団から抜けた。旧実装ではこれらの long/short 両脚が**同一の最終バーに解決され `ln(P/P)=0`** となり、擬似的な「モメンタム 0」として標準化の母集団に混入していた（除外が正しい）。上位30社の顔ぶれは不変・z の差は最大 0.084（範囲 3.42〜5.00 に対し約2%）。
  - **2026-08-17（#480）以降、このヘルパーは DB からは差分しか引かない**（[ADR-0036](../adr/0036-weekly-prices-incremental-load.md)）。**返す形は全履歴のままなので消費側の変更は不要**だが、触るときに知っておくべき性質が3つある。①差分条件 `week_start >= :since` は**既存の500社チャンクの中に**足す——`week_start` は PK 第2列なので単独では先頭列にならず seq scan になり、チャンク分割の意味が消える。②キャッシュのワイヤ形式は namedtuple ではなく**素のタプル**——`_VOLUME_NOT_LOADED` は `object()` の番兵で、pickle round-trip で同一性が壊れて `is` 判定が False になり、`px_volz` が例外ではなく全 nan を返す（#438/#446 が潰した静かな故障の再来）。③`repair_price_scale_breaks`（#465）のような**過去全期間の書き換えは指紋（`max(week_start)`＋`count(*)`）では原理的に見えない**ので、`app_settings.weekly_prices_generation` の世代印で無効化する。印は `_recompute_weeks_from_daily` が「保持窓より古い週を実際に書き換えた」という構造的条件で自動的に進む（明示フックは保険）。挙動が怪しいときの切り分けは `FINAPP_WEEKLY_CACHE=0`＝**指紋クエリすら発行しない**従来動作に戻る。

## 日付・時刻の境界（JST）と株価の鮮度

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「日付・時刻の境界（JST）と株価の鮮度」。

- **データ鮮度は「全社の max」で測らない＝分位で見る（Issue #415）**: 銘柄別の最終 `trade_date` は一様ではない。2026-08-02 の本番実測は **max=2026-07-31 だが該当は2銘柄のみ**、3,677銘柄は 2026-07-13（19日前）だった。この状態で「全社の max」を鮮度の代表値にすると、①UI の as-of バッジが緑のまま19日古いランキングを出す ②`fill_recent_stock_price_gap_yahoo` が `d_from = max+1` を全社に適用して**遅延銘柄の欠測を永久に埋められない** という二重の実害が出る（両方とも実際に発生）。しかも週次バーの欠落は例外を出さず、`build_snapshots` の52週先ラベル（`closes[snap_idx + HORIZON_WEEKS]` ＝**インデックス参照**）や `px_high52dev`/`px_rvol` のローリング窓を静かにずらす一方、`get_momentum_return`（日付カットオフ方式）は壊れない＝**特徴量ごとに壊れ方が違うため発見が極めて困難**。鮮度の測定・表示・補完の起点はすべて**銘柄別（p05/p50 と件数）**で扱う。#356 の「表示桁 == 判定桁は危険」と同型で、**集約の仕方が実態を隠す**タイプの罠。
- **毎晩の gap-fill は「閉場済みの最新 JST 営業日」を基準にする。UTC の `date.today()` と比べない（#474・2026-08-09）**: `fill_recent_stock_price_gap_yahoo(gap_days=0)` の旧判定 `(date.today() - last_d).days <= 0` は、GHA ランナーの **UTC 日付**との比較だった。cron は UTC 18:00 ＝ JST 03:00 なので、**UTC 土曜/日曜（＝JST 日曜/月曜の早朝）は全社が「1日遅れ」に見える**。JST 日曜 03:47 起動の run 31272807314 は、全社が既に持つ金曜バーを 4,437社ぶん取り直して **2時間11分**を使っていた。基準を `last_closed_session()` に替えると本番実測で **4,437社 → 735社**（うち 454社は株価を1件も持たない社）。
  - **起動時刻を動かす前に「その時刻にどのソースが確定しているか」を並べる**。JST 03:00 と JST 17:17 は**市場データの中身が同一**（日本株は同じ大引け／米国は JST 03:00 時点でまだ場中なので直近の確定クローズも同一）＝前倒しで失うものは無く、得るのは「見られる時刻が9時間早い」と「EDINET が1日新しい」の2点だけ。**「早く回せば新しいデータが入る」は自明ではない**ので、ソース別の確定時刻表で確かめてから動かすこと（`docs/DEPLOYMENT.md` の daily-incremental 節に表がある）。
  - **JST 16:00〜22:30 は東証も NYSE も閉じている唯一の窓**。ここに置くと進行中バーを平時は踏まないが、**GHA の cron 遅延は実測で最大6時間**（18:00Z が 00:08Z 起動）なので保証にはならない。スケジュールは第一防御、コード側（`last_closed_session`・in-progress バー除外）が本防御。
  - **#503 の正本反転で顕在化した**。Supabase は既定 `TimeZone=UTC`、ローカル PG は実測 `Asia/Tokyo`（`pg_settings` のサーバ設定なので**全クライアントが継承する**——psql も SQLAlchemy も同じ）。**どちらの世界でも接続でき書き込みも成功するので例外は出ない**（#508 と同型で、接続先の食い違いは沈黙する）。結果として同じ列に UTC と JST が混在した（境界は 2026-08-20）。
  - **対策は `database.SESSION_FIXES` が接続時に `SET TimeZone = 'UTC'` を流すこと**（`connect` フック＝呼び忘れる余地が無い）。ロール既定や `postgresql.conf` は変えない（別マシンへ持っていって再現しない設定に頼らない）。`scripts/mirror_common._SESSION_FIXES` はこれを再利用する——**かつてはミラー側だけが TimeZone を固定しており、`database.engine` は素通しだった**＝同ファイルが float8 の 15 桁丸めで得た「設定は思い出すものでなく接続に付いてくるもの」という教訓が、別の値で再発した形。

## 株価のスケール（1）J-Quants の調整後値と分割の修復

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「株価のスケール（1）J-Quants の調整後値と分割の修復」。

- **J-Quants V2 は必ず調整後フィールド（`AdjC`/`AdjO`/`AdjH`/`AdjL`/`AdjVo`）を使う**（Issue #314）：`/v2/equities/bars/daily` の `C`/`O`/`H`/`L`/`Vo` は株式分割・併合を遡及反映しない**未調整**値。未調整フィールドを使うと分割日を境に系列が段差になりモメンタム/週次リターン計算が破損する（`AdjFactor` は分割時に該当日へ設定される倍率だが、`AdjC` 等は既に遡及調整済みなので自前でスケーリングし直す必要はない）。実地検証（2026-07-12）で確認済みのフィールド一覧: `O,H,L,C,Vo,Va,UL,LL,AdjO,AdjH,AdjL,AdjC,AdjVo,AdjFactor`。`stock_price_weekly` は追記専用・trim しないため、過去に未調整値で書き込まれた行は将来 J-Quants を再取得しても**自動では直らない**（該当週の `daily` が再収集されて `_recompute_weeks_from_daily` が走った週だけ更新される）。本番調査では 2024-06-03 の週を境に315銘柄が同時に価格スケール断層（Yahoo/stooqバックフィル＝調整済み → J-Quants日次収集＝未調整、への切替境界）を起こしていることを確認済み（Issue #314 コメント参照）。
  - **段差の残存量を実測してから直し方を決める（#465・2026-08-08）**: 契約復旧後に公式値（`AdjC`）と `weekly.close_last` を突合したところ、**98〜99% の銘柄は完全一致**し、ずれるのは1〜2%だけだった。乖離の分布は「ほぼ0」と「1%以上」に**きれいに二分**し 0.1〜1% の帯はほぼ空＝閾値は 1% 前後ならどこに置いても同じ集合を拾う（「検知したい値」から逆算した数字ではない）。比率は整数の逆数で、ソニーG（E01777）は 2024-09-27 に 13,365 → 2,861 ＝ **×0.214 ＝ 1/5** ＝ 同社の1:5分割と一致する。
  - **「全期間を公式値で置換」は解ではない**。730日ぶんを全銘柄取り直す案は、大半が既に一致していて得るものが無いうえ、`trim_daily` が**収集ループ末尾で1回しか呼ばれない**ため未 trim の daily が約130万行積み上がり、413MB / 500MB（余裕87MB）の Supabase Free を超える。段差銘柄だけを Yahoo で個別に取り直す `python collector.py --repair-price-breaks`（既定 dry-run・`--persist` で書込・上限超過で中止）を使う。**再発は前提**——weekly は append-only なので分割が起きるたび同じ段差ができる。だから自動化ではなく「いつでも回せる検出コマンド」として残してある。
  - **Yahoo は一部の分割を過去へ遡及反映しない＝修復ソースとして万能ではない（2026-08-08 実走）**: 74社を検出し73社を Yahoo で取り直した結果、**61社は収束・新規悪化0社**だったが、**13社は残った**。三者突合（DB / Yahoo / J-Quants）で原因が確定している——ロードスターキャピタル（3482）の 2026-04-24 は **DB=Yahoo=3025 に対し JQ=2520.8＝ちょうど 5/6**。つまり **DB は Yahoo と完全一致していて、Yahoo 自身が公式と食い違う**（無償割当型の小規模分割で顕著）。**「修復後も残った＝修復が効いていない」ではない**ので、残存を見たらまず DB と修復ソースが一致しているかを確かめること（残存を公式値で直す方法は [SCRIPTS_REFERENCE.md](../SCRIPTS_REFERENCE.md) の `repair_splits_from_jquants` の節）。<br>なお Yahoo の `quote.close`（`fetch_yahoo_history` が使う）は**分割調整済み・配当未調整**で J-Quants の `AdjC` と同規約＝この差は配当調整の違いではない（`adjclose` を使っていれば高配当銘柄が系統的にずれるが、そうはなっていない）。
  - **公式 `AdjFactor` は株式分配型スピンオフを持たない（#568・2026-09-12）**: 子会社株を現物で配るスピンオフは J-Quants が遡及調整せず、Yahoo（= DB）だけが権利落ち日より前へ `(権利付最終日の終値 − 分配株式の初値) / 権利付最終日の終値` を掛ける。見分け方は3つ——**公式 > DB の向き**（分割の取り残しは DB > 公式）・段差が権利落ち日にある・`AdjFactor` に対応するイベントが無い。実例は E02086（6676 バッファロー → シマダヤ 250A・権利落ち 2024-09-27）で、Yahoo の 9/26 以前の終値を係数で割り戻すと全日が呼値（5円）の整数倍になり、係数 `(3820 − 1760) / 3820` の逆数 1.854369 が #466 の実測比と一致した（#466 では2年ぶん「説明できない」とされていた）。**DB を公式へ寄せてはいけない**——週次リターンを使う M-1/M-2/M-6 には DB 側が正しく、寄せると権利落ち日に約 −46% の偽の暴落を作る。突合では公式値を DB のスケールへ換算する: `corporate_actions.SPINOFF_ADJUSTMENTS` へ根拠付きで登録すれば `--repair-price-breaks` と `repair_splits_from_jquants` の両方が換算する。**J-Quants の取得経路（毎晩の catchup・手動収集）は、登録済みの社の権利落ち日より前の日付を書かない**（#651・理由は ADR-0053 の追記）。新しいスピンオフは J-Quants の契約窓に入った時点で検出器に「公式 > DB・イベント無し」として現れるので、そのとき第3のソース（適時開示・IPO 情報の初値）で裏を取って登録する。**登録すると分割補正係数 F も変わる**（#740・ADR-0055 決定4-9。台帳が同じ登録から F を入れる仕組みは ADR-0062）。収集経路と違って止める向きではないので、**誤登録は VIEW の値を動かす**。F に入れた一覧は毎晩のログ「分割補正係数: 登録表のスピンオフ N 件を F に入れた」に出る。DB が調整を失って再び検出されたら、登録を外せば F も同じ晩に外れる。
  - **逆向きもある: 公式だけが調整し DB が正しい企業イベント（#652・2026-09-13）**: E34165（1447 SAAFHD）の新株予約権無償割当（買収防衛策・1株につき1個・目的株式 0.5株・行使価額 1円）では、公式 `AdjC` が権利落ち日より前の全期間へ全員行使時の理論係数 2/3 を掛けるが、Yahoo は split として持たず DB と全期間で一致する（市場は差別的行使条件と取得条項付きの予約権をほとんど織り込まない）。**エンバーゴ群（`post_window_adjustment`）は分割とは限らない**——普通の分割と同じ「公式は窓内を遡及調整済みなのに `AdjFactor` 行が無い」形で現れるので、`--repair-price-breaks --persist` へ回す前に **DB と Yahoo が既に一致していないか**を見る（一致していれば取り直しは無意味）。イベントが契約窓に入ると `repair_splits_from_jquants` の `validate` は段差を公式イベントで説明できて**綺麗に通り**、`--apply` が実際の取引に無い +45% の跳ねを書く。**回避**: `corporate_actions.WITHHELD_OFFICIAL_ADJUSTMENTS` に「社＋日付の窓」で根拠付きで登録する——窓の中に公式イベントがある社は `withheld` 群へ分かれて書かれない。スピンオフのように換算しない理由は ADR-0053 の追記。**同じ登録を企業イベント台帳も読み、窓の中の公式イベントを F の検出と TTM の分割窓の両方から外す**（#739・仕組みは ADR-0062）。外した件数は毎晩のログ「分割補正係数: 保留の窓で外した公式イベント N 件」に出る。外したイベントは検出器から見て「無かった」ことになるので、その社の第1経路（例: 予約権の行使で株数が 1.5 倍になった年）は補正されず、ログでは「公式に分割が無い」の行に出る。**2例目は E05716（2164 地域新聞社・#1254・2026-11-19）**: 公式は 2026-08-07 に 0.668663 を当てるが、実際の終値は前日比 −7.8%（理論どおりなら約 −33%）。夜間の検知（#1253）は比が 1.5 に寄るので「未調整の分割」として毎晩報告し、`repair_splits_from_jquants` も「補正対象」と出す——**比が分割にそろっても、権利落ち日の実際の値動きと開示（買収への対応方針）を見るまで分割と決めない**。

## per / pbr の分割補正（ADR-0055）

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「per / pbr の分割補正（ADR-0055）」。

- **`per` / `pbr` が「調整済み株価 ÷ 当時の1株指標」になっている（#653・#655・ADR-0055）**: 分割より前の年の行だけ per/pbr/market_cap が分割比ぶん小さく、div_yield と（`market_cap` を分母に持つ）nc_ratio/z_nc_ratio が同じだけ大きい（どの列がなぜ歪むかと実測の規模は [ADR-0055](../adr/0055-valuation-basis-mismatch-is-corrected-in-the-view.md) の Context）。**エラーは出ない**——どの値も妥当な株価指標で、**最新行は基準が揃うので既定の画面には出ない**（例外は期末後分割の年の行・下記の #753）。出るのは学習パネル（M-1/M-2/M-6）と、**年度を指定した**スクリーニング・CSV・M-8・`/api/backtest`。
  - **`scripts/measure_split_valuation_bias detect` はこの方式の回帰テストにならない**。測定器は `financial_records` の生値を読むので、補正後も同じ 1,948 行を報告し続ける（#655 本文の「測定器がそのまま回帰テストになる」は実列書き換え方式を前提にした記述）。確認は `financial_metrics.per = ROUND(financial_records.per × split_factor, 2)` の突合（2026-09-12 実測で per/pbr/market_cap/div_yield とも不一致0行。**#753 以降、market_cap は `× split_factor × split_shares_lag`、div_yield は `÷ (split_factor × split_dps_lag)` で突き合わせる**）と、**E01777 ソニーG の 2024年 per 3.29 → 16.45**（F=5.0・#653 の「実際は17〜20倍台」と整合し、翌期の 20.30 と連続する）で行う。**突合の join は `fm.id = fr.id` で取る**——`(edinet_code, year)` で結ぶと、同じ year に annual 行が2本ある社（会計期間変更・実測58組）で別の行と比べてしまい、F=1.0 の行が「不一致」として56件出る（筆者が一度踏んだ）。
  - **期末後分割の年の行は、F ではなく基準の遅れで直す（#753・ADR-0055 決定4-11）**: その行は 1 株指標が分割後の基準なのに、期末の発行済株式数（と多くの社で 1 株配当）が分割前のまま＝生値の market_cap が 1/F、div_yield と nc_ratio が F 倍に出る（E02086 の最新行 42,420 百万円 → 実際は 84,840）。F は「その行より後のイベントの積」なのでこの行は F=1.0 で、**`e.year >= y` にして F に混ぜると同じ行の正しい per / pbr を F 倍に壊す**。遅れを当てる列（VIEW の `split_shares_lag` / `split_dps_lag`）と、当てない行の条件は決定4-11 にある。補正された行では `market_cap <> stock_price × issued_shares / 1e6` になる（意図した非対称）。**係数表に F=1.0 の行がある**（遅れだけを持つ行）ので、F の突合で表を読むときは `factor != 1.0` に絞る（`scripts/measure_split_leak.compare_factors`）。 **VIEW を通らない `sector_ols` は読込（`_load_records`）で同じ遅れを当てる（#758・決定4-12）**。当て損ねても失敗は出ず、該当社の gap_ratio が割安側へ寄るだけ（補正前は該当 87 社の中央値 55.0%・他社 16.5%）。**`market_cap` は生のまま読む**——VIEW が `predicted_market_cap` に `shares_lag` を掛けるので、読込で直すと二重になる。補正で同じ業種の ridge の α（一個抜きで選ぶ）が切り替わることがあり、該当社以外の gap も動く（2026-09-27 の試算で 6 業種・機械は 0.001 → 100）。
  - **`bs_bps` の年次比では「分割があった」は言えるが「何倍か」は決められない（#656・2026-09-12 実測・ADR-0055 決定4-2）**: `bs_bps` は内部留保や有価証券の評価差額でも増えるので、観測比は真の分割比より小さく出る。そのため第2経路は、分割の存在の検出だけを `bs_bps` に任せ、倍率は独立な第3の信号から取る（次の項目。検出量・一致率の実測と経緯は決定4-2）。**`per` の比は第3の検証に使えない**（株価の値動きが混ざる。実測 E00313 は snap ×3.0 に対し `per ×8.05`）。
  - **第2経路の倍率は翌年の `issued_shares` から取る。既定は ON（#659・2026-09-12 実測・ADR-0055 決定4-3）**: **第3信号が取れない年のイベントは採らない**が、係数表は毎晩全置換なので翌年の決算が入れば自動的に F へ入る（一致率・採らなかったイベントの内訳・件数は決定4-3）。**突合には `--coverage partial` が要る**——`in_coverage` の既定（窓が契約窓へ完全に収まる）では、**「公式で判定できる」と「翌年の行がある」が排他になり分母が 0 になる**。`partial` は窓と契約窓の重なりの中だけを見て、公式イベントが見つからない件は `no_official_event_partial` として分母から外す（分母の規則は `MATCH_DENOMINATOR` が唯一の源）。**`partial` で測れるのは倍率だけで偽陽性率は測れない**（公式が返さないことを「分割が無かった」と読めない）ので既定は `full` のまま。偽陽性の分離は #657。
  - **期末後分割は、利益が大きく動いた年に EPS 照合で落ちる（#751・2026-09-26 実測・ADR-0055 決定4-10）**: 期末日の後・決算書の提出前に効力が生じた分割では、その期の EPS / BPS だけが分割後の基準に書き直され、発行済株式数と DPS は分割前のまま残る（株数は翌年の行で動く）。**きっかけは効力日ではなく決議日**（#836・2026-10-08 実測）——提出前に分割を決めていれば、効力が提出より後でも書類は「期首に当該株式分割が行われたと仮定して」1 株指標を算定する。E02242 は期末 2025-03-31・提出 2025-06-25（訂正ではない原本 `S100W5AR`）・効力 2025-09-30（書類の記載。Yahoo の分割日は 2025-09-29＝期末+182日）で、書類の BPS 620.94 / EPS 24.66 が分割後、発行済株式数 500 万株が分割前だった。**提出時点で知りえた情報なので時点再現の漏れではなく、収集も書類どおり**（後の書類による上書きではない）。同じ形（「BPS × 発行済株式数 ÷ 純資産」がちょうど整数分の 1）の年度行は約 310 行・約 280 社（1/2 が 201 行・1/3 が 55 行・1/4 が 25 行・1/5 が 21 行）で、毎年 30〜50 行ある。第2経路の EPS 照合は利益の伸びと打ち消し合うと届かないので、**整合度**（`corporate_actions.consistency_ratio`）で見分けて入れる（整合度の定義・既定 ON にした事前登録の基準・倍率との照合の仕方は決定4-10）。**Yahoo や公式と照らすときは窓の幅に注意する**——期末後分割は効力日が期末+45日を越えうる（決議が提出前なら効力は提出後でもよいので、E02242 のように期末+182日もある）ので、`event_window` の外に同じ比の分割があるだけで「分割なし」に見える（事前登録した Yahoo との照合の不一致 11 件中 9 件がこれ）。**続けて期末後分割した社は、整合度が前年からのずれの変化しか測らないので倍率と食い違い、採られない**（E03186 2023: 整合度 2.00 対 翌年の株数 4.0）。食い違いは夜間ログの「整合度照合: 倍率の食い違い」に出る。分割した年の行の market_cap / div_yield / nc_ratio の歪みは F では直らない（#753）——基準の遅れで直した（上の項・決定4-11）。
  - **同じ年に期中の分割と期末後分割が重なると、第2経路は期末後の分しか F に入れない（#756・2026-09-30 実測・ADR-0055 決定4-13）**: その年のペアは 1 株指標が 2 回分・株数が 1 回分だけ動くので、第2経路は翌年の株数（期末後の 1 回）だけを倍率にする（E35140 2022: 真値 4 に対し 2）。見分け方と、期中の分を足す仕組み（`DEFAULT_IN_PERIOD_DECOMPOSE`）は決定4-13。**Issue に書いた条件は代数で展開してから採る**——案1 の「bps 逆比 ÷ 整合度 ≈ 株数比」は整合度の定義を代入すると「純資産比 ≈ 1」と同じ条件で、純資産が +25% 伸びた対象の 2 社をどちらも救えなかった。**同じ形は EPS 照合を通った組にも 4 件あり**、Issue の記述（整合度照合の 2 件）だけを見ると半分以上を取りこぼす。分割した年の行の遅れ（`basis_lags`）も、期中の分を除いてから判定しないと「株数が既に動いた」に数えて入らない。
  - **純資産総額の前年比は深い割引の増資を分離できない（#657・2026-09-13 実測・ADR-0055 決定4-4）**: **落とせるのは `bs_bps` と純資産総額が食い違う社だけ**で、閾値を下げると本物の分割を巻き込む（既定 `DEFAULT_EQUITY_TOL = 1.0` で落ちる社と、偽陽性と確定しているのに落とせない社は決定4-4）。**許容を動かすなら `verify-sample --census`（契約窓内の全数突合・約 35 分）と、窓外で落ちる社の Yahoo split 照合をやり直す**——余裕は両側とも薄い（E36173 まで 0.015）。偽陽性率は**抽出では測れない**（#654 の 30 社突合は `no_official_event` 0 件だったが、全数では 6/94＝composite 5/22・split 1/69）。
  - **最新年の第2経路は公式 `AdjFactor` で倍率を取るが、表に行が無いことを「分割は無かった」と読まない（#661・ADR-0055 決定4-5）**: 翌年の決算がまだ無いペアは、`jquants_adj_factor_events` の公式イベントがイベント窓の中にあるときだけ倍率に採る（窓の幅・翌年の株数を優先すること・定番比へ丸めない理由と取り込みの実測は決定4-5）。**表は「あれば使う」だけ**——夜間 catchup が見るのは `today-90〜today-80` の日付だけで、PC が止まっていた晩の日付は取り直さず、エンバーゴ（直近約12週）の中の分割はまだ行が無い。どれも「行が無い」に見えるので、無ければ今日までどおり採らない（`no_lagged_row` と `stats["bps_path"]["awaiting_magnitude"]`）。取りこぼしは `python -m scripts.backfill_adj_factor_events` を回し直せば埋まる（upsert・冪等）。**`rebuild_split_adjustment_factors` から J-Quants を叩かない**（決定4-3）。**測定器の CLI（`detect` / `verify-sample`）は公式を渡さない**——公式から倍率を決めたイベントを公式と突き合わせると定義上必ず一致し、一致率が黙って膨らむ。
  - **定番比の表（`CANONICAL_RATIOS`）に比を足すと、確かめた社以外の丸め先も動く（#669・2026-09-13 実測・ADR-0055 決定4-6）**: 表に無い比（3:1 併合・1:15 など）は `unsnapped` として F に入らないか、近い定番比へ composite で丸まる——どちらもエラーは出ない。**足すのは、候補の本物の比を公式 `AdjFactor`（契約窓の内側）か Yahoo の splits（外側）で確かめ、さらに足した前後で倍率が変わるイベントを全部確かめたときだけ**（これまでに足した比・足さなかった比と、その社の例は決定4-6）。前後差は、`rebuild_split_adjustment_factors` と同じ入力（ORDER BY まで同じ annual 行＋`load_jquants_adj_factor_events`）に対して表だけを差し替え、`detect_events` / `cumulative_factors` を2回呼べば DB に書かずに出せる。
  - **同じ EDINET コードでも、上場廃止→再上場で別の実体の行が欠損年をまたいで隣り合う（#672・2026-09-14 実測・ADR-0055 決定4-7）**: 検出器は欠損年があると「直前の使える行」とペアを組むので、旧社と新社の株数と `bs_bps` がたまたま逆向きに同じくらい動くと交差検証を通る（E05714 ソニーFG: 2020-03-31 の旧社と 2026-03-31 の新社で株数 ×15.56・bps 逆比 ×16.91）。**判定を `gap_years` 単独にしない**——本物の分割にも欠損年はある（XBRL の取りこぼし・決算期変更。E03078 は 2018→2020）。判定材料は週次株価の空白（`listing_gap_in_pair`・条件は決定4-7）で、空白は2つの形で現れる——**系列の開始が遅い**（旧社の価格が表に無い・E05714 は 2025-09-29 から）と、**系列が途中で途切れる**（旧社の価格が残る・E03530 SBI新生銀行は 2023-09-25 の次が 2025-11-17）。開始日だけを見ると後者を取りこぼす。**週次の系列が収集の都合で遅く始まる社がある**（2024-05-27 に 225 社・再上場ではない）ので、そういう社が欠損年をまたぐと本物の分割まで比べなくなる——`rebuild_split_adjustment_factors` が比べなかったペアを毎晩ログへ出すので、増えたら中身を確かめる。入力 `load_price_series` の空白は SQL の LAG で測る（週次 約140万行を Python へ持ってこない）。
  - **公式 `AdjFactor` に分割が「無い」と読めるのは、その社の日次バーを実際に受け取った区間の中だけ（#668・2026-09-14 実測・ADR-0055 決定4-8）**: J-Quants は扱わない社でもエラーを返さず **0 本**で返す（E03474 ゴルフ・ドゥ 3032 は契約窓 2024-06-22〜2026-06-22 で 0 本）。`_jquants_fetch_code` は 429 が2回続いても `[]` を返す。どちらも「イベントが無い」と同じ形なので、**#657 の全数突合は E03474 を偽陽性に数えていた**（6/94 のうち 1 件は判定不能だった）。公式の不在で外すのは、受け取ったバーの区間（`bars_spans`）がイベント窓を覆うときだけ（区間の切り方・`no_official_bars`・第2経路に掛けない理由は決定4-8）。区間は `jquants_adj_factor_coverage` に**追記**する（上書きすると契約窓が進んだあとに古い期間の確認が消え、外した補正が黙って戻る）。

## J-Quants API の応答とエンバーゴ

移す前の場所: GOTCHAS.md「DB・運用上の注意」→「J-Quants API の応答とエンバーゴ」。

- **外部APIの権限判定を「別エンドポイントの成否」に委ねない（Issue #425）**: #412 は J-Quants の 403 を切り分けるのに「`/markets/listed/info` が取れていればキーは有効＝境界の欠測」というガードを入れたが、**`/markets/listed/info` は常に 403** だった（2026-07-09/12/13 の **success** run すべてに `listed/info 取得失敗 status=403` が出ている）。判定材料が常に偽なので条件は「全日403」だけに退化し、84日エンバーゴ内を叩く `days_back=14` では**構造的に必ず中断**していた。**判定に使う信号は、それ自体が正常時に成功することを先に実測で確認する**（ログに warning が出ているのに `success` で終わる経路は特に見落としやすい）。<br>併せて **収集元Aの失敗が収集元Bをブロックしない構造にする**: J-Quants の中断が、同じキーに一切依存しない Yahoo ギャップ補完（株価鮮度の実質唯一の担い手）まで巻き添えで止めていた。鮮度を担う収集元を先に置き、他方の失敗は握って継続する（`_pipeline_incremental.py` Phase 4）。**「修正済み」の Issue も本番 cron を1周回すまで検証済みとしない**（#412 はマージ済みだったが実際には障害を直していなかった）。
- **ステータスコードだけ見て理由を推測し、それを docs へ断定で書かない（#462・2026-08-08 実 API で決着）**: J-Quants は 400 と 403 のどちらにも複数の意味を載せており、**区別できるのはボディの文言だけ**。この推測を2回積み重ねた結果、コードとドキュメントが実体のない事象を前提にしていた。
  - **403 にカバレッジ境界は無い**（窓外は 400＋covers 文言。400 と 403 の分類・実装での扱いは [DEPLOYMENT.md](../DEPLOYMENT.md#j-quants-api無料プラン) の J-Quants 制約表が正本）。つまり #412 / #425 が「403＝カバー範囲外」と読んだ観測はすべて**契約失効**（#461）だった——境界なら 400 で静かに空を返すので、そもそも exit 1 しない。2026-07-14〜08-01 の19日連続 failure も同じ。
  - **`/markets/listed/info` の403の理由も誤っていた**。「無料プランに権限が無い」と書いていたが、実体は URL 不在だった（後継の `/equities/master` と、`issued_shares` の移し先は同じ表の `/markets/listed/info` の行）。
  - **400 を「非営業日」と一括りにすると、無視できない空振りが不可視になる**（窓外日を叩かずに飛ばす方法と、エンバーゴ日数を決め打ちしない理由は同じ表の「カバレッジ境界は 400」の行）。決め打ちで切ると、取れるはずのデータを捨てても INFO ログは平常時と区別がつかない。**空振りを削る最適化が、別種の静かな劣化を作り込む**のは典型的な取り違え。
  - 教訓は「新しいステータスに出会ったらボディを実測してから分類を足す」。**推測を docs に断定で書くと、後から実測した人が「確認済みの事実」として扱ってしまう**。
- **止まっていた同期を復活させるときは、復活直後の1回目の結果を必ず検算する（#463）**: #462 で `is_active` 同期（#315・v2 移行以降ずっと停止）を `/equities/master` へ載せ替えて復活させたところ、初回実走で `新規delisted=699件` が出た。内訳を検証すると **`/equities/master` もエンバーゴされており**、**as-of より後に新規上場した銘柄は載らない**（as-of の実測値と `sync_active_status` の対処は [DEPLOYMENT.md](../DEPLOYMENT.md#j-quants-api無料プラン) の J-Quants 制約表「`/equities/master` もエンバーゴされる」の行）。「マスタに無い＝廃止」と読んだため IPO 直後の 589A/607A が `is_active=False` にされ、`is_active.isnot(False)` でフィルタする推奨系プラグインの母集団から消えていた。**長く止まっていた処理は再開時に大量の差分を吐き、その量自体が「溜まっていたぶん」に見えて異常を隠す**。件数だけ見て納得せず、内訳をサンプリングして裏を取る。<br>**判定条件の設計でも1案を実測で棄却した**（棄却した案と反例の銘柄は同じ表の行）。正しいのは **「価格履歴の開始が as-of より後」**＝ as-of 時点でまだ上場していない＝載らなくて当然、という条件。**「新しい」ではなく「古い側が無い」で見分ける**。前提として `stock_price_daily` の保持窓がエンバーゴ日数より長いこと（短いと全件が保護される）。
- **開示データの「齢」は障害ではない。`today − 84日` が仕様上の天井（#424 子4）**: `statement_disclosure.disc_date` の MAX が3ヶ月前でも、それは収集の失敗ではない。J-Quants 無料プランの `/fins/summary` は 12週固定で配信を遅らせるため（`JQUANTS_DISCLOSURE_DELAY_DAYS = 84`）、**どれだけ頻繁に収集しても天井は動かない**。2026-08-02 の観測「MAX 2026-04-17」は、最終収集 2026-07-12 − 84日と**完全に一致**する＝正常に取り切れている証拠だった。`collect-disclosures.yml` に cron を足して改善するのは「84日前のデータが揃うまでの遅れ」だけで、**開示由来の特徴量は当日の売買判断には原理的に使えない**。株価の鮮度ゲート（#420/#415）と同じ物差しで「3ヶ月前＝壊れている」と読むと、直す対象のない障害を追いかけることになる。<br>なお予想対比サプライズの特徴量化層 `feature_disclosure.py` は #1290 で退役し（唯一の予定消費者 #323 は not planned）、画面に会社予想由来の数字が出る経路は今のところ存在しない。**それでも収集は止めない**——発行済株式数の J-Quants 経路（`ShOutFY`）と夜間の TTM 合成の会計基準判定（`ttm_composite._load_basis`）がこの表を読む（[ARCHITECTURE.md](../ARCHITECTURE.md)）。

## Yahoo の取得（ティッカー・上場市場・絞り込み）

- **Yahoo のティッカーは `{sec_code}.T` 固定＝東証以外の単独上場銘柄は構造的に取れない（#475・2026-08-27 全数実測）**: `fetch_yahoo_history` へ渡すティッカーを組む箇所は4つ（`collector_prices.py` の backfill_historical / gap-fill / market更新 / weekly backfill）で、いずれも `.T` を決め打ちしている。株価を1件も持たない 454社を `.S`（札証）/`.F`（福証）で全数プローブしたところ **37社が取得可能**（札証 SAP=15 / 福証 FKA=22。いずれも1年窓で243バー。筑邦銀行8398・南日本銀行8554・豊和銀行8559・宮崎太陽銀行8560・第一交通産業9035・ジョイフル9942・RIZAP2928・北海道中央バス9085 等）。**初出時の「38社（SAP=16）」との差1社は 1734 北弘電社**——`.S` で `exchangeName=SAP` は返るが**バーが0本**で、取り込む値が無い。**しかも 2024-04-11 に上場廃止済みの記号**で、のちに Yahoo が出来高0の幽霊バーを1本返して誤採用された（下記「`--reprobe`」の項・#769）。**財務レコードは持つのに株価が0件**なので、px_* 特徴量を要求する全モデルから例外を出さずに落ちている。

- **Yahoo は「絞られた」ことを例外で教えない（Issue #556・#438 と同型）**: `fetch_yahoo_chart`（`collector_prices.py`）は**全エラー経路を `([], {})` へ畳む**——呼び出し側の分岐を増やさないための意図的な設計だが、そのせいで **429（レート制限）と「その銘柄のデータが無い」が区別できない**。逐次のうちは実害が無かったが、並行度を上げると「絞られて空が返り、例外は1つも出ず、鮮度だけが静かに死ぬ」経路が開く。そこで `yahoo_http_stats()`（run 単位のコンテキストマネージャ）で **status code 別に数え**、`fill_recent_stock_price_gap_yahoo` の完了ログと戻り値へ `429 / 5xx / 4xx / その他` を必ず出す（**0 のときも出す**——「出ていない」ことが読めないと監視にならない）。**関数の署名は変えない**（macro・weekly backfill・probe からも呼ばれるため、引数を増やすと呼び出し側を全部触ることになる）。並行度は `YAHOO_STOCK_CONCURRENCY`（既定 4・`FINAPP_YAHOO_CONCURRENCY` で上書き）で、**`1` にすれば逐次と厳密に同じ挙動へ戻る**。絞りすぎの判断材料は `new_rows` と `price_freshness` の p50/p05、そして 429/5xx の件数——`upserted` は投入行数（`ON CONFLICT DO UPDATE`）なので指標にならない（#474）。**1回の実測を基準線にしないこと**（同じ逐次実装のまま夜ごとに 0.646 → 0.936 s/社と +45% 振れた実測がある）。**4xx は 404 を内訳として分けて出す（`4xx=N（うち404=M）`）**——初回適用後4晩（2026-09-08〜11・並行度4）の実測で 429/5xx は 0、`new_rows` は逐次の晩（3665件）から悪化せず（3720〜3742件）、所要は 44.1分 → 11.2〜13.0分。一方 4xx は毎晩 320〜350件で横ばいで、その正体は**上場廃止社への 404**だった（株価履歴を持つ廃止社 263社・価格ゼロ社の7日ローテーション約50社・`is_active=True` のまま止まった社約20社。カテゴリ別に Yahoo を実際に叩いて確認）＝並行化とは無関係の恒常値。一緒くたに数えると、Yahoo が 401/403 のような 429 以外のコードで拒否し始めても毎晩の約320件に埋もれるので、`scripts/check_nightly_collect.py` は **404 以外の 4xx を警告**にしている。4xx の意味を「404 以外」へ変えなかったのは、内訳を持たない過去の晩と比べられなくなるため。前者 263社は毎晩のリクエストを捨てていたので、#475 のバックオフを広げた（`DELISTED_STALE_DAYS`・[DEPLOYMENT.md](../DEPLOYMENT.md) の Phase 4）。
