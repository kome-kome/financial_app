# バッチの窓はステップ予算へ分割し、超過は起票される失敗にする

## Status

accepted（2026-08-24）。Issue [#530](https://github.com/kome-kome/financial_app/issues/530)。
[ADR-0038](0038-local-postgres-is-the-primary.md)（正本のローカル化）で生まれたローカル駆動
バッチ（#503 Phase 2 / #504）の運用面の追補であり、[ADR-0031](0031-heavy-plugins-require-registered-automation.md) 系列の「登録 ≠ 実行」と同じ
系譜——**無音・無実行を検知可能にする**ための決定。

## Context

ローカル月次バッチ（`scripts/run_monthly.py`）は、タスクスケジューラの `ExecutionTimeLimit`
16時間の窓の中で6ステップを直列に回す:

    vacuum → factor_premia → macro_beta → tune:macro_risk_return → tune:macro_dlm → tune:macro_gbdt

並びは「依存順 ∧ 軽い順」で、`install_monthly_task.ps1` には**打ち切られても前方のステップは
当月分が揃う**と書いてある。しかしこの設計は「前方のステップが窓を食い尽くさない」ことを
暗黙の前提にしていた。窓の幅 16時間も、

> GHA 時代の timeout を直列に足すと最大22時間だが、GHA ランナーは実質2コアでローカルは
> 6コアあるため実測はこれより短くなる見込み

という**未実測の推定**で決めていた。実測は逆だった。

| ステップ | GHA 実績 | ローカル実測 |
|---|---|---|
| `macro_beta` | **116分**（run 30698937879・3,791銘柄×12因子） | **741.5分でも未完走**（3,795銘柄×12因子・#512） |
| `tune×3`（直列換算） | **435分**（run 29118260702 のジョブ別: 178 / 175 / 82） | 未実測 |
| `factor_premia` | — | 1.3〜2.6分 |

規模は同等（銘柄差4社）なので、この 6.4倍以上という差はローカル固有の問題である（原因は
#512 で継続。740分時点の heartbeat が `pm.sample` の内側だった＝遅いのはサンプリング本体で、
`nuts_sampler="numpyro"` の JAX/XLA 経路）。

**その結果、2026-09-01 の月次は `macro_beta` が16時間を使い切り、`tune×3` が一度も起動しない
はずだった。** μ̂（M-1/M-2/M-3 の best params と `--persist-scores`）の最終更新は 2026-07-10 で、
#504 が復活させたかった経路が #504 の窓の中で餓死する形になっていた。

**しかもこれは failure として現れない。** 窓に達するとタスクスケジューラはプロセスを止める
だけで、`run_batch` の `record_footprint` も `notify` も走らない。後続ステップは走った形跡すら
残さずに消える。`install_monthly_task.ps1` の DESCRIPTION に自分たちで「打ち切りは『失敗』と
しては現れない」と書いてあったが、**書いただけで受け止め口が無かった**。

## Decision

**バッチの窓を、ステップごとの時間予算へ分割する。超過したらプロセスツリーごと打ち切り、
`exit=124` という普通の失敗として返す。**

1. `Step` に `budget_min`（分・None は無期限）を持たせる。予算は `BUDGET_MIN` の**名前引き**の
   表から与える——`Step` の定義に直書きすると、ステップを足して予算を付け忘れたことを機械的に
   検出できない。表から引けば `budget_min=None` のまま残り、CI が落とす。
2. `Runner.run` の待ち合わせ（#522 の `Popen` + `wait(timeout=HEARTBEAT_SEC)` ループ）へ deadline を
   入れる。待ち時間を `min(heartbeat_sec, 残り予算)` にするので、**heartbeat の刻みは保ったまま
   予算ちょうどで起きる**。
3. 打ち切りは `kill_tree` で**プロセスツリーごと**。Windows では `taskkill /F /T /PID` が必須——
   venv の `python.exe` はランチャースタブで、CPU を持つ実体は子 PID の側にいる（#512 の調査で
   スタブの CPU 0秒を見て「ハングしている」と誤読しかけた実例がある）。スタブだけ殺すと実体が
   走り続け、予算で切ったつもりの計算が次のステップと CPU を奪い合う。
4. 返す値は `TIMEOUT_EXIT = 124`（GNU `timeout` の慣例。既存の 126＝ログハンドル無し、
   127＝起動失敗と衝突しない）。**足跡・起票の経路にそのまま乗る**ので、Issue 本文には
   「予算超過で打ち切った」ことが exit code の凡例として出る。
5. **窓と予算はセットでしか意味を持たない**ので、`window_problem()` が Σ予算 + マージン ≤ 窓 と
   「予算の無いステップが無いこと」を検証し、CI が月次・日次それぞれで呼ぶ。加えて
   `install_*_task.ps1` の窓の値と `WINDOW_MIN` を照合する（`tests/test_db_target.py` が
   `launch.py` の既定を `database` 側と照合しているのと同型）。

割り当て（月次・Σ925分／窓960分／マージン30分）:

| step | 予算 | 根拠 |
|---|---|---|
| `vacuum` | 45 | 実測未取得。ACCESS EXCLUSIVE を取るので長引かせない |
| `factor_premia` | 20 | 実測 1.3〜2.6分 |
| `macro_beta` | 180 | GHA 実績 116分の外側。**窓の半分未満**（tune を届かせる） |
| `tune:macro_risk_return` | 250 | GHA 178分 |
| `tune:macro_dlm` | 250 | GHA 175分 |
| `tune:macro_gbdt` | 180 | GHA 82分 |

日次は窓360分に対し `pipeline` 240 / `scores` 60（Σ300・マージン60）。通常運転は総所要
60〜70分、1日飛ばした翌日の Yahoo gap-fill 込みで 2h11m 級（#475）なので、240分は**通常運転を
打ち切らない**側に置いた値。

## Consequences

**受け入れる代償**: `macro_beta` は #512 が解けるまで**毎月 `exit=124` で失敗する**。これは
劣化ではなく可視化である——今は「静かに tune が餓死する」、後は「`macro_beta` が起票される
失敗として落ち、`tune×3` は回る」。#512 が未解決であることが毎月 Issue として現れるので、
放置しても静かにならない。

**予算値は実測が出たら見直す。** 特に `vacuum` はローカルでの実測を持っていない。予算そのもの
より「窓が分割してある」ことが本体で、値は動かしてよい（動かすときは `window_problem` が
Σを見張る）。

## 2026-09-01 の実走による訂正（#584 / ADR-0046）

初実走で**仕組みは設計どおり動いた**（`TIMEOUT` 行・`exit=124`・後続の起動・凡例つきの起票）。
ただし上の Consequences のうち2点は実測で否定された:

- **「`macro_beta` は毎月 `exit=124` で失敗する」は起きなかった。** 実際に起きたのは Smart App
  Control が jaxlib の未評価 DLL を初回ロードでブロックしたことによる **exit=1（1.4分）**で、
  予算超過は一度もない。前提だった #512 の所要（約12.6時間）自体、メモリ枯渇下で測った値の
  疑いがある（bench のフル規模外挿は 34分）。
- **`vacuum` の実測が出た**（0.3分）。予算 45分 → 15分へ引いた。ここで空いた30分が
  `deps_smoke`（5分）の枠と窓の余裕になっている。

加えて、**予算内に完走しないステップは何も残さない**ことが分かった（`hyperparameter_search` の
永続化は `search()` 完走後のみ）。窓を分割しただけでは「静かに餓死する」が「起票される失敗」に
変わるだけで、成果は同じくゼロになる。**完走見込みのあるステップにだけ予算を与える**という
原則を [ADR-0046](0046-steps-that-cannot-finish-get-their-own-task.md) で足した。

## Alternatives considered

- **残り窓を都度配分する**（各ステップが「窓の残り」を受け取る）。前方が押した分を後方が
  吸収できて一見賢いが、**どのステップが遅いのかの帰属が濁る**。予算が固定なら「180分の予算を
  超えた」が単独で意味を持ち、#512 の進捗をそのまま測る目盛りになる。
- **順序を入れ替えて `tune` を `macro_beta` より前へ。** 窓の問題は消えるが、依存順
  （`macro_beta_loadings` → M-1）を崩す設計判断であり、「M-1 の tune が先月のローディングを
  使う」ことの是非を別途決める必要がある。窓を守るために依存順を崩すのは順序が逆。
- **`draws` / `tune` を減らして所要を窓に収める。** #291 の品質ゲート（`objective_value` 比較）と
  ADR-0002 の収束基準（r_hat）を別条件の値と比較することになる。探索規模を動かすのは
  **動かした影響を測る回**でやるべきで、窓を守るついでにやらない。
- **何もせず 9/1 を観測する。** 観測はできるが、その月の μ̂ 更新が失われる。μ̂ は既に
  2026-07-10 から固着しており、9/1 を空振らせると75日超になる。
