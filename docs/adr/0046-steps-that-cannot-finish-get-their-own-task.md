# 予算内に完走しないステップは専用タスクへ出す

- **状態**: 採用
- **日付**: 2026-09-01
- **関連**: #584 / #532 / #579 / #512、[ADR-0040](0040-batch-window-is-split-into-step-budgets.md)（窓のステップ予算分割）

## Context

ADR-0040 で月次バッチの窓（16時間）をステップ予算へ分割し、超過は `exit=124` で起票される
失敗にした。2026-09-01 のタスクスケジューラ経由**初実走**でその仕組みは設計どおり動いた——
`tune:macro_risk_return` は 250.2分で打ち切られ、`TIMEOUT` 行と exit code 凡例つきの Issue
（#587）が出て、後続の `tune:macro_dlm` も起動した。

**しかし成果はゼロだった。**

| step | 予算 | 実測 | 結果 |
|---|---|---|---|
| `tune:macro_risk_return` | 250分 | 15/288 で打ち切り | 何も残らない |
| `tune:macro_dlm` | 250分 | 199/294 で打ち切り | 何も残らない |
| `tune:macro_gbdt` | 180分 | **176.3分で150件を完走** | 品質ゲートで persist スキップ |

`hyperparameter_search.py` の永続化は `search()` が**完走してからしか走らない**
（`plugin_tuned_params` への書き込みも `--persist-scores` の最終 execute も）。つまり
**予算内に終わらないステップは時間を使い切って何も残さない**。この日は tune に 680分
（11時間）を費やして μ̂ を1つも更新しなかった。

原因は2つあり、切り分けに実測が要った:

1. **メモリ枯渇**（#588 で解決）。`build_snapshots` のキャッシュ1エントリが約 1.7GB で、
   `min_coverage` の3値ぶんが常駐して約 6.1GB になり、7.9GB のマシンが詰んでいた。実走では
   `[13/288]` の直後から 156分間 1件も進まなかった
2. **所要そのもの**（未解決）。メモリが足りていても M-1 は **2.61分/件 × 288件 ＝ 約752分**で、
   GHA 実績（0.618分/件）の 4.2倍。これはマシンの性質（i5-8400・6コア6スレッド）であって
   キャッシュ修正では消えない

2 が残る限り、M-1 を月次に置いておくと**毎月 250分を捨て続ける**。

## Decision

**「完走見込みのあるステップにだけ予算を与える」を原則とし、窓に入らないステップは専用タスク
へ出す。**

M-1（`tune:macro_risk_return`）を `scripts/run_monthly_m1.py` へ切り出し、毎月2日 JST 01:00・
16時間の窓を持つ `financial_app-monthly-m1` として登録する。

| | 窓 | Σ予算 | +マージン30 |
|---|---|---|---|
| 月次本体（毎月1日） | 960分 | 863分 | 893 ≤ 960 |
| M-1 タスク（毎月2日） | 960分 | 905分 | 935 ≤ 960 |

予算は実測に**寄せず**余裕を残す（ADR-0040 の方針。パネルは毎晩伸びるので所要は据え置かず
伸びる）:

| step | 予算 | 実測 |
|---|---|---|
| `tune:macro_risk_return`（M-1 タスク） | 900 | 752分 |
| `tune:macro_dlm` | 250 → **400** | 306〜369分 |
| `tune:macro_gbdt` | 180 → **240** | 176.3分（完走実績・余裕2%では次回落ちる） |
| `vacuum` | 45 → **15** | 0.3分（ADR-0040 が留保していた実測が出た） |

`macro_beta` は 180分据え置き。bench（`scripts/bench_macro_beta.py --mode real`）のフル規模
外挿は **34分**だが、これは 250銘柄へ間引いた測定で **peak RSS 898MB もその値**である。
本番は 15.3倍の規模なので、所要ではなくメモリが律速になりうる（#512 の「742分で未完走」は
これで説明できる）。**bench は所要を外挿するがメモリを外挿しない**ため、判断は 10/1 の実走に
委ねる——#585 で heartbeat が子ツリーの RSS と空き物理メモリを刻むようになったので、次回は
実測が残る。

## Consequences

**日をまたぐ依存が生まれる。** `macro_beta_loadings`（月次本体・1日）は M-1 の入力なので、
M-1 タスク（2日）は前日の出力を使う。同じ月の中では順序が保たれるが、本体が失敗した月は
M-1 が前月の β で回る。`tests/test_run_monthly.py::test_inference_runs_before_tuning` が
「本体に `macro_beta` があり、M-1 タスクには無い」ことで担保する。

**監視対象が1つ増える。** `batch_freshness.WATCHED` へ 1行足した。**載せ忘れは「走らなかった
のに誰も気づかない」形でしか現れない**ので、`TestEveryLocalBatchIsWatched` が `scripts/run_*.py`
の集合と監視表を CI で照合する（ADR-0031 と同型の穴）。監視表の期待セットはハードコードで、
バッチが増減したら明示的に更新させる。

**登録直後は足跡が無い。** `monthly_m1_last_run` が空の間 watchdog は `missing` として起票する
（`missing_is_problem=True`）。**タスク登録の直後に1回手動実行して足跡を入れること**。
「まだ一度も走っていない」と「止まった」を同じ顔にしないための設計なので、ここは緩めない。

**ADR-0040 の Consequences のうち1つは実測で否定された。** 「`macro_beta` は #512 が解ける
まで毎月 `exit=124` で失敗する」と書いたが、9/1 に実際に起きたのは Smart App Control が
jaxlib の未評価 DLL を初回ロードでブロックしたことによる **exit=1（1.4分）**で、予算超過は
一度も起きていない。所要の想定（12.6時間）自体がメモリ枯渇下の値だった疑いがある。

**登録スクリプトは委譲する。** `scripts/install_monthly_m1_task.ps1` は既定値
（Day 2・タスク名・`run_monthly_m1.ps1`）だけを持ち、月次トリガの XML 生成・S4U・窓の検証は
`install_monthly_task.ps1` へ委譲する。**登録ロジックを2本に増やすと片方だけ直す事故が起きる。**

## Alternatives considered

- **M-1 の探索空間を削って窓に収める**（288件 → 約90件）。ADR-0040 が既に却下している道で、
  `objective_value` の比較（#291 の品質ゲート）が別条件の値と比較されるようになる。実際 9/1 は
  `macro_gbdt` が完走したのに前回スコア 0.5068 を下回った（今回 0.2359）として persist を
  スキップしており、ゲートの前提を崩す変更は影響が読めない。
- **M-1 の cadence を四半期へ落とす。** タスクは増えないが μ̂ の鮮度が構造的に落ち、実行計画が
  月に依存して watchdog の閾値導出（`cadence + 窓`）も複雑になる。M-1 は「止まって最も困る」
  モデル（`sell_ranking` の mu_source 候補）なので、鮮度を落とす側の判断は最後にしたい。
- **窓を広げる。** 月次の 16時間は日次バッチ（毎日 17:20 開始）の手前で切ってある。広げるには
  日次の起動時刻も動かす必要があり、2つのバッチの前提を同時に動かすことになる。
- **均等配分のまま放置する。** 「失敗として現れる方がよい」という ADR-0040 の思想は保たれるが、
  毎月 680分を捨て続ける。**起票される失敗が毎月同じ内容なら、それは可視化ではなく諦めである。**
