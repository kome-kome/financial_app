# プリセット/重みの昇格ゲートは実体を通して測る

## Status

accepted（2026-08-24）。Issue #529 の設計決定。ADR-0028（昇格ゲートの手続き）・ADR-0008
（#509 の実測）・ADR-0039（#517 の実測）の**測定手段**を成文化するもので、ゲートの規則自体は
変えない。

## Context

ADR-0028 の昇格ゲート（期別 rank-IC 系列 ＋ `model_stats.paired_ic_significance` の定常
ブートストラップ ＋ Bonferroni 補正）は、プリセット/重みに対して2回適用された:

- **#509**（2026-08-21・ADR-0008 に記録）: 4プリセット＋統計的最適化の是正前後
- **#517**（2026-08-23・ADR-0039 に記録）: 旧単位/新単位/バランス型の3状態

**どちらも使い捨てのスクリプトで、リポジトリに実体が残っていなかった。** ADR-0039 自身が
「アドホックなスクリプトで行った」と自認している。結果として3つの問題が出ていた:

1. **同じ測定を次にやるとき、また書き直す。** #517 は #509 と同じ枠組みをゼロから書き直した。
   3回目は確実にある（#513 のプリセット重み再設計、#520 の gap_ratio 年度混在は、どちらも
   この測定を要求する）。
2. **前回と同じ手続きで測った保証が無い。** 標準化を `fit_feature_columns`（値を p1-p99 で
   クリップしてから zscore）で行うか `fit_zscore_stats` ＋ `normalize_transform`（生値を
   変換して ±5 クリップ）で行うかで**消費側との整合が変わる**が、この選択は prose のどこにも
   書かれていなかった。
3. **正しい測り方の実体が無いので、次も同じ間違いへ寄る。** `/api/backtest` が使えない理由
   （3/6/12/18/24ヶ月は終端が今日で共通＝独立でなく検定力ゼロ）は ADR-0028 にあるが、
   代わりに何を使うかがコードとして存在しなかった。

`scripts/candidate_bakeoff.py`（モデル候補）・`scripts/macro_feature_bakeoff.py`（マクロ系列）
は同じ `paired_ic_significance` を実体として持っており、**プリセット/重みの比較にだけ実体が
無い**という非対称になっていた。

## Decision

### 1. `scripts/preset_ic_gate.py` を唯一の実体にする

入力は「比較したい重み dict の集合」だけ。出所は問わない（`PRESETS` の静的4本 /
`recommend_factor_premia` の run_id 指定 / 手書きの JSON）。プリセット・重みの rank-IC 比較を
アドホックに書き直さない。

### 2. 標準化は消費側の関数をそのまま呼ぶ

`plugins.recommend.fit_view_metric_stats` → `standardize_metric` を**そのまま import して
使う**。パネルは numpy 配列なので `_panel_rows` で属性アクセスできる形へ写す薄いアダプタだけを
挟む。列ごとに `fit_zscore_stats` を呼び直す実装にすると消費側と別コードになり、次の乖離源に
なる。スコアの分母も `weight_present`（存在指標の |w| 和）で `RecommendPlugin.execute` と同一。

**この選択は実測で値を動かす。** パネルの `z_momentum` は生の log return（#519 で
`build_period_panel` は意図的に標準化しない）だが、本番では `compute_momentum_z` が期内
winsorize→標準化した値を渡す。揃えると バランス型 = **+0.0210**、生のまま合成すると
**+0.0238**。ADR-0008 / ADR-0039 の記録値と一致するのは**揃えた側**で、過去のアドホック測定も
同じ扱いをしていたことがこれで裏付けられた（`--raw-momentum` で切り替えて差分を見られる）。

### 3. gap_ratio はパネルへ載せない。代わりに「測れなかった重み」を必ず出す

`build_period_panel` が `gap_ratio` を持たない理由（sector_ols の非NULL率が 2020〜2024年度
= 0% / 2025年度以降 = 67%超で、含めると有効期間が2ヶ月に落ちる）は ADR-0008 Decision 1 の
まま変えない。

そのうえで **プリセットごとに `Σ|w_{パネルに無い列}| / Σ|w|` を必ず表へ出し**、閾値
（`--max-missing-weight`・既定 0.20）を超えた行は rank-IC を出しつつ**判定からは外す**。

| プリセット | 測れない重み |
|---|---|
| 割安重視 | **44.4%**（`gap_ratio` 2.0 / 4.5） |
| バランス型 | 9.8%（0.5 / 5.1） |
| 成長重視 | 7.0%（0.3 / 4.3） |
| 高収益重視 | 0% |

黙って落とすと「割安重視は rank-IC 負」という**測っていない重みを含んだ結論**が独り歩きする。
ADR-0008 はこの限界を prose の末尾に書いていたが、表の行は他と同じ見た目で並んでいた。

### 4. パネルの世代を必ず出す。過去の実測と比べるときは期を揃える

実行のたびに期数・起点 ym・終端 ym・社数（中央値/最小/最大）・factor_names を印字する
（ADR-0028 規則3）。**パネルは株価の蓄積で毎晩伸びる**——本 ADR の実測日（8/24）時点で
62期（2020-07..2025-08）であり、ADR-0008 の61期（..2025-07）とは1期違う。揃えずに比べると
0.002 程度の差が出て「手続きが違う」ように見えるため、`--until 2025-07` で期を揃える。

### 5. Bonferroni は検定数から機械が出す。p 値の下限を印で示す

`ALPHA = 0.05 / N_TESTS` を必ず表へ印字し、`N_TESTS` は実際に走らせた検定数から導く。
ADR-0008 は「6検定」と書きながら表が5行で、後から突き合わせられない状態になっている。

`bootstrap_mean_ci` は Davison-Hinkley フロアにより `p >= 2/(n_boot+1)`（既定 n_boot=2000 で
0.001）を返す。**ADR-0008・ADR-0039 に並ぶ p=0.001 はすべてこの下限**であり「p=0.001 だから
強い」ではない。下限に達した行には `[p at floor]` を付ける（`--n-boot` で引き下げられる）。

### 6. キャッシュは opt-in、バッチには組み込まない

パネルのキャッシュは `--cache-panel` を明示したときだけ使う。bakeoff キャッシュがデータ世代を
持たず黙って旧世代を返した前例（#454/#456）があるため、既定はフルビルドへ倒す。DB へは書かず
（読み取りのみ）、月次バッチにも入れない——`heavy=True` プラグインではないので ADR-0031 の
登録義務は無く、判断が要るときに人が回す診断ツールとして置く。

## 実測: ADR-0008 / ADR-0039 の再現（2026-08-24・61期・`--until 2025-07`）

**測定手段を足すこと自体は昇格ゲートを通す作業ではない**（#529）。受け入れ条件は既存の実測値を
再現できることなので、それを先に確かめた。

再現に使ったコマンド:

```powershell

python -m scripts.preset_ic_gate --cache-panel --until 2025-07 --preset バランス型 --premia-run-id rfp_20260820T183244Z --premia-run-id rfp_20260823T121746Z --baseline "premia:rfp_20260820T183244Z(pv=None)"
```

`rfp_20260820T183244Z`（`preprocess_version` が NULL＝#509 以前の生スケール・`z_eps` = −3.3367）
と `rfp_20260823T121746Z`（`winsor_z_v1`・`z_eps` = +0.0175）は本番 DB に残っており、
ADR-0039 の A/B 状態は run_id 指定だけで再現できる。**`get_dynamic_preset` は世代不一致の行を
採らないが、本スクリプトは採る**——古い重みを測ることが用途そのものなので、世代はラベルへ出して
区別する（`(pv=None)` / `(pv=winsor_z_v1)`）。

## Considered Options

- **`/api/backtest` の `SCORING_SOURCES` を拡張して rank-IC を出す** → 却下。あれは as-of の
  実現リターン評価で、3/6/12/18/24ヶ月の終端が今日で共通＝独立でなく検定力が無い
  （ADR-0028・#509 でこの訂正自体が記録されている）。ベンチマークも母集団ではなく
  `scored[:500]` なので、スコアが変わればベンチも動く。
- **`scripts/candidate_bakeoff.py` に相乗りする** → 却下。あちらは `walk_forward_cv_monthly`
  → `oof_backtest` の**学習を伴うモデル比較**で、fold・embargo・残差の概念を持つ。プリセットは
  学習を伴わない重みの線形結合なので、同じ枠組みへ押し込むと「fold とは何か」が空論になる。
  共有するのは `paired_ic_significance` と `scripts/_cache.py` に留める。
- **`gap_ratio` を載せたパネルを別に作る** → 保留。sector_ols の充足率が今のデータでどうなって
  いるかの再測定が要る（#520）。載せられても期数が激減して検定力を失う可能性が高く、その判断は
  #520 で行う。本 ADR は「載せない代わりに落ちた重みを明示する」までを決める。
- **月次バッチへ組み込んで毎月自動で回す** → 却下。昇格ゲートは判断が要るときに回す道具で、
  定期実行しても読む人がいなければ ADR-0031 の「登録≠実行」がもう一度出るだけ。

## Consequences

- **#513（プリセット重みの再設計）・#520（gap_ratio の年度混在）が同じ道具で測れる。** 特に
  #513 の B/C 案は walk-forward の昇格ゲートを要求しており、その入口がこれになる。
- **「6検定と書いて5行しか無い」型の記録漏れが起きない。** α と検定数は機械が出して表に載る。
- **p=0.001 の誤読が構造的に防げる。** 下限に達した行には印が付く。
- **パネルが伸びるので、過去の値と比べるときは `--until` が要る。** これは欠点ではなく、
  ADR-0028 規則3（世代を併記する）をコードで強制した結果。
- 消費側（`plugins/recommend.py`）の標準化経路を変えたら、このスクリプトの測定単位も自動で
  変わる。**それが狙い**だが、過去の実測との比較は前処理の世代（`PREPROCESS_VERSION`）を
  跨ぐことになるので、ADR-0039 と同じ注意が要る。
