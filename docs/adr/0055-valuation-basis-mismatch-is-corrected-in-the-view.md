## Context

`collector_prices._compute_market_values` が `financial_records` へ焼き込む
`per` / `pbr` / `market_cap` / `div_yield` は、**分子と分母が別の基準を名乗っている**。
株価は Yahoo / J-Quants 由来で企業イベントを遡及調整済みだが、分母になる 1 株指標
（`pl_eps` / `bs_bps` / `dps` / `issued_shares`）は提出当時の株数基準のままである。
分割より前の年の行だけが「調整後株価 ÷ 旧基準の 1 株指標」になり、
per / pbr / market_cap が分割比ぶん小さく、`market_cap` を分母に持つ
`nc_ratio` / `z_nc_ratio` と `div_yield` が同じだけ大きく出る。

**この壊れ方はエラーを出さない。** 保存された PER は妥当な数字であり、行数も鮮度も正常で、
`financial_records` に「どの基準で焼いたか」を示す列が無いので事後に判別できない。
最新行は現在株価と最新の提出値で基準が揃うため、既定の画面（最新年度のスクリーニング・
推奨）には出ない。出るのは学習・バックテストのパネルと、**年度を指定した**画面である。

#654 の測定で被害量が確定した（ローカル正本・読み取りのみ・2026-09-12）:

- **1,948 行 / 451 社 = 全 annual 行の 6.41%**
- 歪み倍率 F は p50 = **2.00** / p90 = 5.00 / max = 12.50。`F>=2` が 1,812 行、`F>=5` が 302 行。
  逆側（併合）は `F<=0.5` が 61 行
- 断面順位の移動（モデルが使うのは水準ではなく断面の相対位置）: `per` 中央値 27.9pt・
  25pt 超動く行 **940**、`pbr` 24.8pt、`div_yield` 31.8pt、`nc_ratio` 13.2pt
- 株価基準の内訳は adjusted 1,399 / unknown 549 / **raw 0**。「分割前に焼かれてそのままなので
  実は無害」な行は 1 件も無い
- 公式 `AdjFactor` との突合は一致率 **0.967**（agree 29 / disagree_magnitude 1・
  陰性対照の見逃し 0 社）。スナップ（観測比を定番比へ寄せる処理）は 1 件も誤動作していない
  （`agree_rate` と生比も許容した `agree_rate_raw_ok` が完全一致＝`agree_raw_only` が 0 件）

読む側は M-1 `macro_risk_return`（`per` / `pbr` が既定特徴量）と
M-2 `macro_gbdt` / M-6 `macro_enet`（`per` / `pbr` / `div_yield` / `nc_ratio` が既定で全部 ON）。
M-3 `macro_dlm` は `fin_features` を持たないため影響 0。
画面側は年度指定のスクリーニングと CSV、M-8 ネットキャッシュ分析、`/api/backtest`、
買い推奨の `min_market_cap` フィルタ。

**`scripts/preset_ic_gate.py` ではこの歪みを測れない。** `recommend_factor_premia.build_period_panel`
のパネルは `z_roe` / `z_op_margin` / `z_revenue` / `z_cf_ratio` / `z_equity_ratio` /
`z_eps` / `z_de_ratio` の 7 列だけで、per / pbr / div_yield / market_cap / nc_ratio を
1 つも含まない。

## Decision

### 1. 補正は `financial_metrics` VIEW が当て、`financial_records` の生値は書き換えない

決め手は **F が行の固有値ではない**こと。F は「その行の年より**後**に起きたイベントの
累積積」なので、新しい分割が 1 件起きればその会社の過去全行の F が増える。
実列へ焼き付ける方式を採ると、分割のたびに過去行を修復し直す運用が必要になり、
**回し忘れは失敗として現れない**（#504 と同型）。VIEW で当てれば係数表の洗い替えだけで
自動追従する。

副次的な利点が 2 つある。`nc_ratio` / `z_nc_ratio` は VIEW の中で補正後 `market_cap` から
計算されるので、別途何もしなくても整合する。そして生値が無傷なので、検出器の偽陽性が
後から判明したときに取り消せる。

### 2. 係数は専用テーブル `split_adjustment_factors` に持ち、VIEW が LEFT JOIN する

`regression_results` を LEFT JOIN して `predicted_market_cap` / `gap_ratio` を載せている
既存の書き方と同型。行は `(edinet_code, year)` の累積 F で、**F = 1.0 の行は持たない**
（VIEW が `COALESCE(saf.factor, 1.0)` で埋めるので、歪んでいる 1,947 行だけ持てば足りる）。
寄与したイベント数 `n_events` と種別 `kinds` を併記する＝「なぜ補正したか」を SQL で追える。

`financial_records` に列を足す形は採らない。`split_factor` はその行自身の属性ではなく
「その後に起きた別の年の企業イベント」から導かれる値で、行を書いた収集器には知りようがない。

補正の向きは列ごとに逆で、**唯一の源は
`scripts/measure_split_valuation_bias.py::COLUMN_DIRECTION`**（per / pbr / market_cap は ×F、
div_yield / nc_ratio は ÷F）。VIEW がこれに従っているかは
`tests/test_split_adjustment_factors.py::TestViewAppliesTheDirections` が定義 SQL を
ソース照合する。**向きの取り違えは符号が逆の歪みを新しく作る**ので、実値の突合が
Postgres でしかできない以上、演算子だけでも CI で縛る。

**`stock_price` は補正しない。** `COLUMN_DIRECTION` に入っておらず、調整済み株価そのものとして
`sector_ols` の目的変数や画面が読む値である。その結果、補正された行では
`per <> stock_price / pl_eps` になる——**意図した非対称**で、GOTCHAS へ記す。

### 3. 検出アルゴリズムは #654 の測定器の純関数を import して再利用する

`detect_events` / `cumulative_factors` をコピーしない。あちらの純関数ブロックは
`database` / `collector_prices` / `httpx` をトップレベルで import しないことを
テストが固定しており、そのまま使える。`kinds` / `n_events` だけは寄与集合を
`collector_prices` 側で引き直すため、**寄与集合の積が `factor` に一致すること**を
テストで照合する（`e.year > row.year` の述語が正本から乖離したらそこで落ちる）。

### 4. 全種別を補正し、`unsnapped` だけ外す

検出 491 イベントの内訳は split 394 / composite 77 / reverse 16 / unsnapped 4。
**偽陽性（深い割引での増資を分割と見間違える）は composite 側に残る**。既知の 2 例
（E01121 日本板硝子・株数 ×1.5545・純資産 +30% ／ E05716 地域新聞社・×1.4013・+116%）は
`bs_bps` 逆比とのずれが 8.2% / 7.4% で許容 15% の内側に入る。

それでも補正する側を採るのは、**誤差の種類が非対称**だから。未補正の歪みは「後に分割した社
だけが一律に割安に見える」系統誤差で、モデルはこれを規則として学習する。誤補正は増資の
深さ次第のランダム誤差に近い。系統誤差 1,948 行を消してランダム誤差を数十行入れるのは、
断面順位を使うモデルにとって明確な改善である。`kinds` を持つので、あとから composite だけ
外す変更は 1 行で済む。

**形（比の値）だけでは本物を選べない。** 観測比 1.5545 は定番比 1.5 から対数距離で 3.6% しか
離れておらず、本物の 1:1.5 分割（canonical_hist で 20 件）と見分けがつかない。
ADR-0053 が往復段差で確定させた教訓と同型で、分離には独立した第 2 の信号が要る
（純資産総額の前年比が候補。分割は純資産を変えないが増資は増やす）。これは #654 の測定器の
アルゴリズム変更になるため [#657](https://github.com/kome-kome/financial_app/issues/657) へ切り出した。

なお「偽陽性率およそ 5%」は**測定で裏が取れた数字ではない**。`verify-sample` の集計は
`agree` 29 / `disagree_magnitude` 1 のみで `no_official_event` が 0 件であり、
上の 2 社は契約窓（2024-06-20〜2026-06-20）の外でサンプルに入っていない。手で観察した概算である。

> **訂正（2026-09-13・#657）**: 2 社は契約窓の**内側**にある（E01121 は年度 2026、E05716 は年度 2025）。
> 30 社の層化抽出に選ばれなかっただけである。契約窓内の全数突合で測った偽陽性率は
> **6/94 = 6.4%**（composite 5/22・split 1/69）で、2 社はどちらも偽陽性と確定した。決定 4-4 を参照。

### 4-2. 株数が追隨しない社の第2経路は実装するが既定 OFF で入れる（#656）

検出器は「`issued_shares` の年次比」を候補ゲートにするので、**分割を 1 株指標にだけ
反映して株数が据え置きの社**を候補にすら上げられない。そこで `bs_bps` の年次比を
候補ゲートにし、`pl_eps` の比を交差検証にする**第2経路**を足した
（`detect_events(..., bps_path=...)`・`ShareEvent.source` で経路を残す）。

実測（2026-09-12・接続先 local）では確かに大きく拾う。

| | 第1経路のみ | 両経路 |
|---|---|---|
| 検出イベント | 492 (456社) | 749 (676社) |
| 被害行 / 社 | 1,953 / 452 | 2,920 / 672 |

第1経路の 492 イベントは**1 件も変わらない**（同じ (ec, year) を両経路が拾ったら
株数側を採って 1 件へ畳む——畳み損ねると F が比の二乗になる）。看板例の E03137 しまむらも
F(2023)=6.0 / F(2024)=3.0 / F(2025)=3.0 で拾えるようになった。

**それでも既定を OFF にしたのは、公式 `AdjFactor` との一致率が 0.367（11/30）だったからである**
（`verify-sample --bps-path --source bps --n 30 --controls 10`・#654 の第1経路は 0.967）。

**外れ方はランダムではなく、見つけた 16 件すべてで検出 < 公式だった。** 原因は
`bs_bps` が分割以外の理由（内部留保・有価証券の評価差額）でも増えること。真の分割比を F、
bps の成長率を g とすると観測比は `F / (1 + g)` になる。**実測の g は 18%〜67%** と幅が広く、
隣り合う定番比の間隔（例 2.0 と 2.5）を超える。地方銀行がサンプルに多いのは偶然ではなく、
2024〜2025 の有価証券評価益で純資産が伸びた上で分割しているからである。

「`raw` 以上で最小の定番比を採る」上向きスナップ（g > 0 は一方向なので理屈は通る）でも
**0.778（21/27）**で止まる。残る誤りは真の比が 3.0〜6.0 なのに観測が 2.2〜4.0 へ落ちるもので、
間に `2.5` がいるため分離できない。つまり **bps 比は「分割があった」は言えるが
「何倍か」を決められない**。倍率を間違えた補正は、系統誤差を別の系統誤差へ置き換えるだけで、
決定 4 が採った「系統誤差を消してランダム誤差を入れる」とは別の取引である。

**存在の検出としては優秀だった**。抽出 30 社のうち 27 社に公式イベントがあり（偽陽性 3 社）、
**陰性対照の見逃しは 0 社**。だから経路自体は捨てず、`--bps-path` で選べる形で残す。
倒すのは倍率を独立な第 3 の信号から取る改良が済んでからである。

候補は 2 つあるが、どちらもこのサンプルでは結論が出なかった。

- **1 年遅れの `issued_shares`**。しまむらは bps が 2024・株数が 2025 に動く。実測では
  隣年の株数比が公式と一致したのは **8/27** だったが、**サンプルの大半が year=2026＝最新年で
  翻年の行がまだ存在しない**（契約窓が 2024-06〜2026-06 なので抽出が最新年に寄る）。
  year=2025 のケースでは 6.046 / 4.012 / 2.0039 など公式と一致している。
- **公式 `AdjFactor` そのもの**。契約窓の内側なら正確だが、窓の外（2024-06 より前）に
  遡れない——補正が一番欲しいのは古い断面なので、これだけでは埋まらない。

### 4-3. 第2経路の倍率は翌年の `issued_shares` から取り、既定を ON へ倒す（#659）

決定 4-2 が保留した「倍率を独立な第 3 の信号から取る」を、**1 年遅れの `issued_shares`**
で実装した。しまむら型は bps が動いた翌年に株数が動くので、`shares[Y+1] / shares[Y]` に
真の分割比が現れる。株数は内部留保や評価差額では動かない量なので、倍率の基準として素直である。

**候補の出し方（存在の検出）は変えていない。** 決定 4-2 が「存在の検出としては優秀」と
記録したとおりで、変えたのは倍率の出どころだけである。

**第 3 の信号が取れない年のイベントは採らない。** 翌年の行がまだ提出されていない（最新年）、
翌年も株数が動かない、向きが逆、定番比へ寄らない、のいずれもここへ来る。倍率を間違えた補正は
系統誤差を別の系統誤差へ置き換えるだけで、決定 4 が採った取引とは別物になるからである。
**採らなかった年が永久に埋まらないわけではない**——係数表は毎晩の全置換なので（決定 5）、
翌年の決算が入った時点で自動的に F へ入る。

**同じ株数の動きを 2 回数えない。** bps 経路が翌年の動きを倍率に使い、第1経路がその翌年を
独立したイベントとして採ると `cumulative_factors` が比を二乗する（決定 4-2 の `dup_with_shares`
と同じ実害）。第1経路を残す側へ畳む。

#### 実測（2026-09-12・接続先 local）

| | 第1経路のみ | 両経路（旧・bps 比を倍率に） | 両経路（新・翌年の株数を倍率に） |
|---|---|---|---|
| 検出イベント | 492 (456社) | 749 (676社) | **606 (559社)** |
| うち第2経路 | — | 257 (245社) | **114 (113社)** |
| 被害行 / 社 | 1,953 / 452 | 2,920 / 672 | **2,381 / 555** |
| 公式との一致率 | 0.967 (29/30) | 0.367 (11/30) | **0.962 (25/26)** |
| 陰性対照の見逃し | 0 社 | 0 社 | **0 社** |

第2経路の件数が 257 から 114 へ減ったのは**倍率の根拠が無い分を落としたから**である。
棄却の内訳は `no_lagged_row` 74・`lagged_flat` 122・`lagged_direction` 5・
`lagged_unsnapped` 1・`dup_lagged_with_shares` 2。第1経路の 492 イベントは 1 件も変わらない。

唯一の不一致 E38760 は窓の中に公式イベントが 2 件あり積が 4.0 になるが、翌年の株数比は
2.1966 で片方しか捉えていない。**一致率 >= 0.90 かつ陰性対照の見逃し 0 社かつ分母 >= 20 件**
を満たしたので、`DEFAULT_BPS_PATH = True` へ倒した。

#### 突合の窓に `partial` を足した理由

第2経路の倍率は翌年の行から取るので、突合には「公式が判定できる」と「翌年の行が提出済み」の
両方が要る。ところが契約窓は直近 2 年しかなく、`in_coverage` は窓が契約窓へ**完全に**収まる
ことを求めるため、判定できるのは当期末が 2025-08〜2026-05 のイベントに限られる。その翌年の
決算（2026-08〜2027-05）は 1 社も提出されていない——**2 つの条件は排他**である（実測:
契約窓の内側にある第2経路だけのイベント 57 件はいずれも最新年）。

そこで `in_coverage(..., mode="partial")` を足した。窓が契約窓と**重なって**いればサンプルに
入れ、**重なりの中で公式イベントが見つかった件だけを分母に数える**。見つからなかった件は
「分割が無かった」と「契約窓の外で起きた」を区別できないので `no_official_event_partial` に
して分母から外す（分母の規則は `MATCH_DENOMINATOR` が唯一の源で、CLI へ書き写さない）。

**これは倍率が合っているかだけを測る窓である。** 偽陽性率は測れない（公式が返さないことを
「分割が無かった」と読めないため）ので、既定は `full` のままにし `--coverage partial` を
明示したときだけ緩める。偽陽性の分離は #657 が純資産総額で別に測る。

#### 公式 `AdjFactor` を本番経路へ入れなかった理由

決定 4-2 が挙げたもう 1 つの候補（公式 `AdjFactor` を倍率に使う）は採らなかった。
係数表を作り直す `rebuild_split_adjustment_factors` は毎晩の収集パイプラインの内側で走る
（決定 5）。ここへ公式 API を入れると、毎晩の係数表が J-Quants のレート制限と契約窓に縛られ、
**外部サービスが落ちた晩に補正が静かに全部外れる経路**ができる。案 1 は追加のデータ取得が
ゼロで 2018 年まで遡れるので、本番経路には案 1 だけを置く。窓の内側を公式で埋める併用は
**#661** へ送った——棄却 74 件の `no_lagged_row`（＝最新年）と契約窓の内側はちょうど
相補的なので、埋めるならそこである。
→ #661 で、**係数表の作り直しには API を入れず、catchup が DB へ残した公式値を読む**形で
併用した（決定 4-5）。上の理由はそのまま生きている。

### 4-4. 第1経路に純資産総額のチェックを入れ、許容は 1.0 にする（#657）

決定 4 が挙げた「純資産総額の前年比」を、第1経路の3つ目の条件として入れた
（`detect_events(equity_tol=...)`・既定 `DEFAULT_EQUITY_TOL = 1.0`）。株数と**同じ向きに**
`bs_total_equity` が `1 + tol` 倍を超えて動いたら、増資（併合側なら減資）と読んで採らない。
純資産が減る向きは赤字・減損であって増資の証拠にならないので、片側でしか判定しない。
純資産が欠損・0 以下の社は今日までどおり採り、`n_unknown` に数える（実測では該当 0 件）。

#### この信号で分離できる範囲は狭い

**`bs_bps ≈ 純資産総額 ÷ 株数` が成り立つ社では、純資産比は何も足さない。**
`bps逆比 / 株数比 = 1 / 純資産比` なので、bps の交差検証（許容 15%）が既に「純資産の伸びが
±15% 程度」を見ている。第1経路 492 件で整合度 `(bps逆比/株数比) × 純資産比` を測ると、
中央値 1.000・5〜95% が 0.951〜1.077 で、ほぼ全件でこの関係が成り立っていた。

したがって、**深い割引の増資（決定 4 が問題にした形）はこの信号でも分離できない。**
簿価の 1/3 で株数を 1.5 倍にしても純資産は +16.7% しか増えず、本物の分割でも純資産は
業績で伸びる（第1経路 split の中央値 +8.2%・p95 +16.8%）。落とせるのは `bs_bps` と
純資産総額が食い違う社だけである（E01121 は整合度 1.196、E05716 は 2.002）。
整合度が 2 前後の社が 3 社あり（E05716・E36173・E38739）、期末後に分割した社が 1 株情報を
分割後の基準で開示している可能性があるが、確かめていない。

#### 既定の決め方（実測の前に宣言した規則）

格子 `EQUITY_TOL_GRID = (0.15, 0.25, 0.40, 0.60, 1.00)` のうち、次の 3 つを全部満たす最小値を
既定にし、1 つも満たさなければ無効（`None`）のままにする、と先に決めた。

- (a) 契約窓内の全数突合で、チェックが落とすイベントに `agree` / `agree_raw_only` が 0 件
- (b) 同じく、`no_official_event`（公式に分割が無い＝偽陽性）を 1 件以上落とす
- (c) 契約窓の外で落とす第1経路のイベントについて、Yahoo の split に
  「イベント窓内で定番比と 5% 以内で一致するもの」が 1 件も無い

`disagree_magnitude` は害にも利益にも数えない（落としても F=1.0 という別の誤りに置き換わるだけ）。

### 4-5. 翌年の行が無い最新年は、DB に残した公式 `AdjFactor` で倍率を取る（#661）

決定 4-3 が採らなかった `no_lagged_row`（翌年の決算がまだ無い第2経路のペア・74 件）を、
公式 `AdjFactor` で埋めた。その 1 年のあいだ、最新年の分割より前の全断面が補正されないまま
M-1 / M-2 / M-6 の学習パネルへ入っていたからで、F は「その行より後のイベントの積」なので
最新年のイベントは被害行が最も多い。

#### 決定 4-3 の理由とどう両立させたか

**係数表の作り直しには API を入れない。** 公式の値は新しい表 `jquants_adj_factor_events` に
持ち、書き手は J-Quants を叩く経路の側だけに置いた。

- 毎晩の J-Quants catchup が、受け取った日次バーから `AdjFactor != 1`（普通株のみ）を残す。
  応答には全銘柄ぶん載っていたのに捨てていた値で、**API 呼び出しは 1 回も増えない**。
  価格行の選別（`AdjC != C` / スピンオフ）より前で拾う——分割の前後は価格行を捨てる日と重なりやすい。
- #661 より前に契約窓を通り過ぎたイベントは、一回きりの `scripts/backfill_adj_factor_events.py` で埋める。

`rebuild_split_adjustment_factors` はこの表を読むだけである。J-Quants が落ちた晩は行が
増えないだけで、既に残した値と補正は消えない。

#### 「あれば使う」だけにする

**表に行が無いことを「分割は無かった」とは読まない。** catchup が見るのは `today-90〜today-80`
の日付だけで、PC が止まっていた晩は取り直さず、エンバーゴ（直近約 12 週）の中の分割はまだ
行が無い。どれも「行が無い」に見えるので、イベント窓（前期末−45日, 当期末+45日]の中に公式
イベントが無ければ今日までどおり採らない。取りこぼしは取り込み CLI を回し直せば埋まる。

窓の中にあれば、積の逆数を第 3 の信号にして、翌年の株数と同じ規則で「1.4 倍以上動いているか」
「bps と向きが合うか」を判定する。bps と eps の交差検証を通ったペアにしか使わないので、
誤った社へ付いた値が単独で補正を作ることはない。

#### 公式の比は定番比へ丸めない

計画では翌年の株数と同じく `snap_to_canonical` へ通すつもりだったが、実測で次が分かって
やめた。定番比の表に 6 と 7 が無いので、E38205（1:6）と E38979（1:2 と 1:3 の積 6）は
5（composite）へ寄って **F が 17% 小さく入り**、E02128（1:7）は残差 1.4 で採られない。
**丸めは株数比に増資の分が混ざるのを切り離す仕組み**で、`AdjFactor` は株価の遡及調整に
使われた係数そのもの＝F の正本なので、そのまま使う（`kind` は向きだけで split / reverse）。
定番比の表そのものに 6 と 7 を足す案は、既存の第1経路の composite（株数比 5.768 など）の
丸め先まで変え、決定 4-4 の全数突合をやり直すことになるので採らなかった。
→ #669 で候補の本物の比を確かめた。5.768 は 1:5 分割＋増資で 6 を足す根拠は無く、表には
1/3 と 1/15 だけを足した（決定 4-6）。

#### 翌年の株数と公式の両方が取れるときは、翌年の株数を優先する

倍率は翌年の株数から決めたまま変えず、食い違いは `stats["bps_path"]["official_crosscheck"]`
と夜間ログに数えるだけにした。既存の係数表を公式で動かすのは #661 の範囲（最新年を埋める）を
超えるうえ、どちらを信じるかの根拠がまだ無い。毎晩追加の取得なしに、2 つの書き手が合っているか
を測り続けられる。

**測定器の CLI（`detect` / `verify-sample`）には公式を渡さない。** 公式から倍率を決めた
イベントを公式と突き合わせると定義上必ず一致し、一致率が黙って膨らむ。

#### 実測（2026-09-13・接続先 local・契約窓 2024-06-21〜2026-06-21）

取り込みは 108 社（倍率待ちのペアを持つ社＋翌年株数と突き合わせる社）・約 36 分で、
96 社から 102 件のイベントが取れた。係数表への影響は、同じ annual 行で公式の有無を切り替えて
読み取り専用で計算した（係数表は夜間バッチが作り直す）。

  **63 件すべてで bps 比が公式比より小さかった**——決定 4-3 の「bps 比は `F/(1+g)` になる」と整合する。
- 公式はあったが採らなかったのは 1 件（E37147・bps は併合方向なのに公式は 1:2 分割＝`official_direction`）。

#### 限界

- **イベント窓は当期末+45日で切れる。** 期末後かなり経ってから効力を持つ分割は、公式があっても
  採られない（採らない側への誤り）。窓を提出日まで広げるには `AnnualRow` に提出日が要り、
  突合の定義（一致率 0.962）も変わる。
- 取り込み CLI は候補社だけを社単位で取るので、候補にならない社の過去のイベントは表に無い。
  その社が将来倍率待ちになる時点（決算の後）には、夜間 catchup が既に残している前提である。
- 第1経路に残る偽陽性 5 件（決定 4-4）は、同じ表で判定できるが、既存の補正を減らす変更なので
  この決定には入れていない。

### 4-6. 定番比の表には、候補の本物の比が確かめられ、巻き込みを起こさない比だけを足す（#669）

決定 4-5 は公式由来の倍率を丸めないことで表の欠け（6 と 7 が無い）を避けたが、第1経路（当年の
株数比）と第2経路（翌年の株数比）は今も `snap_to_canonical` を通る。表に無い比は、近い定番比へ
composite で丸まって F が誤るか、`unsnapped` として F に入らないかのどちらかになり、
**どちらもエラーは出ない**。main の検出器で該当しうる候補が 5 件あった。

規則は先に決めた（2026-09-13）。

- (a) 候補の本物の比を、公式 `AdjFactor`（契約窓の内側）か Yahoo の splits（外側）で確かめる。
  確かめられた比だけを足す（疑いの比を推測で足さない）
- (b) 足した表で倍率（`canonical` / `kind`）が変わるイベントを**全件**出し、それも同じ方法で確かめる。
  1 件でも「公式に分割が無い」「倍率が違う」イベントを新たに補正へ入れる比は足さない

(b) を置いたのは、表の比が 1 社の丸め先だけでなく、その比の周りにある全イベントの寄り先を
変えるからである。1 社の裏付けで足すと、分割でない株数の動きまで補正へ入りうる。

### 4-7. 上場廃止をまたぐペアは比べず、定番比に 15 を足す（#672）

決定 4-6 の限界に残した E05698 の本物の 1:15 を補正するには、E05714 型のペアを検出側で落とす
必要があった。同じ EDINET コードのまま上場廃止→再上場した社では、欠損年をまたいで旧社と新社の
行が「直前の使える行」としてペアになり、株数と `bs_bps` がたまたま逆向きに同じくらい動くと
交差検証を通る。

#### 判定材料を欠損年の長さだけにしない

`gap_years >= 2` のペアは本物の分割にもある（XBRL の取りこぼし・決算期変更。E03078 大塚家具は
決算期変更で 2018→2020 になっている）。長さで切ると本物を落とすので、長さは「少なくとも 1 期
ぶんの通期行が無い」という前提条件にだけ使い、**別の実体と読む根拠は、ペアの期間の中にこの社の
市場価格が 1 年以上無く、当期末までに価格が戻っていること**に置いた。`companies` には上場日の列が
無く、`delisted_date` は今起きた遷移しか持たないので、過去の上場廃止を判定する材料にならない。

上場廃止→再上場は週次株価に 2 つの形で現れる。

| 形 | 実例 | 週次株価 |
|---|---|---|
| 系列の開始が遅い（旧社の価格が表に無い） | E05714 ソニーFG（2020 年廃止・2025-09-29 再上場） | 2025-09-29 から始まる。Yahoo の `firstTradeDate`（8729.T）も同日 |
| 系列が途中で途切れる（旧社の価格が残る） | E03530 SBI新生銀行（2023 年廃止・2025 年再上場） | 2023-09-25 の次が 2025-11-17（784 日） |

条件（`listing_gap_in_pair`）:

- `gap_years >= 2`（`LISTING_GAP_MIN_YEARS`）
- 価格の空白（系列の開始前、または系列の途中で隣り合う週の間隔が 365 日以上）のうち、価格が戻った週が
  窓 `(max(前期末, 週次表全体の開始日), 当期末]` の中にあり、窓の中に入っている空白の長さが 365 日
  （`LISTING_GAP_MIN_DAYS`）以上のものがある

週次表全体の開始日（2019-07-29）より前はどの社にも価格が無いので空白に数えない。当期末より後に
価格が戻る空白は数えない（当期末の行が上場廃止中に提出されたものなら、旧社と同じ実体でありうる）。
**系列を持たない社は判定しない**（上場廃止で価格が消えた社と区別できない）。判定はペア単位で、
第1経路・第2経路のどちらにも渡す前に外す。第2経路が翌年の株数を先読みするときも、(当年, 翌年) が
該当すれば翌年の行が無い年と同じ扱い（公式 `AdjFactor` か倍率待ち）にする。
入力は `database.load_price_series` が読む（空白は SQL の LAG で測り、該当する数行だけを返す）。

#### 規則 (b) の判定単位を「F が変わる行」へ改める

15 を足すと第2経路で E23634 アミタ HD が新たに入る（翌年の株数比 15.0086）。イベント窓
(2020-11-16, 2022-02-14] の中の分割は 5:1 だけなので、決定 4-6 の規則 (b) を文字どおり読むと
「倍率が違う」になり、15 を足せない。

しかし VIEW が掛けるのはイベントの倍率ではなく、**行ごとの累積積 F** である。Yahoo の splits は
5:1（2021-12-29）と 3:1（2022-09-29）で、**どちらも F が変わる 2018〜2020 年の行より後**にあるので、
その 3 行の正しい F は 5 × 3 = 15 と一致する。翌年の株数比は、2 期に分かれた分割を 1 つの比に
畳んでいただけだった。

そこで規則 (b) の判定単位を「足した前後で F が変わる行ごとに、その行より後の分割の積と一致するか」
へ改める。イベント窓の中の比と一致するかは、行の F が正しいかを確かめる手段の 1 つであって、
目的そのものではない。

### 4-8. 公式に分割が無いと社単位の取得記録で確かめられた第1経路のイベントは採らない（#668）

決定 4-4 の後に残った第1経路の偽陽性（増資を分割と見間違えたもの）を、公式 `AdjFactor` の**不在**で
外した。形（比の値）でも純資産比でも本物と分けられない社（E01121 は純資産 ×1.3027 で、落とせる許容では
本物の E36173 も落ちる）に、独立した書き手の信号を足す。

#### 「行が無い」ではなく「受け取ったバーの区間の中にイベントが無い」で判定する

決定 4-5 のとおり、`jquants_adj_factor_events` に行が無いことは「分割は無かった」と読めない。そこで
**取り込み CLI（`scripts/backfill_adj_factor_events.py`）が社単位で公式の日次バーを受け取った区間**を
新しい表 `jquants_adj_factor_coverage` に残し、次の 3 つがそろったときだけ第1経路のイベントを採らない
（`detect_events(official_coverage=...)`）。

1. bps の交差検証と純資産比チェックを通っている（採る直前に判定する）
2. その社の区間（重なりを併合したもの）のどれか 1 本が、イベント窓（前期末−45日, 当期末+45日]を
   完全に覆う（`window_confirmed`・包含規則は `in_coverage(mode="full")` と同じ）
3. 窓の中に公式イベントが無い（`official_ratio_in_window` が None）

区間の無い社・窓がはみ出す社・窓の中に公式イベントがある社は、今日までどおり採る。

**区間は要求した期間ではなく、返ってきたバーの最初と最後の日付で持つ。** 調査で、#657 の全数突合が
偽陽性に数えた E03474 に対して J-Quants は契約窓で **0 本**を返していたと分かった
（2026-09-14 実測・契約窓 2024-06-22〜2026-06-22）。J-Quants は扱わない社にもエラーを返さず、
`_jquants_fetch_code` は 429 が 2 回続いても `[]` を返す。どちらも「イベントが無い」と同じ形なので、
要求した期間で記録すると「確かめた」に化ける。受け取ったバーは 10 日（`MAX_BAR_GAP_DAYS`）を超える
空白で区間を切る（東証の休場は暦日 6〜7 日まで。取得漏れや売買停止の中で起きたイベントを見落としうる）。

**区間は上書きせず追記し、読むときに併合する。** 1 社 1 行へ上書きすると、契約窓が進んだあとに取り込みを
回し直したとき古い期間の「確かめた」が消え、外した補正が黙って戻る（係数表が行ったり来たりする）。
イベントと区間は 1 社ずつ同じ commit で書く——区間だけ残ってイベントが欠けると、本物の分割を外す。
夜間 catchup は区間を書かない（1 晩に 11 日ぶんしか見ず、止まっていた晩を検出できない）。

#### 決定 4 の取引と矛盾しない理由

決定 4 は「未補正の歪みは系統誤差、誤補正はランダム誤差に近い」として偽陽性を残す側を採った。これは
**偽陽性を本物から分けられなかったから**である。今回外すのは、公式の日次バーをイベント窓の全期間ぶん
受け取り、その中に企業イベントが 1 件も無いと確かめた社だけで、分割が起きていれば `AdjFactor` に
現れる（第1経路は期末の発行済株式数が動いた社なので、効力日は窓の内側にある）。系統誤差を増やさずに
ランダム誤差だけを減らす変更で、取引の前提を変えていない。

**公式にある側の誤りは、補正を残す向きにしか効かない。** #652（E34165）のように新株予約権無償割当でも
`AdjFactor` が付くことがあるが、この規則が使うのは「公式に無いこと」だけなので、公式に分割以外の事象が
あっても今日までどおり採る。

**第2経路には掛けない。** 第2経路は、期末後・提出前の分割を 1 株指標だけが先取りする社を拾う経路で、
効力日がイベント窓の外に出うる。同じ窓の中の不在は「分割が無い」の証拠にならない。第1経路が不在で
落としたペアを第2経路が独立に拾うことは、決定 4-4 と同じく妨げない。

**測定器の CLI（`detect` / `verify-sample`）には記録を渡さない。** 渡すと偽陽性が突合から消え、
偽陽性率が測れなくなる（決定 4-5 と同じ理由）。代わりに `verify-sample` は、公式のバーがイベント窓を
覆っていない社を `no_official_bars` として一致率の分母から外す（`match_event(official_spans=...)`・
partial 窓ではバーが 0 本のときだけ）。E03474 のような判定不能を偽陽性に数えないためである。

### 5. 係数の洗い替えは収集パイプラインの内側（Phase 4 の直後）に置く

`_pipeline_incremental.py` の `update_market_data_from_history(db4)` の直後、および
`_pipeline_gh.py` の `point_in_time=True` 版の直後。**入力の近さで決めた**——係数は
`issued_shares` と `bs_bps` から復元するので、直前の工程がそれを更新した直後が唯一ずれない
位置である。独立ステップへ切り出すと「収集は成功したが係数だけ古い」状態が作れてしまう。
入口を 2 本とも揃えるのは、手動の全件実行のあとだけ係数が古くなるのを防ぐため。

**例外は握らない**（直前の株価反映と同じ扱い）。この工程の自己検証だけが係数表の固着を
検知する仕組みなので、黙って続けると #504 と同型の穴になる。検出 0 件のときは
**既存の表に触らずに失敗する**——全置換の順序で「消してから失敗」にすると、補正が静かに
全部外れた VIEW が残り、しかもどの値も妥当な株価指標なのでエラーとしては現れない。

`batch_freshness.PRODUCERS` へは登録しない。あの表のエントリはすべて月次バッチの producer で、
`PRODUCER_COVERAGE` は heavy プラグイン名をキーに持つ dict のため、この工程は対象外である。
`sector_ols` / `macro_enet` が `nightly_scores.VerificationError` で「execute は成功したが
永続化を確認できなかった」をその場で失敗にしているのと同じ考え方を採る。

### 6. `plugins/utils.py::PREPROCESS_VERSION` は上げない

ADR-0039 が守るのは `recommend_factor_premia` の `mean_b` の単位だが、その推定に使う
`build_period_panel` のパネルは z_* 7 列だけで per / pbr / div_yield / market_cap / nc_ratio を
含まない（上の Context）。**永続化済みの重みの意味は変わらない。**
この判断を明記しておくのは、上げ忘れと区別がつかないため。

永続化された μ̂ の陳腐化も実害にならない。既定の μ 出所である M-6 `macro_enet` は
`nightly_scores.HEAVY_AUTOMATION` で毎晩の `run_nightly.py` に登録されており、
翌晩には補正後のデータで学習し直した μ̂ に入れ替わる。

### 7. rank-IC の変化は採否の条件にしない（リーク量の測定として読む）

**この歪みは単なるノイズではなく、未来情報のリーク（先読み）である可能性が高い。**
2019 年断面のある行の PER が小さいのは「2019 年時点で割安だった」からではなく
「2019 年より後に分割が起きた」からで、分割を行うのは株価が上がって単位金額が大きく
なりすぎた会社である。つまり歪んだ PER は「この先この会社の株価は上がる」という未来の
事実を過去の断面へ持ち込んでいる。併合は逆向きに同じことをする。

この読みが正しければ、**補正すると rank-IC は下がり、下がるのが正しい**。
ADR-0028 の昇格ゲート（成績が上がったものを採用する）をそのまま当てると、
リークを残す判断になる。

名乗るだけでは証拠にならないので、直接証拠を 1 つ取る——補正量 F とラベル（52 週先
リターン）の関係を、**分割が起きるまでの年数で層別**して並べる。リークなら「直近の分割ほど
強く、遠い分割ほど弱い」という単調な形が出るはずで、出なければこの読み自体を捨てる。
測定は `python -m scripts.model_comparison_run --models macro_gbdt,macro_enet`
（`oof_backtest` は再学習も追加の株価取得もしない純後処理でコストはほぼゼロ・重いのは
上流の walk-forward 学習）。M-1 は strict（`macro_nan_ok=False`）でパネルを M-2 / M-6 と
共有できず同一共通域の比較が成立しないため（ADR-0045 / ADR-0050 と同じ制約）参考値として別に測る。

## Consequences

- 過去断面の per / pbr / div_yield / market_cap / nc_ratio / z_nc_ratio が基準の揃った値に
  なる。恩恵を受けるのは M-1 / M-2 / M-6 の学習パネル、年度指定のスクリーニングと CSV、
  M-8、`/api/backtest`、`min_market_cap` フィルタ。
- **`scripts/measure_split_valuation_bias detect` は回帰テストにならない。** 測定器は
  `financial_records` の生値を読むので、VIEW 補正後も同じ行数を報告し続ける。
  #655 本文の「測定器がそのまま回帰テストになる」は実列書き換え方式を前提にした記述で、
  この方式には当たらない。代わりに `financial_metrics.per = ROUND(financial_records.per ×
  split_factor, 2)` の突合（2026-09-12 実測で per / pbr / market_cap / div_yield とも
  **不一致 0 行**）と、**E01777 ソニーG の 2024 年 per 3.29 → 16.45**（F=5.0・#653 の
  「実際は 17〜20 倍台」と整合し、翌期の 20.30 と連続する）で受け入れ判定する。
  **突合の join は `fm.id = fr.id` で取る**——`(edinet_code, year)` で結ぶと、同じ year に
  annual 行が 2 本ある社（会計期間変更・実測 58 組）で別の行と比べてしまい、F=1.0 の行が
  「不一致」として 56 件出る。
- **書いた行数は 1,947（451 社）で、#655 本文の 1,948 と 1 行ずれる。** 同じ year に annual 行が
  2 本ある社でペアの向きが入力順に依存するためで、こちらは `ORDER BY edinet_code, year,
  period_end` まで指定して**再現性を取る側**を選んだ（測定器の `_SQL_ANNUAL` は
  `edinet_code, year` まで）。
- 補正された行では `per <> stock_price / pl_eps` になる（決定 2 の意図した非対称）。
- **H1（半期）行は範囲外。** `financial_metrics_interim` VIEW は「H1 行は市場データが未収集の
  ため nc_ratio 等の市場依存派生は NULL になる（想定内）」であり、値が入っていないものは
  歪みようがない。ただし `point_in_time=True` を回すと H1 行にも株価が焼かれて歪む
  （GOTCHAS へ記載）。
- 新テーブルと VIEW の変更はどちらも ADR-0048 の指紋へ効くので、`init_db()` が自動で移行する。
  手書きの移行 SQL は持たない。
- 偽陽性がおよそ数十行の誤補正として残る。`kinds` と `split_factor` が残るので、
  独立した第 2 の信号（純資産総額の前年比）で分離する改良は後から差分で入れられる。
- **検出器は `issued_shares` が分割に追随しない社を取りこぼす（2026-09-12 に実測で判明・
  #655 の作業中に発見）。** 候補ゲートが `issued_shares` の年次比なので、`bs_bps` と `pl_eps` は
  分割を反映しているのに株数が据え置きの社では**候補にすら上がらない**。
  **#653 の看板例だった E03137 しまむらがこれ**——`shares ×1.0000` のまま
  `bps ×1.8670 / eps ×1.8971`（→1:2）と `bps ×2.8965 / eps ×2.8159`（→1:3・#653 が記録した
  2026-02 の分割）で、2 件とも F=1.0 のまま残る。規模は **161 行 / 156 社**（検出できているのは
  451 社）。必要条件「`bs_bps` が 1.4 倍以上下がったのに株数が動かない」だけなら
  1,117 行 / 826 社だが、減損・大幅赤字・タグ基準の変更が混ざる（実測 E39487 は bps ×129.75）。
  上の数字は `pl_eps` が同じ倍率で動いたこと（許容 15%）と定番比へ寄ることを交差させて絞った値で、
  推定比の分布（×2.0 が 56・×2.5 が 29・×1.5 が 24・×3.0 が 23・×4.0 が 16・×5.0 が 11）は
  検出済みイベントの分布と同じ形をしている。**`per` の比は第 3 の検証に使えない**
  （株価の値動きが混ざる。実測 E00313 は snap ×3.0 に対し per ×8.05）。
  **#656 で第2経路を実装し、公式 `AdjFactor` と突合した上で既定 OFF で入れた**（決定 4-2）。
  存在の検出は優秀（抽出 30 社中 27 社に公式イベント・陰性対照の見逃し 0 社）だが、
  **倍率の一致率が 0.367** しか出なかった（`bs_bps` が内部留保でも増えるため、
  観測比が真の分割比より系統的に小さく出る）。倍率を独立な第 3 の信号から取る改良が
  済むまで、この 161〜257 イベントは補正されないまま残る。
  → **#659（決定 4-3）で倍率を翌年の `issued_shares` 比から取るようにして一致率が 0.962 になり、
  既定を ON へ倒した。** 翌年の決算がまだ無い最新年（`no_lagged_row`）は決定 4-3 でも採らず、
  #661（決定 4-5）が `jquants_adj_factor_events` に残した公式 `AdjFactor` で埋める。
- `sector_ols` は per-share 財務金額を説明変数・調整済み株価を目的変数にしており**同型の
  歪みを持つ**が、現在は `latest_year_subq` で最新年度だけを回すため `gap_ratio` へ届いて
  いない。#626 が過去年度への遡及計算を予定しており、そのとき同じ問題が出る。

## Considered Options

### 案A: valuation 用に未調整株価を別に持つ

**既存行に対して原理的に実行できない。** 2018 年まで遡った未調整株価の入手手段が無い——
J-Quants の未調整終値 `C` は契約窓 2 年ぶんのみ（実測 2024-06-20〜2026-06-20）、
Yahoo は調整済み系列しか配信せず、`stock_price_daily` / `stock_price_weekly` は
ADR-0053 の決定により調整済み単一スケールのみを保持する。

効くのは今後焼く行だけだが、毎晩焼かれるのは `point_in_time=False` 経路の最新 annual 行
のみで、そこは元々基準が揃っていて歪まない。**列を増やす費用を払って効果がゼロ。**

### 案B': `financial_records` の実列を一括 UPDATE する

画面も学習も一度に直り、読み出し時の計算コストも無い。だが決定 1 のとおり F が陳腐化する
ので修復を回し続ける運用が要り、回し忘れは失敗として現れない。加えて偽陽性が生値を
上書きしてしまう（取り消せない）。

### 案B'': 1 株指標（`pl_eps` / `bs_bps`）の側を遡及調整する

#653 が案B として挙げた形だが、`pl_eps` / `bs_bps` は `sector_ols` の説明変数・`z_eps` /
`eps_growth` の元であり、XBRL の提出値そのものである。書き換えると影響範囲が
バリュエーション列の外へ広がる。歪んでいるのは比であって提出値ではない。

### 案C: 学習パネル構築側（`macro_snapshots.load_data`）だけで補正する

変更範囲は最小だが、年度指定のスクリーニング・M-8・`/api/backtest` は歪んだまま残り、
同じ銘柄・同じ年度について画面と学習で違う PER が出る二重帳簿になる。

### 案D: 現状維持（#653 の案C）

F の中央値がちょうど 2.00 で、断面順位が 25pt 超動く行が per だけで 940 ある。
#466 の「説明できない乖離は直さない」とは違い、**原因は説明でき、公式値との突合で
一致率 0.967 まで裏が取れている**。採る根拠が無い。
