# 1つの価格列には1つのスケールしか書かない（食い違う公式値は採らない）

## Status

accepted（2026-09-08）。Issue [#620](https://github.com/kome-kome/financial_app/issues/620)、
実害の観測は [#568](https://github.com/kome-kome/financial_app/issues/568)、
前提の現象は [#466](https://github.com/kome-kome/financial_app/issues/466)。
[Issue #314](https://github.com/kome-kome/financial_app/issues/314) の決定
（J-Quants からは調整後 `AdjC` を保存する）を**採否の条件付きで狭める**。

## Context

`stock_price_daily.close` には毎晩2人が書いていた。

| 書き手 | 窓 | 中身 |
|---|---|---|
| Yahoo gap-fill（`_pipeline_incremental.py` Phase 4） | 直近セッション | Yahoo の調整済み終値 |
| J-Quants catchup（同 Phase 4） | `today-90 〜 today-80` | JPX 公式の `AdjC` |

どちらも「調整済み」だが、**調整に含まれるイベントが違う**。Yahoo は 1:1.2 のような無償割当を
splits として持たない（#466 で確定）ため、その社では2つのスケールが恒常的にずれる。この状態で
片方が 11営業日ぶんだけ上書きすると、**その帯の両端に企業イベントではない段差**ができる。
11営業日で元へ戻る企業イベントは存在しない——分割でも併合でも無償割当でもない。

実測（2026-09-07・E32779 3482 ロードスターキャピタル）:

| trade_date | db | C（未調整） | AdjC（公式調整後） | db が一致するのは |
|---|---|---|---|---|
| 2026-05-29 | 2861.0 | **2861.0** | 2384.2 | C（Yahoo） |
| 2026-06-01 | 2306.7 | 2768.0 | **2306.7** | AdjC |
| 2026-06-15 | 2587.5 | 3105.0 | **2587.5** | AdjC |
| 2026-06-16 | 2938.0 | （契約窓外） | （契約窓外） | Yahoo へ戻る |

**この壊れ方はエラーを出さない。** どちらの値も妥当な株価で、`ON CONFLICT DO UPDATE` は成功し、
行数も鮮度も正常に見える。現れるのは週次リターンを入力に持つ M-1 / M-2 / M-6 の中だけで、
しかも該当社の該当期間だけである。`stock_price_daily` に書き手を示す列は無いので、
**どの行がどちらのスケールかは事後に判別できない**。

混在の**構造は全社にある**。段差として現れるのは Yahoo と JPX の調整が食い違う社だけで、
2026-09-07 時点ではそれが2社（E32779・E05716）だった。今2社なのは偶然の少なさである。

既存ツールで直らないのは、`scripts/repair_splits_from_jquants.py` の `validate()` が
この帯で2条件とも狂うため。「最新の測定比が 1.0」を**帯のおかげで**通し（DB が正しいからではない）、
「全段差が公式イベント日で説明できる」を**帯の左端で**落とす。しかも公式値を取れる窓は契約窓
（無料プランは直近12週エンバーゴ）で終わるので、**帯の右端は原理的に観測できない**。片側の段差
しか見えないため「エンバーゴ内の分割」と読むしかなく、#568 は2度にわたって群分けを外した。

## Decision

**1つの価格列には1つのスケールしか書かない。** J-Quants catchup は、返ってきた行の未調整値 `C` と
調整後値 `AdjC` を突き合わせ、**食い違う行を書かない**（`collector_prices._jquants_batch_gen`）。

- 判定は**返ってきた行の中だけで完結させる**。DB の既存値は前夜までの上書きで既に汚れている
  可能性があり、基準にすると自己参照になる
- 丸め差で公式値を捨てないよう、許容は `collector_utils.rounding_tolerance` を使う。**収集側と
  `repair_splits_from_jquants` が同じ関数を共有する**（別々に持つと、片方が「同じ」と見た行を
  もう片方が「段差」と読む）
- `C` が無い行は「食い違い」とは**別に数える**（`scale_unknown`）。同じ箱に入れると、API が
  `C` を返さなくなった日に「調整差のある社が全社へ広がった」と読めて打ち手を取り違える
- 弾いた行数と社数は毎晩ログへ出す。弾いた社は「公式値による是正の機会を失う」側に倒れるので、
  黙って捨てると「なぜこの社だけ古い誤りが残るのか」を後から追えない

これは #314 の決定（`AdjC` を保存する）を**捨てるものではない**。列マッピングは `AdjC` のままで、
採用された行では `AdjC == C` が成り立つ。#314 が避けたかった「分割日で系列が段差になる」は、
Yahoo が自分のスケールで一貫して書くことで避けられる。Yahoo が調整を落とす社の段差は
#466（`repair_splits_from_jquants`）の担当で、この決定はその境界を動かさない。

### 採らなかった案

- **案A: 系列全体を JPX 公式スケールへ寄せる。** 公式が正であり `AdjFactor` という監査可能な根拠を
  持つ。だが Yahoo は「今日」を書く唯一の担い手（J-Quants 無料は12週エンバーゴ）なので、
  **直近12週は必ず Yahoo スケールで入る**＝境界は消えず場所が移るだけ。恒久化するには銘柄ごとの
  補正係数を永続化し、Yahoo が毎晩書く値にも掛け、係数の再測定と分割検知の運用を新設する必要がある
- **案C: catchup を該当社だけスキップする。** 本決定と似るが、対象を「今わかっている2社」という
  名簿で持つことになる。名簿は将来 Yahoo が別の社の調整を落とした瞬間に古くなり、**古くなったことが
  失敗として現れない**。本決定は毎晩レスポンスから判定するので名簿を持たない

## Consequences

- 調整差のある社では、公式値による是正が効かなくなる。もともとその社では公式値を書くと壊れていた
  ので実害は増えないが、**その社の古い調整もれは #466 の経路でしか直らない**
- 既に入ってしまった帯は仕組みの修正では消えない。`scripts/repair_scale_mixture.py` が
  該当社の直近 `DAILY_WINDOW_DAYS` を Yahoo で取り直す。**順序を逆にしない**——先にデータだけ直すと
  次の晩の catchup が書き戻す
- 再発検知は「往復段差（飛んで数日で戻る帯）」を毎晩見る。ただし**形だけでは本物を選べない**:
  全社走査では候補が 234社出て、そのうち本物は2社だった（2026-09-08 実測）。帯の長さでも、帯の
  内側が一定比かでも分離できない（E32779 は帯の中で株価が 13% 動いている）。したがって毎晩の判定は
  **その晩 `AdjC != C` を報告した社との交差**で行う。調整差の無い社は誰が書いても同じ値になる＝
  混ざりようがないので、この交差が過不足のない網になる
- 確定は公式値との突合で行う（`AdjC != C` かつ **帯の日の DB 値が `AdjC` と一致する**）。突合は
  1社20秒（`JQUANTS_RATE_SLEEP`）なので、CLI は候補が `--max-verify` を超えたら突合せずに止まる
- 2026-09-08 に E32779・E05716 を修復した。修復後、両社の 2026-06-01〜06-15 は `AdjC` と一致
  しなくなり（E32779 の 6/1 は 2306.7 → 2768.0＝未調整 C と同値）、週次の段差も消えた
