# 不実行の検知はローカル watchdog が足跡の鮮度で行い、閾値は cadence＋窓から導出する

## Status

accepted（2026-08-26）。Issue [#515](https://github.com/kome-kome/financial_app/issues/515) 手順3。
[ADR-0038](0038-local-postgres-is-the-primary.md)（正本のローカル化）が生んだローカル駆動バッチの
運用面の追補で、[ADR-0040](0040-batch-window-is-split-into-step-budgets.md) が Consequences に
残した穴を塞ぐ。[ADR-0031](0031-heavy-plugins-require-registered-automation.md) 系列の
「登録 ≠ 実行」と同じ系譜——**無音・無実行を検知可能にする**ための決定。

## Context

2026-08-21 17:20:03、タスクスケジューラ起動の夜間バッチが `0xC000013A`
（STATUS_CONTROL_C_EXIT）で即死した。残ったものは何も無い。

| 確認したこと | 結果 |
|---|---|
| タスクの `LastTaskResult` | `0xC000013A` |
| `.logs/nightly_20260821.log` | **存在しない**（1行も書かれていない） |
| `app_settings.nightly_last_run` | 前日のまま＝**今日の足跡なし** |

足跡（`app_settings` の `*_last_run` / `*_last_success`）は「走っていない」ことを**正しく
示していた**。問題は読む側が存在しなかったことで、別件の調査でたまたま気づくまで丸1日
誰も知らなかった。

**バッチが起動前に死ぬと failure が出ない。** `batch_common.notify` の起票経路は
`run_batch` が最後まで到達して初めて動くので、その手前で死んだ回は通知の対象にすらならない。
ADR-0040 が同じ構造を別の場所で言い当てている——窓の終わりの打ち切りも
`record_footprint` に到達しないので「失敗としては現れない」。`docs/DEPLOYMENT.md` には
自分たちで「検知できるのは `monthly_last_success` が進まないことだけ」と書いてあったが、
**書いただけで見る主体が無かった。**

損害は当日の鮮度で終わらない。1日飛ぶと翌日の Yahoo gap-fill の対象が 4,051社まで膨らみ
（#475）、翌晩の所要が 2時間超へ伸びる。

正本はローカル PostgreSQL（ADR-0038）なので、**GitHub Actions からこの DB は見えない**。
`check_egress_health.py` が使っている「非ゼロ終了 → `notify-failure.yml` が起票」の経路は
原理的に使えない。

## Decision

**ローカルのタスクスケジューラで毎日走る watchdog（`scripts/check_batch_freshness.py`）を
1本置き、足跡の鮮度を見て自分で起票する。**

### 1. 閾値は「約束」から導出する。実測からは逆算しない

各バッチは「cadence ごとに1回、窓の中のどこかで足跡を書く」と約束している。健全な世界で
経過が取りうる上限はそのまま **`cadence + 窓`** になる。両項ともリポジトリに定数として
存在するので、閾値は書き写す定数ではなく式になる。

| 監視対象 | cadence | 窓 | 閾値 |
|---|---|---|---|
| 夜間バッチ | 24h | `run_nightly.WINDOW_MIN`（6h） | **30h** |
| 月次バッチ | 31日（同一日付の最長間隔） | `run_monthly.WINDOW_MIN`（16h） | **760h** |
| watchdog 自身 | 24h | `SELF_WINDOW_MIN`（15分） | **24.25h** |

副産物が3つある。

1. **「実行中に警告を出さない」が構造的に成立する。** 閾値に含まれる窓の項が、そのまま
   「まだ走っていてよい時間」の許容そのものだからで、プロセスの生存を覗く必要がない。
2. **閾値が watchdog 自身の起動時刻に依存しない。** 20:00 を 21:00 へ動かしても壊れない。
   CI が「任意の観測時刻で健全な履歴は鳴らない」を縛れる——ここが落ちるなら
   「起動時刻に合わせて閾値を詰めた」＝逆算をやっている。
3. **窓を広げれば閾値も自動で広がる。** ADR-0040 の「窓と予算はセットでしか意味を持たない」を
   1段外へ延ばした形で、乖離が原理的に起きない。

実測もこれと整合する。2026-08 の夜間バッチは名目 17:20 に対し実起動が 17:51（+31分）〜
19:01（+1h41m）だった（`StartWhenAvailable` による追いつき実行）。**名目時刻を基準に判定すると
誤検知する**が、経過ベースなら遅延は窓の項が吸収する。正常運転の連続実行間隔の実測は
22.8h / 24.0h、1日飛んだときは 31.3h。

> **【2026-08-29 追補・#551】上記の括弧内は当初「`WakeToRun` 未設定 ＋ PC がスリープなら復帰後に
> 走る」と書いていたが、原因の説明が誤っていた。** 実測するとこの PC はデスクトップ
> （`Win32_Battery` 無し・`ChassisTypes=3`）で **AC 時のスリープは無効**（`powercfg` の
> `STANDBYIDLE` AC = `0x0`）、System ログの 6005/6006 は**毎朝 08:00 頃のシャットダウンと
> 夕方 17:40 前後の電源投入**を示していた。ずれているのは電源オン窓の外にある夜間 17:20 だけで、
> 窓の内にある watchdog 20:00 は実起動 **20:00:02** とずれていない＝**差は「その時刻に PC が
> 点いているか」だけ**である。したがって `WakeToRun` を足しても直らない（ウェイクタイマは
> ユーザーが行ったシャットダウンからは起動できない）。**この ADR の決定（閾値を `cadence + 窓`
> から導出する）は影響を受けない**——むしろ「名目時刻を基準に判定しない」という判断が、
> 想定していた理由とは別の理由で正しかったことになる。詳細は #551 と `docs/DEPLOYMENT.md`。

### 2. 見るのは `*_last_run` であって `*_last_success` ではない

`monthly_last_success` は**設計上ずっと古い**。ADR-0040 が受け入れた代償のとおり、#512 が
解けるまで `macro_beta` は毎月 `exit=124` で落ちる。成功で鳴らすと**恒久的に open な Issue**が
でき、「初日から常時 failure」で通知そのものが信用されなくなる。

加えて「走ったが失敗した」はバッチ自身の起票が既にカバーしている。それが破れる唯一の経路は
`gh` の不調だが、**その場合この watchdog も起票できない**——つまり成功側を見ても効く場面が
原理的にほぼ無い。

成功側は報告と Issue 本文には必ず載せる。読む人が「走っていない」と「走ったが通っていない」を
1秒で切り分けられることには価値がある。

### 3. 起票は同一タイトルの open へ追記する

毎日走るので、タイトルに日付・件数・経過時間を入れた瞬間に Issue が毎日積み上がる。
タイトルは**対象ごとに固定の文字列**とし、`gh issue list --state open` から**ラベルで絞らずに**
完全一致を探して、あればコメント追記・無ければ新規作成する（`.github/workflows/notify-failure.yml`
の流儀を Python へ移した。ラベルで絞ると誰かが `ops` を外した瞬間に重複起票が始まる）。
listing が失敗したら新規作成へ倒す——**重複より沈黙の方が悪い**。

検出の種類（`stale` / `missing` / `unreadable`）はタイトルに入れない。`stale` → `missing` の
遷移で2本目が開くため。連続 N 日目のカウンタも持たない——足跡の生値が動かないまま経過だけ
伸びるコメントが並ぶこと自体が経過の証拠で、状態を持つとその状態が壊れたときに嘘をつく。

### 4. 無限後退は自己監視1段で打ち切る

「見張りを見張る役」は作らない。代わりに watchdog は自分も監視対象に含め、
`watchdog_last_run` を**読んでから書く**。リアルタイムに自分の死は検知できないが、次に
走ったとき自分の沈黙期間を検出して報告する＝**事後に隠しはしない**。

これは実際に効く場面がある。PC が数日止まって復帰すると `StartWhenAvailable` で夜間バッチと
watchdog の両方が追いつくが**順序は保証されない**。夜間バッチが先に走ると `nightly_last_run` が
更新され、飛んだ日は足跡から永久に消える（**足跡は最後の1回しか持たない**）。自己足跡だけが
その期間を証言できるので、どちらが先に走っても検知が成立する。

### 5. 通知経路は健全な回にも確かめる（2026-08-26 追記）

異常を検出したときにしか `gh` を呼ばない設計だと、**「通知経路が死んでいる」ことは異常が
起きた当日に初めて分かる**——つまり一番届いてほしい回に届かない。#515 が
「登録の成功 ≠ 実行の成功」だったのと同じ形で、ここは **実行の成功 ≠ 通知が届く**。

初回の実運用投入（S4U タスクでの疎通確認）がまさにこれを踏んだ。健全だったので `notify` が
呼ばれず、**`gh` は1度も起動されないまま「疎通確認できた」と読める状態**になった。S4U は
セッション0で走るので PATH も `gh` の `hosts.yml` の解決も対話セッションと変わりうる。

そこで `check_gh()` を毎回走らせ（`shutil.which("gh")` ＋ `gh auth status`）、健全な回にも
`通知経路: gh 到達可` を報告へ出す。到達不能なら problem として扱うが、**その `gh` で起票は
試さない**（手段が死んでいると分かっているものを叩いても無駄）——痕跡はタスクの
`LastTaskResult`（exit 3）とログにだけ残る。それが「通知できないことを黙る」よりましな
唯一の形である。

## Consequences

**検知できない残余がある**: PC の恒久停止・タスクの削除・venv の消滅。これは正本をローカルへ
置いた（ADR-0038）ことの帰結で、**GHA からローカル DB が見えない以上どこにも置けない**。
最後の環は人で、それは既に `/api/morning` の as-of ブロック（#416/#417）が担っている。

**足跡は最後の1回しか持たない**ので、一度後続の実行が起きると過去の飛びは復元できない。
「あの週に何回飛んだか」は原理的に答えられない。必要になったらログ（`.logs/*.log`）か、
足跡を履歴表へ移す設計変更が要る。

**`batch_common.notify` には依然として重複防止が無い**（本 ADR の起票経路は
`check_batch_freshness.py` 側に持たせた）。月次は #512 が解けるまで毎月新しい Issue を積む。
`batch_common` 側へ共通化するかは別途。

**新しいローカル駆動バッチを足したら監視表へ1行足す必要がある。** 足し忘れは
ADR-0031 と同型で失敗として現れないので、`tests/test_check_batch_freshness.py` が
`scripts/run_*.py` の集合と監視表を照合して CI で落とす。

## Alternatives considered

- **`run_nightly` の先頭で前回の足跡を見る。** タスクを増やさずに済むが、**nightly 自身が
  起動しなかった日は見張りも動かない**——まさに検知したい事象だけが素通りする。#515 の
  8/21 はこの経路では最後まで検知できない。
- **GitHub Actions から見る。** `egress-health.yml` と同じ形にできれば「ローカルが丸ごと
  死んでも動く」見張りになるが、正本がローカルなので **GHA からこの DB へ到達できない**。
  Supabase 側の `app_settings` は 2026-08-07 の断面で止まっており、読んでも常に古い。
- **閾値を実測から置く**（正常 24.0h・欠落 31.3h の間に 26h を取る等）。当初はこの案だった。
  実測は閾値の**検算**には要るが、**根拠にすると窓を広げたときに黙って古くなる**。ADR-0040 が
  「窓と予算はセット」で解いた問題と同じ形なので、同じ解き方（導出にして CI で照合）を採る。
- **プロセスの生存を見る。** `Get-ScheduledTaskInfo` の `LastTaskResult`（`267009`＝実行中）を
  読めば「今走っている」が分かる。しかし S4U 化（#515）で watchdog は**セッション0で走る**ため
  対話セッションからは CPU 時間もコマンドラインも読めず、逆も同様。足跡は DB の1行なので
  セッション境界を越える。
- **成功（`*_last_success`）でも鳴らす。** 上記 Decision 2 のとおり、月次が恒久的に鳴り続けて
  通知が信用されなくなる。

## 2026-09-07 追記: 「走ったか」だけでは成果物の固着を拾えない（#504）

本 ADR の判定は足跡（`*_last_run`）1本で、答えられるのは**バッチが起動したか**だけだった。
2026-09-01 の月次はその意味では健全に走っている。だが `tune:macro_dlm` が予算切れ
（exit=124）、`tune:macro_gbdt` が当時の品質ゲートで persist スキップ（exit=1）となり、
**成果物は1つも前進しなかった**。失敗自体は `batch_common.notify` が #587 として起票し、
それは対処されてクローズされた。

にもかかわらず穴は残った。2026-09-07 に直接クエリして測ると `plugin_tuned_params` は
`macro_gbdt` が 50日・`macro_dlm` が 59日 古いままで、**その間ずっと誰も気づいていなかった**。
バッチ側の起票が言えるのは「その回が失敗した」ことまでで、**閉じた後も残る固着**は
どこにも現れない。ADR-0031 の「登録があること ≠ 動いていること」の1段先に
「**走ったこと ≠ 値が前進したこと**」がある。

### 決めたこと

`batch_freshness.py` へ第2の軸 `PRODUCERS` を置き、成果物の最終更新を測って watchdog が
別タイトルで起票する。

- 対象は**月次3系統**（`plugin_tuned_params` の M-1/M-2/M-3・`macro_beta_meta`・
  `recommend_factor_premia`）。日次（`sector_ols` / `macro_enet`）は
  `nightly_scores.VerificationError` が毎晩「execute は成功したが永続化を確認できなかった」を
  その場で失敗にしており、2経路で見ると同じ事実に Issue が二重に立つ。
- 閾値は本 ADR と同じ **`cadence + 窓`** の導出。実測（50日・59日）から逆算しない。
- `macro_beta` は **`status=live` の行だけ**数える。隔離（quarantined・#609）された run は
  残っていても producer が読まないので、鮮度としては固着と同じ意味になる。
- **`collect()` / `summarize()` は触らない。** producer 行を混ぜると `/api/morning` の
  レスポンス構造が変わる。固着は月単位でしか起きないので毎朝のカードには載せない。
- 「走っていない」と「走ったが値が書けていない」は原因も対処も違うので、**Issue のタイトルを
  分ける**（前者はタスク登録と実行環境を疑い、後者はログの exit と品質ゲートを見る）。

見落としの再発は `PRODUCER_COVERAGE` と `HEAVY_AUTOMATION` の照合が CI で防ぐ
（`exempt:` は理由必須・空理由は落とす）。

## 2026-09-11 追記: ok へ戻った起票は watchdog が閉じる（#635）

Decision 3 は「起票して、再検出は追記する」までで、**閉じるのは人の手**だった。起票本文が
「復旧を確認したらクローズしてください」と依頼していたが、#634（JPX 業種マスタ）は起票の
16分後に修正で解消したのに翌日まで open のまま残った。閉じ忘れた Issue へ次の欠落が追記
されると、「過去に直った話」と「今起きている話」が同じスレッドに混ざって埋もれる——
Decision 3 の「追記で積み上げない」が、そのまま「古い話に埋もれる」へ裏返る。

### 決めたこと

- **対象が `ok` の回に、同じタイトルの open な起票を、復旧の根拠（読んだ場所・値・判定時刻）を
  コメントしたうえで閉じる**（`gh issue close --comment --reason completed`）。再発すれば
  新しい Issue が立つ。
- **1回の ok で閉じる。** ok は `cadence + 窓` の約束からの導出で、stale の後に ok へ戻るのは
  「検出後にバッチが実際に走って足跡を書いた」ときだけ。連続回数は数えない——Decision 3 の
  「状態を持つとその状態が壊れたときに嘘をつく」をそのまま適用する。
- **ok を積極的に言えた対象だけを閉じる。** `problems()` の補集合にはしない。DB を読めなかった
  回は行が空なので、補集合だと全対象が「問題なし」に見えて全部閉じてしまう。
- **人の手が入った Issue は閉じない。** 起票も人（Claude 経由を含む）のコメントも同じ gh
  アカウントから出るため**投稿者では見分けられない**。watchdog が書く本文すべてに HTML コメントの
  目印（`<!-- finapp-watchdog -->`）を埋め込み、**目印の無い本文・コメント＝人の手**とみなす。
  その場合は閉じずに復旧コメントを1回だけ残し、最新コメントが既に復旧コメントなら何もしない。
  本文に目印の無い Issue（手で立てた同名 Issue・目印導入前の起票）も同じ扱い＝安全側。
- **`--now` の回は閉じない。** 過去の時刻を渡すと、いま stale の対象が ok に見えて本物の
  open Issue を閉じる。起票は安全側の方向なので `--now` でも従来どおり行う。`--dry-run` は
  gh を叩かず、閉じる候補をログへ列挙するだけにする。
- **閉じ損ねは起票の失敗と同じ exit 3。** 閉じ損ねた Issue は次の欠落を埋もれさせるので、
  健全な回でも沈黙させない。

### 採らなかった案

- **2回連続の ok を要求する。** 一時的な回復を弾く意図だが、足跡は「走った」という事実で、
  一度書かれた足跡が取り消されることはない。連続回数を Issue 上のコメントで持つ案も検討したが、
  閉じるのが1日遅れるだけで守れるものが無い。
