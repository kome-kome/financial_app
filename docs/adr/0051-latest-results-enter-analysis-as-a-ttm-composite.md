# 最新業績は TTM 合成として分析へ入れる（半期を通期の列へ混ぜない）

## Status

accepted（2026-09-18・実装済み）。2026-09-07 提案 → 09-17 に設計を詰め → 09-18 に実装
（末尾の追記2本。食い違うところは**後の追記が優先**）。昇格ゲート（子3）は未実施で、既定は通期のまま

## Context

「最新業績が分析に反映されているか」という問いに対する実態は**反映されていない**である（#424）。
`sql/financial_metrics_view.sql:58` が `WHERE fr.period_type = 'annual'` で通期に限定しており、
半期（H1）は収集済みでも `financial_metrics` VIEW に出ない。M-1〜M-6・recommend・sell_ranking の
どれからも見えない。

### 実害の大きさは季節で 30% 〜 88% と振れる

決算月の分布（最新 annual・4,423社・2026-09-07 実測）: **3月期 2,595社（59%）** /
12月期 626社（14%）/ 2月期 244 / 9月期 227 / 6月期 183 / 8月期 107。

H1 の収集が最新まで追いついている前提で、提出ラグ（通期3ヶ月・半期2ヶ月）を置き
「H1 のほうが新しい社数」を数えた:

| 基準日 | H1 が新しい社数 | 主な内訳 |
|---|---|---|
| 2026-09-07 | 1,347 / 4,423（**30%**） | 12月期626社（H1 2026-06-30 > 通期 2025-12-31）・9月期227・6月期183 |
| 2026-12-07 | 3,910 / 4,423（**88%**） | 3月期2,595社が加わる（H1 2026-09-30 > 通期 2026-03-31） |
| 2027-03-07 | 3,885 / 4,423（88%） | 同上 |
| 2027-06-07 | 3,335 / 4,423（75%） | 3月期・9月期・6月期 |

**12月〜5月はおよそ9割の銘柄で最新の実績を捨てている。** 3月期が59%を占めるため、
その H1（9月末）が入る11月以降に効き幅が跳ね上がる。

### 供給が止まっている（これは方式の選択と独立の問題）

現データでの実測は上の推定と一致しない——H1 のほうが新しい社は **275社（6%）** だけで、
平均すると H1 は annual より **349日古い**。原因は収集経路が無いことである:

| 経路 | 現状 |
|---|---|
| `collector.py --interim` | 呼び出し元は `.github/workflows/collect-interim.yml`（**手動トリガのみ**） |
| `collector_disclosures` | 同上（`collect-disclosures.yml`・手動のみ） |
| 夜間バッチ `run_nightly.py` | ステップは `pipeline` と `scores` の2本のみ |
| 月次バッチ `run_monthly.py` | `vacuum` / `price_suffix` / `factor_premia` / `tune:*` |

**#503 で GHA の cron を全停止した結果、H1 と会社予想はどこからも収集されなくなった。**
齢は `financial_records` H1 が `period_end` MAX **2025-09-30（11.2ヶ月）**、
`statement_disclosure` が `disc_date` MAX **2026-04-17（4.7ヶ月）**。

**どの方式を採っても、供給を戻さない限り鮮度は1日も改善しない。**

### 器はすでにあるが孤児になっている

`financial_metrics_interim` VIEW と読み取りモデル `FinancialMetricInterim` は #219② フェーズCで
実装済み（`sql/financial_metrics_interim_view.sql` / `database.py:1997`）。しかし grep で消費者を
洗うと、**`database.py` の定義と `tests/test_financial_metrics_interim.py` 以外どこからも読まれて
いない**。供給先だった #323（イベント駆動モデル）が wontfix になったためである。
`statement_disclosure` も同じ形で、利用は `scripts/event_study_*.py` の2本だけ。

**壊れているのは器ではなく、供給と消費の両端である。**

### 半期を通期の列へ素朴に混ぜると VIEW が壊れる

`WHERE period_type='annual'` を外すだけでは駄目で、理由は同ファイルのコメントが明記している:

- `z_*` は `PARTITION BY year`（`WINDOW yw`）→ 同一 year に annual と H1 が混在すると
  **期間の異なる値で Zスコアを取る**
- `rev_growth` / `delta_roe` は `LAG(...) OVER (PARTITION BY edinet_code ORDER BY year, period_end)`
  → **通期→半期の LAG が「成長率」として計算される**（無意味）

さらに CLAUDE.md の設計制約「**説明変数と被説明変数は同一次元**（per-share 財務金額[円/株]→
株価[円/株]の Ohlson 型）」がここで効く。H1 の PL は半期ぶんなので、通期と同じ列へ混ぜると
**フローの期間が銘柄ごとにばらばらな説明変数**になる。ストック（BS）は期末値なので混ぜても
次元は壊れないが、フロー（PL・CF）は壊れる。

## Decision

**H1 は TTM（直近12ヶ月）合成として通期の列へ入れる。半期の行をそのまま露出しない。**

1. **合成式**: フロー（PL・CF）は `annual(FY-1) − H1(FY-1) + H1(FY)`、ストック（BS）は
   **最新 H1 の期末値**をそのまま使う。年度粒度が保たれるので `PARTITION BY year` の Zスコアも
   `LAG(... ORDER BY year, period_end)` の成長率も**現在の定義のまま壊れない**。
2. **次元整合が保たれる**ことが案Bに対する決定的な利点である。TTM は常に12ヶ月ぶんのフローなので、
   per-share 財務金額 → 株価の Ohlson 型がそのまま成立する。モデル側の学習を組み直さなくてよい。
3. **合成したことを行に残す**。`period_type` は `'annual'` のままにせず、合成の別を持つ列
   （例 `basis` = `annual` | `ttm`）と、合成に使った H1 の `period_end` を持たせる。
   **どの行が合成かを消費側が知らないまま使えてしまう状態を作らない。**
4. **合成できない社は合成しない**（通期のまま残す）。無理に埋めると欠測が「古い実績」ではなく
   「間違った実績」に化ける。
5. **供給の回復は方式の選択と独立に先行する**（→ 実際には月次ではなく日中枠の暦で定常化した・#681・ADR-0056）。`collector.py --interim` と会社予想収集を
   月次バッチ（`scripts/run_monthly.py`）のステップとして入れる。**ステップを足したら
   `BUDGET_MIN` へ予算を書き、Σ + マージン ≤ 窓を保つ**（#530・ADR-0040。付け忘れは
   `window_problem` が CI で落とす）。

### 適用範囲を 2022年度以降に限る

TTM に必要な3点（`annual(FY-1)` / `H1(FY-1)` / `H1(FY)`）が揃う割合の実測:

| year | H1 件数 | 前年H1あり | 3点そろい（revenue） |
|---|---|---|---|
| 2026 | 298 | 290 | 284（**95%**） |
| 2025 | 3,829 | 3,741 | 3,677（**96%**） |
| 2024 | 3,839 | 3,722 | 3,655（95%） |
| 2023 | 3,798 | 3,670 | 3,607（95%） |
| 2022 | 3,740 | 3,597 | 3,534（94%） |
| 2021 | 3,692 | 1,017 | 1,003（**27%**） |
| 2020 | 1,045 | 0 | 0（**0%**） |

2021年度以前が低いのは H1 の収集履歴が浅いためで、**TTM を使えるパネルは実質4年強**。
それより前は通期のまま残す（`basis='annual'`）。

H1 側の列充足率（2025年度・3,824件）は高く、合成の材料としては十分:
`pl_net_income` 100% / `bs_total_assets` 100% / `cf_operating_cf` 100% / `pl_eps` 100% /
`pl_operating_profit` 99% / `pl_revenue` 98%。

### 合成が壊れる条件を検知して落とす

TTM の敵は会計基準変更・決算期変更・連結範囲変更である。**どれも「例外が出ないまま数値だけ
おかしくなる」形で入る**ので、合成時に構造的な条件で弾く:

- `accounting_standard` が `annual(FY-1)` と `H1(FY)` で違う → 合成しない
- 決算期変更（`period_end` の月が前年と違う）→ 合成しない
- 合成結果の符号・桁が前年通期から極端に外れる → 合成しない（閾値は実測してから決める）

**弾いた件数を必ず数えて出す**。ゼロ件が続くなら検知が働いていない可能性を疑う
（#605 の「価格が無い」と「価格が止まった」を混ぜない、と同じ形）。

## Consequences

- **鮮度**: 12月〜5月はおよそ9割の銘柄で、最大6ヶ月ぶん新しい実績が分析へ入る。
- **既存モデルは無改造**。VIEW の窓関数もモデルの次元整合もそのまま。これが案Bに対する主な利得。
- **`financial_metrics_interim` の位置づけが決まる**。TTM は通期側の VIEW が持つので、
  interim VIEW は「半期の生値を見る窓」として残る（消費者は引き続きゼロ）。
  **退役させるかは別途判断**（ADR-0044 の「退役は削除ではない」に従う）。
- **バックテストの point-in-time 性**: TTM 行の as-of は H1 の**提出日**であって期末日ではない。
  `filing_date` を持たない行を as-of として使うと先読みになる。`FinancialMetricInterim` が
  `filing_date` を持っているのはこのためで、合成側も同じ基準を引き継ぐ必要がある。
- **前処理世代**: TTM 行が断面へ入るとフローの分布が動く。`plugins/utils.py::PREPROCESS_VERSION`
  を上げるかは、**実際に断面の前処理が変わるかで判断する**（ADR-0039・#517。上げ忘れは
  CI で拾えない）。
- **昇格ゲート**: 鮮度が上がることと予測が当たることは別である。TTM を既定にする前に
  `scripts/preset_ic_gate.py` で rank-IC を測る（ADR-0041。**過去の実測と比べるときは
  `--until <ym>` で期を揃える**）。
- **月次の窓**: `--interim` のステップ追加で月次バッチの Σ予算が増える。GHA での成功実績は
  2h31m だが**ローカルの所要は未実測**で、比は律速要因をまたいで移らない（GHA 0.847 対
  ローカル 0.422 で見込みを64%外した前例がある）。**入れる前に1回手動で測る。**

## 追記（2026-09-17）: 実装前の設計の詰め（#424 子2）

供給は #647 の修正と #681 の暦で回復した（9/16 の実走で H1 の `year=2026` が 298 → 3,875 行）。
実装に入る前に、#424 の 9/11 コメントに残した 7 つの論点を決めた。**上の Decision と食い違う
ところはこの追記が優先する。**

### 決定1. TTM 行は過去の年度にも残す（Decision の「通期がまだ無い間だけ」を置き換える）

最新の断面にだけ置くと、学習パネルと OOF 評価が見る過去の断面に TTM が一度も現れない。
すると子3 の昇格ゲートで効果を測れず、「学習は通期の値・推論は TTM の値」というずれも残る。
**2022 年度以降の各年度について、H1 が出てから次の通期が出るまでを TTM 行で表す。**
学習パネルの行選び（`macro_snapshots._find_applicable_fin`＝期末＋45日で最新の行）は期末日だけで
行を選ぶので、TTM 行の期末日を H1 の期末日にすれば、過去の断面でも「その時点で最新の行」が
自然に TTM になる。

### 決定2. 合成は夜間に Python で行い、専用の表へ全置換する

分割補正係数（ADR-0055）と同じ形。弾く判定と件数の記録を Python の純関数に置いてテストで縛り、
TTM 行の F も同じ段で作る。VIEW の SQL で都度合成する案は、弾く判定を SQL で書くことになり、
VIEW を実 PostgreSQL で走らせるテストが無いので壊れても CI で気づけない。夜間が止まると TTM も
古いまま残るが、それは通期の行と同じで、watchdog が夜間の足跡で拾う。

### 決定3. 既存の `financial_metrics` は変えず、「通期＋TTM」の VIEW を別に作って選んで使う

`financial_metrics` は画面・スクリーニング・M-1〜M-6・推薦・バックテストの共通の入口で、そこへ
混ぜると測る前に全部の結果が変わる。1 つの VIEW に入れて読み手ごとに行の基準（CONTEXT.md）で絞る案は、
絞り忘れた読み手が黙って TTM を混ぜる（同じ社が同じ年度で 2 行に見える・エラーにならない）。

- 学習パネルの読み込みに切替を持たせ、**既定は通期のみ**。子3 のゲートは切替の両側を測る
- **画面・推薦・スクリーニングへ広げるかは昇格の後に別途決める**（それまで `/api/companies` 等の
  「最新行」の選び方＝論点4 は変わらない）

### 決定4. 会計基準の変更は「読める範囲」で判定し、読めない過去は桁の外れと決算期の変更で弾く

`financial_records.accounting_standard` は 2026-09-17 時点で通期 30,387 行・半期 23,932 行とも
**全行が空**で、XBRL の生データも保存していない（`xbrl_raw_documents` 0 行）。

- 2024-07 以降は会社予想の表（`statement_disclosure.doc_type`、例 `..._Consolidated_IFRS`）から
  会計基準を読み、`annual(FY-1)` と `H1(FY)` で違えば合成しない
- それより前は判定できないので、**合成値が前期の通期から桁・符号で外れる**ことと**決算期の変更**
  （期末日の月が変わった）の 2 つで弾く。桁の閾値は実装時に分布を測ってから決める
- 今後の収集で XBRL の DEI（書類の属性）から会計基準を埋める。**過去の書類は取り直さない**
  （通期・半期あわせて約 5.4 万件で、日中枠を数日ふさぐ）
- 弾いた件数は理由ごとに毎晩ログへ出す（Decision のとおり）

### 決定5. TTM 行の 1 株指標と市場データ

- **1 株指標は株数の基準を揃えてから合成する。** 前期の通期・前期の H1・今期の H1 のあいだに
  分割があると、1 株の値をそのまま足し引きすると基準が混ざる。各材料の 1 株指標を
  `issued_shares` の比で今期 H1 の株数基準へ直してから `annual − H1 + H1` を取る（株数が
  変わっていなければ素朴な式と一致する）
- **株価は通期の行と同じ規約に揃える。** 社の最新の行（それより後の通期が無い TTM 行）だけ現在株価、
  それ以外は H1 期末の株価（週次の調整済み株価）を使い、per / pbr / 配当利回り / 時価総額を
  TTM の値から計算し直す。H1 の行に入っている per（半期 EPS で割った約 2 倍の値）や中間配当だけの
  利回りは使わない
- **TTM 行の分割補正係数は「H1 期末より後のイベントの積」。** 年度ごとの F（ADR-0055）は通期の
  期末日で区切るのでそのまま使えない。日付のある公式 `AdjFactor` があればそれで前後を決め、
  無ければ H1 と通期の `issued_shares` の比で、分割が H1 期末の前か後かを決める
- **配当は TTM にしない。** 年間配当は通期の実績（`dps`）を前期の値のまま使う（中間配当と期末配当の
  配分は社ごとに違い、H1 から年間を作れない）

### 決定6. as-of と年度の付け方

- TTM 行の期末日は今期 H1 の期末日、年度（`year`）は今期 H1 の年度（DEI の当期末の年）
- 材料の年度が `annual(FY-1).year = H1(FY-1).year = TTM.year − 1` を満たさない社は合成しない
  （決算期の変更として数える。出所が書類のメタデータと DEI で違うので、変則決算で食い違いうる）
- **H1 の提出日が期末＋45日より遅い行からは TTM を作らない**（数える）。学習パネルは期末＋45日で
  行を使い始めるので、遅れて出た H1 を使うと先読みになる。落とした社は通期の行へ戻るだけで済む

### 決定7. 窓関数は行の基準ごとに分けて計算する

- `z_*` は「同じ年度・同じ基準」の行の中で標準化する（`PARTITION BY year, basis`）。TTM 行を
  同じ年度の通期の行の平均で測る案は、最新の年度に通期の行がまだ揃っていないので成り立たない
- 成長率・前年差は同じ基準の前年の行と比べる（TTM は前年の TTM と）。前年の TTM が無い最初の
  年度（主に 2022）は NULL になる

### 決定8. 既存の周辺はここでは変えない

- `sector_ols` / `regression_results` は通期のままにし、TTM 行の `gap_ratio` は NULL。過去年度への
  遡及（#626）と一緒に扱う。いま学習パネルは `gap_ratio` を使っていない
- 新しい VIEW 用の ORM・`db_egress` の列数の較正・`tests/test_financial_metrics_interim.py` の
  列固定テストは、実装のときに新しい VIEW 側へ足す（既存の `FinancialMetric` は変えない）
- `financial_metrics_interim` VIEW はそのまま残す（Consequences のとおり）

### 決定9. 昇格ゲート（子3）の形

TTM は行を新しくするだけで社を増やさないが、材料の欠けで TTM 行を作れない社がいるので、
ADR-0050 と同じく**共通 (ym, ec) 域で**切替の両側を比べる。対象は M-2 / M-6（M-1 は strict で
パネルを共有できないので別に参考値）、指標は rank-IC と `short_side_spread`、補正は ADR-0045 の
Bonferroni に揃える。**既定を切り替えるのはゲートを通ってから。**

## 追記（2026-09-18）: 実装（#424 子2・PR で入った形）

実装して初めて分かったことがあり、**決定5（1株指標を株数の比で揃える）は「揃わなければ作らない」へ
置き換えた**。ほかの決定は上のとおり。実体は `ttm_composite.py`（合成の純関数と夜間の作り直し）・
`ttm_financial_records`（表）・`sql/financial_metrics_with_ttm_view.sql`（VIEW）・
`plugins/macro_snapshots.use_fin_rows()`（切替）。

### 実装1. 分割をまたぐ社・年度は合成しない（決定5 の置き換え）

株数の比で 1 株指標を直す案は、**分割と自己株式の消却・増資を区別できない**ので採らなかった。
EPS は期中平均株数ベースなので、消却や増資では基準を直してはいけない。実測（2026-09-18・
候補 18,300 組）では株数が ±5% を超えて動く組が約 5% あり、うち半分は定番比に乗らない
（増資・消却）。生の比で揃えると、その全部に誤った倍率を掛けることになる。

代わりに、**危ない窓＝(前期 H1 の提出日, 今期 H1 の提出日]** にイベントがある社・年度を作らない。
分割は遡って修正されるので、この窓の外のイベントは 3 つの材料すべてに入っているか、どれにも
入っていないかのどちらかになる。判定は 3 つの信号のどれか 1 つでも当たれば作らない:

1. `issued_shares` の比、または「純利益 ÷ EPS」で逆算した株数の比が 1.4 倍以上（検出器の
   `DEFAULT_MIN_RATIO`）。**逆算を併せて見るのは、期末の後・提出の前の分割では EPS だけが
   遡って直り、`issued_shares` が期末の株数のまま残るため**（実測 222 件がこれだけで見つかる）
2. 係数表の検出器（`detect_events`）のイベント窓が危ない窓と重なる。第2経路の「倍率待ち」も同じ扱い
3. 公式 `AdjFactor` の日付が危ない窓の中にある

**1.4 倍未満の小さな分割（1:1.1 の無償割当など）は、公式の契約窓（2024-06 以降）の外では拾えない。**
既存の通期の補正（F）と同じ制約で、`CANONICAL_RATIOS` の小さい比へ寄せる判定は使わなかった
——検出器の丸めは残差 0.8〜1.25 を「複合」として定番比へ寄せるので、**ほぼ全件が分割扱いになる**。

作らなかった社は学習パネルで通期の行に戻るだけで、母集団は減らない。

### 実装2. H1 に無い列の扱い（決定4 の補足）

実測で H1 側が空になる列が多いことが分かった（候補 19,134 組）。空のままにすると VIEW が
`net_cash` / `de_ratio` の計算で 0 として扱い、**値が黙って偏る**。

| 列 | H1 で欠ける | うち翌年の通期にはある | 扱い |
|---|---|---|---|
| `bs_bps` | 99.0% | 91.8% | 通期の BPS × (H1 純資産 ÷ 通期純資産) で合成 |
| `pl_rd_expenses` | 43.3% | 91.0% | 前期の通期の 12 か月値で代用（`rd_intensity` が 4 割欠けるため） |
| `bs_receivables` / `bs_buildings` / `bs_machinery` / `bs_investment_securities` | 27〜34% | 89〜92% | 前期の通期から引き継ぐ |
| `bs_short_term_debt` / `bs_long_term_debt` / `bs_bonds_payable` ほか | 4〜8% | 69〜91% | 同上 |
| `pl_extraordinary_income` / `pl_extraordinary_loss` / `cf_capex` | 2〜24% | 58〜70% | 空のまま（フローは期間が混ざる） |

「表示の省略」と言える根拠は**同じ社の翌年の通期にその列がある**ことで、引き継いだ件数は列ごとに
毎晩ログへ出す。配当（`dps`）と従業員数は前期の通期の値（決定5 のとおり配当は TTM にしない）。

### 実装3. 桁の外れの閾値

TTM 売上 ÷ 前期通期の売上、今期 H1 の総資産 ÷ 前期通期の総資産が **5 倍・1/5 の外**なら作らない。
実測の分布は 売上比 p0.1%=0.438 / p50=1.029 / p99.9%=2.094（最大 8.97）、総資産比 p0.1%=0.590 /
p50=1.014 / p99.9%=2.616（最大 16.59）。**分位点で切らない**——p99.9 で切ると事業が倍増した社を
毎年一定数落とす。5 倍で外れるのは、総資産比が毎年 7〜9 倍で一定の社（E00317）のような構造的に
基準の違う行に寄る（実測 18 件 = 0.1%）。

### 実装4. 2026-09-18 時点の実測

合成 **17,250 行 / 4,026 社**（年度別 2021:872・2022:3,130・2023:3,412・2024:3,341・2025:3,260・
2026:3,181・2027:54）。作り直しの所要は **15.4 秒**（分割イベントの検出 7 秒を含む）なので、夜間の
ステップ予算（pipeline 240 分）は変えていない。

作らなかった理由: `no_prev_h1` 4,209 / `split_detected` 968 / `late_filing` 562 / `split_shares` 421 /
`split_implied_shares` 222 / `no_prev_annual` 90 / `dup_rows` 72 / `consolidation_change` 51 /
`period_shift` 31 / `split_awaiting` 12 / `magnitude_assets` 11 / `second_half_nonpositive` 9 /
`magnitude_revenue` 7 / `standard_change` 5 / `split_official` 1。

注記: 会計基準を判定できない 14,471 件（`statement_disclosure` が 2024-07 以降しか無い）・
うちエンバーゴ中 649 件・株価が当たらない 1,187 件。

**適用範囲は「材料が揃う年度すべて」**とした（Decision の「2022年度以降」を置き換える）。2021 年度は
872 行しか作れないが、2022 年度の TTM 行の成長率の比較相手になる——無いと 2022 の TTM 行は
成長率が空になり、その特徴量を選んでいる断面から**サンプルごと落ちる**。

### 実装5. 窓関数・VIEW の作り

`financial_metrics_with_ttm` は「通期の行（`financial_metrics` と同じ式・同じ値）＋ TTM 行」を
`basis` 列（`annual` / `ttm`）付きで出す。窓は `(year, basis)` / `(year, industry, basis)` /
`(edinet_code, basis ORDER BY year, period_end)`。**TTM 行の成長率・前年差は直前の行が前年度の
ときだけ出す**（作らなかった年度をまたいで「2 年前との比」を成長率にしない）。
`regression_results` は通期の行にだけ結合する（決定8）。

通期の行が `financial_metrics` と 1 行も違わないことは、実 PostgreSQL で双方向の `EXCEPT` を
取って確かめる（`tests/test_financial_metrics_with_ttm_postgres.py`・`FINAPP_TEST_PG_URL` が要る）。
CI 側は 2 つの SQL の**式そのもの**を突き合わせる（`tests/test_financial_metrics_with_ttm.py`）。

### 実装6. 切替と、本番の表を守るしくみ

`plugins/macro_snapshots.use_fin_rows("annual" | "with_ttm")`（ContextVar）。既定は `annual` で、
プラグインの param にはしない（UI に出ると昇格前の TTM が本番の実行で選べてしまう）。内側では:

- **producer スコアの永続化を止める**（`tuning_dry_run` を強制）。`recommend_factor_premia.persist` は
  `RuntimeError` で拒否する——永続化行は行の基準を持たないので、書くと本番の推薦が「TTM で推定した
  重み × 通期の断面」を読む（`PREPROCESS_VERSION` では検出できない・#509 と同型）
- **`shared_snapshot_cache()` の内側で基準を変えることを禁止する**。断面キャッシュの上限は 1、M-1 の
  CV キャッシュは `id(samples_by_ym)` をキーにしており、解放後の id 再利用で前の基準の結果が返りうる

`load_data` のキャッシュキーにも基準を含める。`PREPROCESS_VERSION` は上げない（前処理は変えていない）。

### 実装7. 表と夜間

`ttm_financial_records` は毎晩の全置換（`_pipeline_incremental.py` と `_pipeline_gh.py` の
**分割補正係数の直後**）。財務列は `FinancialRecord` の列定義から複製する（再分類項目を増やす場所を
1 箇所に保つ）。列が食い違ったら `init_db()` が VIEW ごと落として作り直す（派生データなので翌晩に戻る）。

- **入力が無い（H1 が 0 件）**: 警告して表に触らず 0 を返す
- **入力はあるのに 1 件も作れない**: 表に触らず `RuntimeError`
- 差分側だけは失敗を握って先へ進み、**最後に exit 1**（#580）。TTM は既定では誰も読まないので、
  ここで抜けると後続の株価鮮度・往復段差の検知——本番の画面が依存する側——まで止まる
- ミラーの範囲外（`MIRROR_EXCLUDED`）。派生表なので引く必要が無く、TTM を作らない側から全置換で
  引くとローカルの TTM が全消えする
- `db_egress` の較正は足さない（「測っていない数字は書かない」。未登録なら保守側の既定値になり、
  ローカルからの読み取りは Supabase の枠を使わない）

### 実装8. 残る制約

- **最新の TTM 行では、今期 H1 の提出より後に起きた分割が F に入らない**（次の通期がまだ無いので
  検出器が見つけられない）。通期の最新行と同じ制約である
- 会計基準の判定は 2024-07 以降の開示にしか効かない。それより前は桁の外れと決算期の変更だけで弾く
- 昇格ゲート（子3）は未実施。**既定は通期のままで、画面・推薦・スクリーニングへは広げていない**

## 追記（2026-09-18）: 子3 の測り方——昇格ゲートの実体

決定9 のゲートを `scripts/momentum_gate.py` の5つ目の軸 **`--fin-rows`** として足した（新しい
スクリプトは作らない・ADR-0050 決定4）。日中枠（#618）の仕事 `gate:ttm` として回す。

- **条件**: `annual`（通期のみ・本番の構成＝分母）と `with_ttm`（通期＋TTM）。条件名は
  `FIN_ROW_SOURCES` から作る。他の軸（モメンタム・マクロ・交互作用・列数）は本番構成に固定する
- **対象**: M-2 / M-6（1枚のパネルを共有）。2モデル × 2指標 = 4検定・alpha 0.0125＝ADR-0045 の
  昇格ゲートと同じ。M-1 の参考値は `--models risk_return` で別に回す（混ぜると alpha が変わる）
- **判定文は中立**（`FIN ROWS AXIS`）。既定を切り替えるかは実測を見てこの ADR に記録する

### 見つけた穴: 検証スクリプトは切替を素通りしていた

`momentum_gate` を含む検証スクリプトは、財務を `candidate_bakeoff._load_financials` で読む。これは
`FinancialMetric` を直に引き、ディスクキャッシュのキー（`bakeoff_fin_metrics_v2`）にも基準が無かった。
**`use_fin_rows("with_ttm")` で包んでも、黙って通期だけを測る**——どちらの基準でも妥当なパネルが
できるので例外は出ず、ゲートは「差なし」を返す。直し方:

- 基準 → VIEW の対応と並び（`id` まで入れて一意）を `macro_snapshots.fin_rows_model()` の1箇所へ置き、
  `load_data` と `_load_financials` が共有する（書き写さない）
- キャッシュのキーを基準ごとに分ける。通期のキーは据え置く＝既存の pickle も、これまでのゲートの
  測定条件も変わらない
- `--fin-rows` では財務を**キャッシュせずに同じ実行の中で**読む。キーは形状だけで世代を持たないので、
  片方の pickle だけが古い世代だと、差に「データの鮮度の差」が混ざる

### 黙って同じものを比べる形を2段で止める

1. **TTM 行が0件**（夜間の再構築の失敗など）: VIEW の通期側は `financial_metrics` と同じ行を返すので、
   比較は例外なく走る。`ttm_row_count`（通期＋TTM の行数 − 通期の行数）が 0 以下なら停止する
2. **TTM 行はあるのに断面へ1行も届かない**（as-of の選び方の変化など）: `count_changed_rows`（同じ
   (ym, ec) で特徴量が1つでも違う行の数・nan 同士は同じ）が 0 なら停止する

どちらも CV に入る前に止まるので、日中枠の1日を空の比較で使い切らない。

### 母集団は動く（決定9 の「社を増やさない」は、減る側で外れた）

2026-09-18 に M-2 のパネル（stride=1）を両側で組んで突き合わせた:

| | 通期のみ | 通期＋TTM |
|---|---|---|
| サンプル（ym, ec） | 95,254 | 85,533（**−10.2%**） |
| 片側にしか無い | 10,242 | 521 |
| 共通のうち特徴量が変わる行 | — | 23,410 / 85,012（27.5%） |

- 通期側の行は、2つの VIEW で**全 30,402 行が一致**した（`financial_metrics_with_ttm` の通期側は
  `financial_metrics` と同じ）。差はすべて TTM 行から来ている
- 縮む理由: TTM 行は成長率・前年差の欠けが通期より多い（`rev_growth` 27.4% 対 17.9%・`eps_growth`
  26.3% 対 14.6%。前年の TTM が無い年は作らないため）。M-2 / M-6 は財務列が1つでも欠けた行を
  **通期の行へ戻さずに行ごと落とす**（`_build_snapshots_impl`）ので、TTM 行が当たる月にその社が消える
- 共通域の判定はこの縮みの影響を受けない。ただし **raw の水準は「縮む側は有利に見える」（ADR-0045）に
  当たる**ので、with_ttm の raw が高く出ても昇格の根拠にしない
- 昇格を検討するなら、「TTM 行が欠けていれば通期の行へ戻す」選び方を別に考える余地がある（未実装・
  ゲートの結果を見てから）

`--smoke` では共通行のほぼ全件が「変わった」と出たが、これは間引きで突き合わせが壊れた結果で
（ADR-0050 決定3）、stride=1 の 27.5% が実態である。

### まだ測っていない

本測定（stride=1）は日中枠に積む。**既定は通期のままで、この追記は何も切り替えていない。**

## Considered Options

### 案B: `period_type` 別の並列 VIEW（`financial_metrics_interim`）＋モデル側で選択

器がすでにあるので実装は最小。しかし**モデルを半期ベースで学習し直す必要**があり、
「どちらを見るか」の分岐が全モデル・UI へ波及する。半期パネルは通期の半分以下の深さしか
持てず、次元整合（Ohlson 型）も per-half の意味へ読み替えが要る。**採らない。**

ただし VIEW 自体は残す（半期の生値を見る窓として。上記 Consequences）。

### 案C: H1 は「サプライズ特徴量」としてのみ使う

`statement_disclosure`（会社予想）との乖離を特徴量化する。`feature_disclosure.py` に器がある。
VIEW を触らずに済むが、**「最新業績で評価する」という当初要求を満たさない**。加えて
`statement_disclosure` 自身が 4.7ヶ月古く、供給が止まっている点は同じ。**採らない**——
ただし TTM とは排他ではないので、供給が戻った後の追加特徴量として別途検討できる。

### 案D: `WHERE period_type='annual'` を単純に外す

VIEW の窓関数が壊れる（Context 参照）。**採らない。**
