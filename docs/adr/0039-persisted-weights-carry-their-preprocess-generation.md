# 永続化した重みは、推定に使った前処理の世代を自分で持つ

## Status

accepted（2026-08-23）。Issue #517。[ADR-0008](0008-recommend-factor-premia-fama-macbeth.md)（Fama-MacBeth
プレミアムの永続化）の追補で、[#509](https://github.com/kome-kome/financial_app/issues/509)
の是正が実際に本番へ持ち込んだ不整合への回答。

## Context

#509 は消費側（`recommend.execute` / `backtest.score_record`）と推定側
（`recommend_factor_premia`）の両方に期内 winsorize→標準化を入れ、**重み 1.0 の意味を列間で
揃えた**。その結果 `mean_b` の単位が「生スケール1単位あたり」から **「1sd あたり」** へ変わった。

しかし `recommend_factor_premia` テーブルは run_id / factor / mean_b / se / t / p / n_periods
しか持たず、**推定に使った前処理の世代を持たなかった**。`get_latest_factor_premia` は最新 run_id
を無条件に返し、`get_dynamic_preset` はそれをそのまま重みとして採る。

つまり是正コミット（2026-08-21 15:21 JST）から次の月次実行までの間、「統計的最適化」を選んだ
ユーザーには

> 旧・生スケール較正の重み（`z_eps` = **−3.34**） × 新・断面標準化済みの特徴量

という、ADR-0028 の昇格ゲートが**一度も測っていない組み合わせ**が出ていた。

**この組み合わせを実測した**（61期パネル・スコア合成だけを切り替え・共通期ペアリングの定常
ブートストラップ・in-sample）:

| 状態 | 平均 rank-IC |
|---|---|
| **A. 旧単位の重み × 新単位の特徴量**（2026-08-21 15:21 〜 08-23 の本番） | **−0.0881** |
| B. 新単位の重み × 新単位の特徴量（再走後） | **+0.0959** |
| C. バランス型 × 新単位の特徴量（フォールバック先） | **+0.0211** |

- B − A: diff **+0.1840** CI[+0.1119, +0.2621] p=0.001（n=61）**有意**
- C − A: diff **+0.1092** CI[+0.0569, +0.1673] p=0.001（n=61）**有意**

A は #509 の検証時に測った是正前の値（−0.0807）とほぼ同じ水準で、**単位が食い違った重みは
「劣化」ではなく符号が負のまま**だった。

`docs/MODELS.md` 自身が「古い重みが残っている場合は静かにそれが使われる」と書いており、
**その罠を書いた本人が踏んだ**形になる。鮮度を cron（現在はローカル月次バッチ）に委ねるという
運用上の約束はあったが、**前処理を変えた側にはその約束を守らせる仕組みが無かった**。

## Decision

**`recommend_factor_premia` の各行が、推定に使った前処理の世代 `preprocess_version` を持つ。**

1. `plugins/utils.py::PREPROCESS_VERSION` を**唯一の源**とする（現在値 `"winsor_z_v1"`）。
   producer（`recommend_factor_premia.persist`）が書き、consumer
   （`recommend.get_dynamic_preset`）が照合する。
2. **世代が一致しない行は採らない**。`get_dynamic_preset` は `None` を返し、
   `resolve_weights` が既存の未算出フォールバック（バランス型）へ倒す。理由は `log.warning`。
3. **列は nullable。既存行のバックフィルはしない。** NULL がそのまま「#509 以前の生スケール」
   という正しい意味を持つ（`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` の加算的マイグレーション）。
4. **前処理を変えたら `PREPROCESS_VERSION` を上げる。** 上げた瞬間から既存の永続化行は採用対象外
   となり、`factor_premia` を回すまで「統計的最適化」はバランス型へ落ちる。

### 「古い一致ランを探す」を採らなかった理由

不一致のとき、より古い一致世代のランへ遡ることもできた。**採らない**。鮮度の落ちた重みを黙って
使うのは、この ADR が塞ごうとしている失敗そのものだからである。加えて実測が支持する——
フォールバック先のバランス型（C: +0.0211）は、壊れた状態（A: −0.0881）より**有意に良い**
（diff +0.1092・p=0.001）。「多少古くても専用の重みの方がマシ」は成り立たなかった。

## Considered Options

| 案 | 中身 | 棄却理由 |
|---|---|---|
| **A. 前処理世代の列を足す**（採用） | `preprocess_version` を持たせ、不一致なら採らない | — |
| B. run_id に世代を埋める | `run_id` の命名規約へ世代を含める。DDL 不要 | 文字列規約は破られる。検証がテスト頼みになり、規約を知らない経路が書いた行を止められない |
| C. 運用手順で担保 | 「前処理を変えたら factor_premia を必ず回す」を手順書へ | **「登録≠実行」と同型の罠**（[ADR-0031](0031-heavy-plugins-require-registered-automation.md)・#432 / #443 / #423 子5）。本プロジェクトが3回踏んだ形をもう一度採る理由がない |

## Consequences

- **静かな単位不整合が構造的に起きなくなる。** 前処理を変えると、次に `factor_premia` を回すまで
  「統計的最適化」は選べる（UI には出る）がバランス型と同じ重みになる。**選択肢が消えるのではなく
  重みが安全側へ倒れる**ので、ユーザーから見た破壊的変更にはならない。
- **世代を上げ忘れると本 ADR は無力**。`PREPROCESS_VERSION` の更新は人間の判断に残る。ここは
  「前処理の変更 → 世代を上げる」を `plugins/utils.py` のコメントで明示し、CI では縛らない
  （前処理の変更を機械的に検出する手段が無く、偽陽性で止まるコストの方が高い）。
- 同じ問題は `macro_beta_loadings` / `plugin_tuned_params` にもありうる（producer が推定した
  パラメータを consumer が読む構造）。今回は範囲を広げない。必要になった時点で本 ADR の形を写す。
- 測定は #509（ADR-0008 の追記）と同じくアドホックなスクリプトで行った。再現に必要な手続きは
  上表の注記（61期パネル・スコア合成だけ切替・共通期ペアリング・in-sample）が持つ。
