# 日中枠は窓に収まるだけキューを取り出す（1日1件をやめる）

## Status

accepted（2026-09-20）。Issue [#707](https://github.com/kome-kome/financial_app/issues/707)。
[ADR-0040](0040-batch-window-is-split-into-step-budgets.md)（窓をステップ予算へ分ける）の
予算の配り方を件数へ広げ、[ADR-0056](0056-the-daytime-queue-follows-a-calendar.md)（暦）の
「何を先頭へ積むか」とは独立に「何件取り出すか」を決める。
[ADR-0054](0054-searches-fold-before-the-budget-instead-of-losing-everything.md) の締切
（`FINAPP_STEP_DEADLINE_UTC`）はそのまま各件へ渡る。

## Context

平日日中バッチ（`scripts/run_daytime.py`・#618）はキューから **1日1件**だけ取り出す。
1日の窓は8時間（480分）で、1件に与える予算は 445分（`JOB_BUDGET_MIN = WINDOW_MIN 480 -
DEPS_SMOKE_MIN 5 - MARGIN_MIN 30`）。

2026-09-20 時点のキュー:

```
1. gate:macro       (実測   7分)  ← #615
2. gate:ttm         (実測  30分)  ← #424 子3
3. gate:demean      (実測   7分)  ← #615
4-6. bench:rhat-scale (実測 440分 × 3)  ← #664
```

**先頭3件は合計44分なのに、445分の窓を3日ぶん食い潰す。** 祝日（9/21〜23）を挟むので、
実際の消化は 9/24（木）・9/25（金）・9/28（月）の3日に散る。

これは待ち時間だけの問題ではない。open な issue 5件のうち3件（#615・#424・#664）は
「実測が出るまで判断できない」状態で、その実測をこのキューが握っている。さらに #615 と
#424 の判断は **同じデータ世代で `nomacro` / `macro` / 列数上限 / 目的変数を並べてから決める**
設計（ADR-0050 の追記・ADR-0047 の「永続化済みスコアは測ったパネルとセット」）なので、
3件がバラバラの日に出ても**揃うまで判断できない**。

### 「1日1件」が守っていたもの

`run_daytime.py` 冒頭の根拠は、2026-09-07 に `macro_beta` を手動実行したとき
**同一パネル・同一設定・同一コードで発散が 0 → 344回に増えた**実測である。差は
**その7時間の裏で重いテストを並走させたこと**だけだった。本番の推論経路にはスレッド固定が
無く、XLA が使うコア数は実行時の混み具合で決まる。コア数が変われば浮動小数の加算順序が
変わり、NUTS は初期のごく小さな差が軌道を分岐させる。

つまり守っているのは「**重い計算の裏で別の作業を並走させない**」であって、
「1日に1件しか回さない」ではない。**同じ窓の中で順番に回すことは並走ではない。**

1日1件という形は、窓（`ExecutionTimeLimit`）と予算（`budget_min`）の対応を単純にするための
実装上の選択だった。ADR-0040 が予算を導入したとき、日中枠にはまだ1件しか概念が無かった。

## Decision

### 1. キューの先頭から、窓に収まるだけまとめて取り出して順に回す

```
share(N) = JOB_BUDGET_MIN / N

selected = [先頭の1件]                    # 無条件
for key in queue[1:]:
    trial = selected + [key]
    if すべての j in trial について  measured_min(j) * JOB_HEADROOM <= share(len(trial)):
        selected = trial
    else:
        break
```

実装は `run_daytime.select_jobs()`。`select_job()` はその先頭を返す薄い包みとして残す
（`--peek` の `key` フィールドなど、既存の読み手を壊さない）。

**先頭の1件は無条件**に選ぶ。余裕の規則を当てると `bench:rhat-scale`（実測440分・
`440 × 2 = 880 > 445`）が自分で自分を弾く。先頭が窓に入ることは `enqueue` 時の検査
（`measured_min <= JOB_BUDGET_MIN`）が既に保証している。

現キューへの適用:

| 試行 | share | 必要（measured × 2） | 判定 |
|---|---|---|---|
| +gate:ttm → N=2 | 222.5 | 14 / 60 | 採用 |
| +gate:demean → N=3 | 148.3 | 14 / 60 / 14 | 採用 |
| +bench:rhat-scale → N=4 | 111.3 | 14 / 60 / 14 / **880** | 打ち切り |

→ **3件**。先頭が `bench:rhat-scale` なら N=2 の時点で `880 > 222.5` なので **1件**＝
現行と同一で、退行しない。

### 2. 予算は窓の等分であって所要の按分ではない

- N=1: その1件が `JOB_BUDGET_MIN`（445分）＝**現行と完全に同じ**
- N>1: 各件が `JOB_BUDGET_MIN / N`

どちらでも `Σ 予算 = 445`、`deps_smoke` 5 を足して 450、マージン 30 で 480 = 窓ちょうど。
`batch_common.window_problem` の検査は件数によらず通る。

**所要比で按分しない。** 按分すると「伸びた仕事ほど予算も勝手に増える」形になり、
ADR-0040 の「予算は実測から逆算した値ではない——パネルは毎晩伸びるので所要は据え置かず
伸びる」が崩れる。`measured_min` を読むのは**何件取り出すかの計画**のときだけで、
打ち切りの閾値は常に窓から導く。

予算は割り当てではなく**打ち切りの閾値**なので、7分で終わる仕事に 148分 を渡しても
残りが無駄になるわけではない（次の仕事がすぐ始まる）。

### 3. 余裕（`JOB_HEADROOM = 2.0`）は約束であって実測の逆算ではない

意味は「**所要が倍に伸びても打ち切られない**」。この値だけが `measured_min` を読む場所で、
読む目的は件数の計画に限られる（決定2）。

実測との関係: `interim` は 62.0 → 64.6分（+4%）、`gate:max-features` は見積り30分に対し
実測 20.1分。伸びは緩やかなので倍は十分に広い。狭すぎれば「窓が余っているのに1件しか
取らない」だけで済み、**広すぎたときだけ**打ち切りが起きる——だから広い側へ倒す。

### 4. 件数の上限定数は置かない

「最大3件まで」のような数は窓からも約束からも導けない恣意的な定数になる。上限の役は
`JOB_HEADROOM` と `share(N)` が果たす——短い仕事が並べば件数は伸びるが、それは窓が
許しているということであって、抑える理由が無い。

### 5. 同じ名前は1日に2回取らない

ステップ名は `run_batch` の `results` 辞書のキーなので、同じ名前を2つ選ぶと結果が片方に
潰れる。`bench:rhat-scale` のように**わざと複数積む**運用があるため、重複に出会ったら
そこで打ち切る。

### 6. in-flight マーカーは未完了の仕事を全部持ち、1件終わるごとに縮む

複数件を先にキューから取り除くと、**3件目の途中で OS ごと消えたときにまだ走っていない
仕事がキューから消える**。#639 が塞いだ穴と同じ形で、**失敗としては現れない**。

1. マーカーの形式を `{"jobs": [...], "job": <先頭>, "state", "requeued", "at"}` にする。
   `jobs` の無い古い値は `[job]` として読む（`inflight_jobs()`）——マーカーは DB に残りうる
   ので、複数件へ広げた回のデプロイで前夜の中断を取り落とさない
2. `batch_common.Hooks` に省略可能な `on_step_done(step, exit_code)` を足し、`run_batch` の
   ステップループから呼ぶ。`run_daytime` は終わった仕事をマーカーの `jobs` から外す

これで3件目で消えた回に戻るのは3件目だけになり、完了済みの計算を捨てない。縮めるのは
**終わった仕事だけで成否は問わない**（「結論を出した失敗は戻さない」という `pop_queue` の
判断をそのまま保つ）。

あわせて、回収時の重複除去を「全部消す」から「**戻す1件につき1つまで**」へ直した。
`bench:rhat-scale` を3つ積んだ回に中断が起きると、従来は残りの2つまで黙って消えた。
相殺したときはログに1行出す（黙って減らさない）。

### 7. `--steps` で絞った日は、生き残ったステップの仕事だけを取り除く

絞ったのに全件 `take` すると、走らせていない仕事がキューから黙って消える（#692 が
塞いだ穴と同型）。

### 8. `--peek` の既存フィールドは変えず、`keys` と `total_measured_min` を足す

`run_daytime.ps1 -Now` が読む口。`key` / `measured_min` は先頭1件のままで、
`sensitive` だけ **1件でも敏感なら true**（安全側）に変える。`-Force` の門はここで開くので、
混ざっていたら敏感側へ倒す。

## Consequences

- #615（`gate:macro` / `gate:demean`）と #424 子3（`gate:ttm`）の判断材料が、3日に散らず
  **9/24（木）に揃う**。同じデータ世代で並べるという設計が成立する
- `bench:rhat-scale` ×3（440分×3）の消化速度は変わらない。1件で窓を使い切るため
- `batch_common` に増えるのは省略可能なフック1つで、他の4バッチ（nightly / monthly ×3 /
  backup）の挙動は変わらない
- 1日の実走が長くなる日がある。窓（8時間）は広げていないので、夜間バッチ（17:20）との
  間隔 80分 は保たれる
- `run_daytime.ps1 -Now` を昼過ぎに叩くと窓が夜間バッチへ食い込みうる点は**変わらない**
  （440分の仕事1件でも同じ）。ここでは直さない

## 採らなかった案

### 案A: 窓を広げる

9時間にすれば1日1件のままでも消化が進む。**採らない**——夜間バッチ（17:20）まで20分しか
残らず、日中枠が長引いた日にメモリを取り合う。それは 2026-09-07 の発散を招いた条件そのもの。
`tests/test_run_daytime.py::TestBudgetFitsTheWindow` がこの間隔を縛っている。

### 案B: 所要比で予算を按分する

`measured_min` の比で 445分 を分ける。**採らない**——決定2 のとおり ADR-0040 の
「予算は実測から逆算しない」と衝突する。パネルは毎晩伸びるので、按分は必ず陳腐化する。

### 案C: マーカーは全件を持ち、中断時は全件戻す

`batch_common` を触らずに済む。**採らない**——完了済みの仕事を再実行する。440分の
`bench:rhat-scale` が混ざる日には、丸1日ぶんの計算を捨てることになる。

### 案D: 1回の実走で `run_batch` を件数ぶん呼ぶ

フックが要らない。**採らない**——足跡・通知・env ヘッダが件数ぶん重複し、失敗した日の
Issue が複数立つ。1日の実走は1本のログにまとまっているほうが読める。
