# 売り候補ランキングの並びのキーを、売り専用の予測 S2（下側 20% 点）へ切り替える

## Status

**accepted（2026-11-15）**。#1201（ユーザー判断「切り替える方向で進める」2026-11-12・計画の承認 2026-11-15）。
[ADR-0071](0071-sell-ranking-keeps-only-the-measured-best.md) の決定 1 のうち「並びは M-6 の現在μ̂ の昇順」を覆す。
手法が 1 つであること、下位 1/5 の切り方、画面に選択肢を出さないこと（ADR-0071 の決定 2〜6）は変えない。

## Context

ADR-0071 は、売り候補ランキング（`plugins/sell_ranking.py`）を「M-6 の μ̂ の低い順に並べ、下位 1/5 を売る」1 手法に絞った。
M-6 は 52 週先リターンの**平均**を当てる。売りで知りたいのは大きく下がる社なので、当てる答えだけを**下側 20% 点**に替えた
L1+L2 の分位回帰（S2）を、測る前に規則を固定して比べた（#1158・[`docs/prereg/sell-quantile-model.md`](../prereg/sell-quantile-model.md)）。

| 主審（S2 − M-6） | 差 | 95%CI | p（両側・α=0.025） | 期数 |
|---|---|---|---|---|
| (a) 上位層の売り側spread | +0.0161 | [+0.0029, +0.0279] | 0.007 | 16 |
| (b) 全社の売り側spread（拒否権） | +0.0071 | [−0.0002, +0.0169] | 0.035 | 17 |

判定は **adopt**（(a) が有意に良く、(b) は有意に悪くない）。19 期のうち 2 期は S2 の予測が全社で同じ値になり、順位が付かなかった。
事前登録 §4 は、採用でも本番の切り替えは別の PR（新しい ADR）にすると定めていた。

#1202 で、M-6 の実行が同じパネルで S2 も解いて `sell_quantile_scores` へ保存するようにした（既定の並びは変えていない）。
切り替えの前に、#1201 の手順で次を確かめた（2026-11-15・読み取りだけ）。

| 晩 | S2 の所要 | M-6 の実行（S2 込み） | スコア更新のステップ | S2 の保存 |
|---|---|---|---|---|
| 2026-11-12 | 231.2 秒 | 10.0 分 | 10.1 分・exit=0 | 3,649 行・全社同値でない・失敗なし |
| 2026-11-13 | 189.7 秒 | 8.0 分 | 8.1 分・exit=0 | 同上 |
| 2026-11-14 | 365.5 秒 | 12.3 分 | 12.5 分・exit=0 | 同上 |

- ステップの予算は 60 分（`run_nightly.BUDGET_MIN["scores"]`）。S2 を足す前の M-6 の実行は 5.3〜7.3 分だった
- `sell_quantile_scores` と `macro_enet_scores` は同じ 3,649 社で、基準日も同じ（2026-11-13）
- 参考（判定に使わない）: 2026-11-13 の断面の全社で、S2 と M-6 の μ̂ の順位相関は 0.977、下位 1/5（729 社）の重なりは 87.1%

## Considered Options

1. **据え置く（M-6 の μ̂ のまま）**——却下。事前登録の判定が adopt で、所要も予算に収まった
2. **S2 に切り替え、S2 が使えない回は判定を出さない**——却下。全社同値の回（19 期のうち 2 期）に売りの札が出なくなる
3. **S2 に切り替え、S2 が無い保有だけ M-6 の μ̂ で補う**——却下。下側の分位と平均は尺度が違い、混ぜると順位が壊れる
4. **画面で S2 と M-6 を選べるようにする**——却下。ADR-0071 の決定 4（売りの決め方を選ばせない）
5. **S2 に切り替え、使えない回は保有全体を M-6 の μ̂ で並べて理由を画面に出す**——採用

## Decision

1. `sell_ranking.SELL_KEY_SOURCE` を `SELL_KEY_S2` にする。並びは S2 の現在の予測（`sell_quantile_scores.q20`）の昇順で、
   予測がそろった m 社の先頭 `m // 5` 社が `SELL`（切り方は ADR-0071 のまま）。S2 だけ欠けた保有は「データ不足」
2. S2 が使えない回——表が空（未保存・全社同値の回）か、S2 の断面の日付が M-6 と違う——は、保有**全体**を M-6 の μ̂ の
   昇順で並べる（#1202 で作った `choose_sell_keys` の規則のまま）。理由を応答の `sell_key_fallback` に入れ、分析画面と
   朝の画面に注意の色で出す
3. 画面は並びに使った値（下振れの見込み＝下側 20% 点）を列として出す。M-6 の μ̂ は参考表示として残す
4. `depends_on` は `macro_enet` のまま（S2 は M-6 の実行が同じ夜に作り、倒れる先も M-6 の μ̂）。`MU_SOURCE` は残す
5. Render（閲覧用の断面）には S2 の行が無いので、そこでは常に 2 の経路になる。断面へ書き戻す経路は作らない（ADR-0038）
6. OOF 運用再現（`scripts/oof_portfolio_replay.py`）の売りと、売りの計測の分母（`sell_mu_source_bakeoff.SELL_BASE`）は
   M-6 の μ̂ のまま。S2 の OOF 予測は運用再現に入っていない
7. 戻すときは `SELL_KEY_SOURCE = MU_SOURCE` の 1 行（ADR-0071 の形）。戻すときも新しい ADR を添える

## Consequences

- 「売却」の札が付く保有が、M-6 の μ̂ で並べていたときと入れ替わることがある（全社での下位 1/5 の重なりは 87%）
- 予測が全社同じ値の回と Render では、M-6 の μ̂ で並ぶ。Render では注意が常に出る
- S2 の学習・保存が失敗した晩も、夜間バッチは exit=0 で終わる（#1202 の設計）。切り替え後は本番の売りの並びの入力なので、
  失敗として現す仕組みを #1237 で足す。それまでは画面の注意と診断値（`python -m scripts.nightly_diag_report`）で気づく
- 運用再現の成績（#1224）と買い方の規則の計測（#1227）は、本番と違う売り方（M-6 の μ̂）の成績になる。運用再現に S2 を
  足す道具は #1238
- 売りの決め方を変えるときは、これまでどおり `scripts.sell_mu_source_bakeoff` で測ってから新しい ADR で変える。本番の予測での
  答え合わせ（#1157）には S2 の月次の写しが入っている（#1208）
