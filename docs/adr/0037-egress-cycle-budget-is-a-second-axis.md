# Egress の歯止めは2軸。プロセス予算は暴走を止め、月枠を守るのは請求サイクル累計だけ

## Status

accepted（2026-08-19）。Issue #478 の設計決定で、#483（閾値監視）をブロッカーごと解く。
[ADR-0034](0034-client-side-egress-ledger-and-circuit-breaker.md) の追補——あちらが入れた
プロセス単位のブレーカが、実際に起きた2回目の超過に対して**原理的に無力だった**ことへの回答。

## Context

Supabase 無料枠の Egress は 5GB/月。2026-07 に 61.2GB（1224%）、2026-08 に 7.312GB（146%）と
2回続けて超過し、いずれも組織全体が restricted（402）になった。2回目は8日間の停止で、
`daily-incremental` の schedule を止めたまま復旧を待つことになった。

ADR-0034 は全経路の計測とプロセス単位のサーキットブレーカを入れた。しかし
**2回の超過は種類が違っていた**:

| | 形 | プロセス予算（400MB/プロセス）で止まるか |
|---|---|---|
| 2026-07（61.2GB） | 暴走型（検証フルロードの反復・1プロセスが大量に引く） | 止まる |
| 2026-08（7.312GB） | **じわじわ型**（スパイク約2GB＋平常運転 約5GB） | **止まらない** |

400MB/プロセスという上限は、1日に 12 プロセス走れば 4.8GB/日を流しても一度も踏まれない。
**再発したのはじわじわ型なのに、対策は暴走型にしか効いていなかった。**

計測側にも3つ穴が残っていた（2026-08-19 に実物で確認）:

1. **台帳が集約されない。** 帰属ラベル `FINAPP_JOB` は 17 ワークフローすべてに入っていたのに、
   台帳ファイルを artifact として回収していたのは `nightly-scores.yml` の1本だけ。
   残り16本は run ログを手で落とさない限り月次のロールアップに乗らない。
2. **ローカル実行が既定で無計測。** `FINAPP_EGRESS_LEDGER` を人が手で立てる運用で、
   `.egress/ledger.jsonl` は 1,961B・前日の1回ぶんしか無かった。
   **過去2回の超過はどちらもローカル検証の反復が主因なのに、そこだけ記録が空だった。**
3. **総量の閾値監視が無い。** #483 は Supabase Management API で総量を取る設計だったが、
   PAT が `gh secret list` に無く、ブロッカーのまま着手されていなかった。

## Decision

### 1. 請求サイクル単位の累計を第2の軸として持つ

プロセス予算（`DEFAULT_MB_LIMIT`）はそのまま残し、**別軸**でサイクル累計を積む。
2つは目的が違うので、どちらか一方に統合しない:

- プロセス予算 … 1回の暴走を、その場で止める
- サイクル累計 … 月枠に対する残量を、プロセスを跨いで守る

### 2. 累計の置き場所は DB（`app_settings`）

**ローカル CLI と GitHub Actions ランナーが同じカウンタを見られる唯一の場所**だから。
ファイルに置くと、開発者の手元で払った Egress が GHA からは見えず、その逆も見えない。
`weekly_price_cache` が世代印を DB に置いたのと同じ理屈＝**印は書き手と読み手の両方から
見える場所に置く**。

読みは1プロセス1回（最初の `record()` で lazy）、書きは1プロセス1回（`emit_summary`）。
加算は1文の中で行う:

```sql
value = (CASE WHEN :rolled THEN 0
              ELSE COALESCE(NULLIF(app_settings.value, '')::bigint, 0) END + :n)::text
```

**読んで足して書く3手に分けない。** 夜間バッチと手元の CLI が同時に走ると、後から書いた
方が相手の加算を潰す。サイクル境界の判定も、印の更新が「値が変わったときだけ行を返す」
性質（`WHERE ... IS DISTINCT FROM ... RETURNING 1`）を使い、追加の SELECT 無しで済ませる。

### 3. ブロックは 95%、警告は 80%。100% には置かない

枠を使い切った瞬間に全ジョブが死ぬより、手前で止めて人が判断できる余地（残り 5%＝256MB）を
残す方が復旧が速い。**restricted に入るコストは、ジョブが1本落ちるコストより桁違いに大きい**
（実測で8日間の停止）。

### 4. ミラー（ローカル）接続では積まない

ローカル PostgreSQL のミラー（#481・`FINAPP_DB_TARGET=local`）からの読取は Supabase の
Egress を1バイトも使わない。ここを積むと「ミラーで検証したのに枠が減る」ことになり、
**ミラーへ逃がす動機を自分で壊す**。台帳 JSONL には従来どおり残すので、帰属の記録は失わない。

### 5. 自己計上の再帰はスレッドローカルのフラグで止める

累計の読み書き自体が `after_cursor_execute` を通り、`record` → `_check_budget` →
`cycle_snapshot` → `_load_cycle` → SELECT → `record` の無限再帰になる。フラグを
**スレッドローカル**にしてあるのは、立てている間だけ他スレッドの計測まで止めないため
（`execute_plugin` が `asyncio.to_thread` でワーカースレッドへ逃がすので並行実行は常に起こる）。

### 6. pytest 実行中は累計を必ず無効にする

**ローカルの pytest は `database.py` を import した時点で本番 Supabase 向けの engine を作る**
（`.env` の `DATABASE_URL` を読むため）。ここを有効なままにすると `record()` を呼ぶ全テストが
本番へ接続しに行き、`emit_summary` の atexit が本番へ書き込みまで行う。

これは机上の懸念ではない——本 ADR の実装中に**全体テストが10分超ハングし、本番の
`app_settings` にテスト由来の 32,362 バイトが実際に書き込まれた**（該当行は削除済み）。
「ローカルスクリプトは本番DBに直結する」という既知の罠が、そのままテストにも当てはまる。

### 7. 台帳 JSONL は既定オン。環境変数に依存させない

未設定時の出力先を `.egress/ledger.jsonl`（`.gitignore` 登録済み）にする。
**「覚えていれば計測される」を「黙っていても計測される」へ倒す。** 無効化は
`FINAPP_EGRESS_LEDGER=0`。ジョブごとにファイル名を分けるのはやめ、全ジョブが既定パスへ書く
（帰属は JSONL の中の `job` フィールドが持つので、ファイル名で区別する必要が無い）。

### 8. 枠の消費を failure へ翻訳する独立ジョブを置く（PAT 不要で #483 を解く）

`egress-health.yml`（毎日 UTC 21:00）が `scripts/check_egress_health.py` を走らせ、閾値超過で
exit 2 → `notify-failure.yml` が Issue を自動起票する。`macro-health`（#420）と同じ形。

**判定に要るものは既に DB の中にある**ので Management API の PAT は要らない。#483 は
「正本の総量」として別途残し、PAT が用意できたら台帳の推定値との残差を較正へ回す（排他ではない）。

`workflow_run` チェーンにせず cron で回すのは、**Egress がワークフローの成否と無関係に
積み上がり、開発者のローカル CLI からも積まれる**ため。「収集が成功した後に見る」では
見落とす経路が残る。

**Database Size も同じジョブで見る。** 2026-08-19 時点では Egress より先に Database Size が
壁（430MB / 500MB = 86%）で、Egress は超えても翌サイクルで戻るのに対し
**Database Size を超えると read-only** で収集そのものが止まる。「枠の消費」という同じ問いなので
見る場所を分けない。閾値は Egress より厳しい 90% に置く。

### 9. artifact の回収漏れは CI のメタ検査で落とす

**回収漏れは failure を出さないので `notify-failure.yml` では原理的に拾えない**
（ADR-0031 の `HEAVY_AUTOMATION` と同型）。`tests/test_db_egress.py` に2本置く:

- `upload-artifact` を持つ全ステップの `path` に `.egress` が含まれること
- `DATABASE_URL` を渡す全ステップに `FINAPP_JOB` があること（帰属ラベルの取り付け漏れ）

前者は「検査が空振りしていないこと」（対象が 10 件以上あること）も併せて固定する。

## Considered Options

**A. プロセス予算の上限を下げる。** 400MB → 100MB 等。じわじわ型には効かない（プロセス数が
増えれば同じ）うえ、正当に重い夜間バッチ（初回 67.7MB）が誤爆する余地が増える。棄却。

**B. 累計をファイル（`actions/cache`）で持つ。** GHA の run 間では持ち回れるが、
**開発者のローカル実行と共有できない**。過去2回の主因がまさにそこなので、最も守りたい経路が
守れない。棄却。

**C. Management API で総量を取る（#483 の原案）。** 正本の総量が取れるのは利点だが、PAT が
無いまま数週間ブロックされていた実績がある。**答えが要るのは「誰が食ったか」の方**で、
そこは台帳しか出せない。排他ではないので、後から足す形に変えた。

**D. 有料プラン（Pro $25/月）へ上げる。** 3つの枠（Egress 250GB・DB 8GB・Disk IO）が同時に
解ける。ユーザー判断で「無料枠を維持し構造で守る」を選択（2026-08-19）。この ADR はその決定の
実装であり、Pro へ移っても計測と帰属の価値は残る。

## Consequences

- **良い**: 月枠に対する残量が、ローカルと GHA の両方から同じ値で見えるようになった。
  超過は restricted を待たずに 80% で Issue になる。
- **良い**: `FINAPP_EGRESS_LEDGER` を覚えている必要が無くなった。ローカル検証の反復が
  自動的に台帳へ載る＝次に超過したとき「誰が食ったか」に答えられる。
- **代償**: 累計のために1プロセスあたり SELECT 2本と UPSERT 2本を払う（数百バイト）。
  枠の 0.00001% 程度で、測る対象に対して無視できる。
- **限界1**: 累計は**推定**（行数 × 較正済み B/行）であって正本ではない。較正の出所は
  `EGRESS_COST_TABLE` の `measured_on` / `source_issue` が持つ。ダッシュボードの実測との
  残差は、1サイクル回した後に突き合わせて評価する（#478 の最終検証）。
- **限界2**: `db_egress` を通らない転送（`pg_dump` によるミラー初回 pull 等）は
  `record_external()` で手で積む必要がある。自動では乗らない。
- **限界3**: restricted に入ってしまうと累計を DB へ書けない。ただしその時点で既に手遅れなので、
  歯止めとしての価値は失われない（書けなければ警告を出して本処理は続ける）。
