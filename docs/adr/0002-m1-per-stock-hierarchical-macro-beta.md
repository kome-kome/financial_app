**検証メモ（2026-07-18・#341 のプール仮説を実測反証）**: 「chains=2 の run を複数回まわして生サンプルをプールすれば 2×N チェーン相当の r_hat が strict 1.01 を切れるのでは」という案を検証した（実験基盤 `scripts/experiment_pooled_rhat.py`・PR#351）。縮小規模（実データ500銘柄・K=4・draws/tune=800・numpyro）で **r_hat_max は 2/4/6/8 チェーンを通じて 1.0100 で完全に平坦（delta=+0.0000）**、一方 ESS は 525→1927 と約4倍に増加した。結論: **プールは ESS（サンプル数）を増やすが r_hat は下げない**——r_hat はチェーン内混合の良さ（between/within 分散比）で決まり、同程度に混合の甘いチェーンを増やしても比は不変。r_hat を下げるレバーは「チェーン数↑」ではなく「1本1本の混合改善（reparameterization・target_accept↑・tune↑）」。過去に draws=800/1000 でもサンプル長で動かなかった事実と合わせ、**~1.01–1.02 はこのモデル幾何の安定した床**であり、`--r-hat-threshold` の緩和（cron 1.05）が妥当な対処だったと確認された（プール昇格は見送り）。なお r_hat_max は銘柄数（パラメータ数）が増えるほど上がる max 順序統計の性質があり、500銘柄で 1.01・本番3800銘柄で 1.02 という差もこれで説明できる。

**改訂（2026-08-02・Issue #356）— 上記 #341 検証メモの数値的根拠を撤回**: 収束診断 `summarize_diagnostics` が `az.summary` を**既定引数**で呼んでいたため、返っていた `r_hat_max` は真値ではなく **arviz が表示用に小数2桁へ丸めた値**だった（`arviz/stats/stats.py` の `decimals = {col: 3 if col not in {"ess_bulk","ess_tail","r_hat"} else 2 if col == "r_hat" else 0}`・`ess_*` は整数丸め）。これにより:

- 直上の検証メモ「**2/4/6/8 チェーンを通じて 1.0100 で完全に平坦（delta=+0.0000）**」は、床の実測ではなく **2桁丸めの解像度そのもの**である（真値が 1.005→1.014 で単調に減っていても、すべて 1.01 と表示される）。よって「~1.01–1.02 はこのモデル幾何の安定した床」という結論、および「500銘柄で 1.01・本番3800銘柄で 1.02 という差は max 順序統計で説明できる」という付随解釈は、**いずれも根拠を失った**（プールが r_hat を下げないという理論的説明自体は成立するが、当該実測はその証拠になっていない）。
- `persist_allowed` の strict 基準 1.01 は、丸めのため実効的に「真値 < 1.015」として動作していた（真値 1.0051 と 1.0149 が同じ 1.01 として通る）。cron の緩和閾値 1.05 での判定結果は変わらない（1.02 台は生値でも通過する）が、strict 1.01 を指定した場合の厳格さは今回の修正で本来の定義どおりになる。

対処: `summarize_diagnostics` を `round_to="none"`（生値）へ修正し、丸め回帰を検知する単体テスト（`TestSummarizeDiagnostics`）を追加。教訓は [GOTCHAS.md](../GOTCHAS.md#分析計算の実装メモ)「閾値比較に使う統計量は表示用整形を経ていない生値であることを確認する」へ一般形で記録した。

**生値での再実測（2026-08-02・run 30724216104）— #341 の結論は撤回でなく「反転」**: 同一パラメータ（500銘柄・K=4・draws/tune=800・target_accept=0.95・numpyro/adapt_diag）で再実行した結果、

| runs | chains | r_hat_max | ess_bulk_min | n_div |
|---:|---:|---:|---:|---:|
| 1 | 2 | 1.0194 | 214.8 | 0 |
| 2 | 4 | 1.0108 | 405.3 | 0 |
| 3 | 6 | 1.0128 | 631.6 | 0 |
| 4 | 8 | **1.0105** | 819.0 | 0 |

**2ch 1.0194 → 8ch 1.0105（delta=-0.0089）とプールで r_hat は下がる**（6ch で一度 1.0128 へ戻るノイズはあるが、2→8ch の低下は明確）。すなわち #341 検証メモの「プールは ESS を上げるが r_hat は下げない——r_hat はチェーン内混合で決まり、混合の甘いチェーンを増やしても between/within 比は不変」という結論は**実測上は成立していなかった**（丸めが変化を隠していた）。ESS が 214.8→819.0 と約4倍になる点だけは初回と同傾向。

ただし 8チェーンでも **strict 1.01 は未達**（1.0105・残り 0.0005）。またパネルは #411 の窓延伸により初回実測（n_obs=7607・n_factor=6）から n_obs=11289・n_factor=12 へ増えており、パラメータ数増は r_hat_max（max 順序統計）を押し上げる方向に働く点は割り引く必要がある。cron の閾値 1.05 は現状維持（生値でも 1.02 前後は通過し判定結果は変わらない）。

**tune 増は棄却（2026-08-02・run 30725731129）**: #356 に残る唯一の未検証レバーだった warmup 増を、Run A と同一パネル・同一 seed 系列で `tune=800 → 2000` のみ変えて実測した。

| chains | tune=800（Run A） | tune=2000（Run B） |
|---:|---:|---:|
| 2 | 1.0194 | 1.0279 |
| 4 | 1.0108 | 1.0162 |
| 6 | 1.0128 | 1.0183 |
| 8 | **1.0105** | **1.0158** |
| ess_bulk_min(2ch) | 214.8 | 157.2 |

**全チェーン数で一貫して悪化**し、ESS も 214.8→157.2 と落ちた。`target_accept=0.95` の下で適応期間を延ばすとステップサイズがより保守的（小さく）調整され、`draws=800` の範囲では自己相関が増えて実効サンプルが減る——という説明と整合する。**tune を増やす方向は採らない**（draws を据え置いたまま tune だけ延ばすのは逆効果）。

したがって Issue #356 が列挙した3案は、①non-centered＝初版から実装済み・②target_accept 0.95＝適用済み・③tune 増＝実測棄却、で**すべて決着**した。床を下げる手段として実測上唯一残ったのはプール（チェーン数を分割ジョブで稼ぐ Stage 3 fan-out）だが、500銘柄・8チェーンでも 1.0105 と strict 未達であり、本番規模（3800銘柄）では max 順序統計の性質上さらに不利になる。**strict 1.01 は現実的な目標ではなく、cron の緩和閾値 1.05 での運用継続が妥当**という #341 の運用判断自体は（根拠となった数値は誤っていたものの）結論として維持される。

**Stage 3（fan-out）は実装しない（2026-08-06・Issue #413 クローズ）**: 実測上唯一残ったレバーである
プール（`chains=2` のジョブを N 本並列に回し idata をプールしてから persist する）について、実装の
可否を #413 で追跡していた。判断基準は「Stage 2 で `k_runs=8`（16チェーン）を測り strict 1.01 を
切るか」だったが、次の3点から**その実測を待たずに見送りを確定した**:

1. **改善がノイズと同オーダーまで縮んでいる。** 8 チェーンで 1.0105（strict まで残り 0.0005）だが、
   推移は単調ではない（2ch 1.0194 → 4ch 1.0108 → **6ch 1.0128** → 8ch 1.0105）。6ch の戻りが
   示すとおり、この領域の変動は実験ノイズに支配されており、16ch で 1.01 を割り込む保証がない。
2. **本番規模ではさらに不利。** `r_hat_max` は全パラメータの max 順序統計であり、500 銘柄で切れても
   約3,800 銘柄の本番で切れる見込みは薄い（#411 の窓延伸で `n_factor` が 6→12 に増えた分も
   押し上げ方向に働く）。
3. **得られるのは診断値だけ。** プールが上げるのは ESS（事後平均の精度）であって μ̂ の順位ではなく、
   推奨結果は変わらない。一方コストは `macro-beta-inference.yml` のジョブ分割・idata の artifact
   受け渡し・combine ステップの新設と、本番 DB 実書込の再検証（[[feedback_verify_db_writes_directly]]）。
   **運用は緩和閾値 1.05 で既に回っており実害が出ていない。**

再開の条件は「診断値ではなく**推奨値（μ̂ の順位）**が壊れている」ことが観測された場合とする。それが
無い限り、収束の床は cron 閾値 1.05 で受け止める。`scripts/experiment_pooled_rhat.py` と
`experiment-pooled-rhat.yml` は Stage 2 まで動く状態で残す（再開時はそこから測り直せる）。

**「g++ 不在が遅さの主因」は棄却（2026-08-25・Issue #512）**: ローカル実行が GHA の 6.4倍以上
遅い件で、起票時の見立ては「`pytensor.config.cxx` が空 → PyTensor が C 実装を使えず Python
フォールバック（起動時に `g++ not detected! ... Performance may be severely degraded` が出る）」
だった。これを **Linux ランナー側から C コンパイラだけ外して直接測り、棄却した**
（`bench-macro-beta.yml` の `pytensor_cxx=off` ＝ `PYTENSOR_FLAGS=cxx=`・同一パラメータ
（合成パネル 500銘柄・chains=1・tune=100・numpyro/adapt_diag）・同時刻 dispatch の対で2組）:

| 組 | `cxx='/usr/bin/g++'` | `cxx=''`（ローカルと同条件） |
|---|---|---|
| 1組目 | 0.0394 us/step/obs | **0.0226** |
| 2組目 | 0.0410 us/step/obs | **0.0386** |

**C バックエンドを外しても遅くならない**（最速の観測はむしろ「なし」側）。仮説が予測する「著しい
劣化」は起きない。機構としても整合する——本番は `nuts_sampler="numpyro"` ＝ モデルは JAX へ
トランスパイルされ、**サンプリングのループに PyTensor の C バックエンドは通らない**。g++ がある側で
`probe`（初回コンパイル込み）が 56.2s に対し無い側が 30.4s と短いのも、C コンパイル代が
**起動時にだけ乗る**ことの現れである。

実測で分かった差の実体は**1 leapfrog 歩あたりのコスト**で、しかも規模依存だった（n≤250 では
1.3〜1.5倍、n≥500 で 4〜6.6倍。本番規模の実データ（3,800銘柄・n_obs 94,037）では
22,176 us/step ＝ フル規模換算 約20時間）。`chain_method`・ホストデバイス強制・スレッド上限は
いずれもばらつきの範囲で、主因ではない。**両プラットフォームで `steps/draw` が 1023
（`max_tree_depth=10` の上限）に張り付いている**ことと、`beta` / `mu_sector` が
`pm.Deterministic` ＝ トレース保存で本番 posterior が約1.2GB になることが、それぞれ別の
レバーとして残った（#540 / #541）。計測の手順と落とし穴は [GOTCHAS.md](../GOTCHAS.md) を参照。

**#541 は解消済み（2026-08-25）**: `beta` / `mu_sector` の `pm.Deterministic` を外し、
自由 RV（`mu_universe` / `mu_sector_raw` / `sigma_sector` / `beta_raw` / `sigma_stock`）から
事後に再構成する方式へ変えた（`macro_beta_inference._reconstruct_beta_chunk`）。**確率構造は
不変＝統計的な変更ではない**ため本 ADR の設計判断は変わらない。収束診断も同じ `beta` に対して
計算し続ける（銘柄チャンクへ分割し r_hat は max・ESS は min を累積。スカラーパラメータごとに
独立な統計量なので全体と厳密に一致する）——**strict 1.01 のゲートは `beta` の r_hat に対して
較正された値**であり、代わりに `beta_raw` を見るとゲートが黙って緩くなるため。残るレバーは
#540。

**軌道長のレバー: 一律キャップは棄却・warmup 限定キャップ `(8, 10)` を採用（2026-08-25・Issue #540）**:
`macro_beta` は `steps/draw` が 1023（= 2**10 − 1・numpyro 既定 `max_tree_depth=10` の上限）に
100% 張り付いており（#512）、**毎 draw が構造的に最大コストを払っていた**。ただし
**「上限を下げれば速くなる」ではない**——軌道を切れば 1 draw あたりの実効サンプル（ESS）が落ちる
ので、所要ではなく統計効率で測って決めた（測定の実体は `scripts/grid_macro_beta.py` と
`scripts/bench_macro_beta.py --max-tree-depth`。ADR-0041 と同じく**アドホックなスクリプトで
終わらせず残す**）。

指標は **ESS_bulk / leapfrog 歩**（時間を含まない量）を主にした。`ESS/秒 = (ESS/歩) × (歩/秒)` で
`歩/秒` はマシンとパネルの性質であって `max_tree_depth` の関数ではなく、ローカルの us/step は
**時間帯で 2.4倍振れる**（[GOTCHAS.md](../GOTCHAS.md)）——数時間かかる格子を所要で並べると
ドリフトがそのまま格子の差に化ける。

`ess_bulk_med` と ESS/歩 は**両者ほぼ同一**（差 0.3% 以内）・発散は全条件 0。`r_hat_max` の

外している——**この差は設定由来ではない**（#341/#356 で確認した床の揺らぎの範囲）。所要は
平均 388.6s → 184.3s ＝ **2.11倍速**。

実データでの追認（ローカル・本番パネルを 500銘柄へ間引き・**12因子＝本番と同次元**・
chains=2・tune=800・draws=400）:

| `max_tree_depth` | steps/draw | 到達率 | 発散 | `r_hat_max` | `ess_bulk_min` | `ess_bulk_med` | 所要[s] |
|---|---:|---:|---:|---:|---:|---:|---:|
| 8 | 255 | 1.000 | 0 | **1.2261** | **7.391** | 246.8 | 579.4 |
| **(8, 10)** | 511 | 0.000 | 0 | 1.0388 | 85.2 | 1074 | **599.3** |
| 10（現行） | 511 | 0.000 | 0 | **1.0556** | 36.49 | 981.5 | 1593.7 |

`(8, 10)` と現行の `steps/draw` が**完全に一致（511）**＝ **warmup を切っても適応後の軌道長は
変わらない**（「warmup を短い木で適応させると本番の軌道長がずれるのでは」という交絡はここで否定
された）。統計量は `(8, 10)` が全項目で同等以上、所要は 2.66倍速。一律 md=8 は実データでも崩壊する
（`ess_bulk_min` 7.391）。ただしこの規模は到達率 0.000 ＝ **張り付き regime ではない**ので、
張り付き regime での証拠は上の合成パネル（3シード）が担う。

**`target_accept` を 0.90 へ下げる案は「軌道長のレバーとしては」無効**: ta=0.90 でも `steps/draw` は
1023・到達率 1.000 のままで**軌道は縮まず所要も変わらない**（396.5s vs 392.3s）。ゲート統計は
むしろ良い（`ess_bulk_min` 308 vs 163・`r_hat_max` 1.0216 vs 1.0350）が、これは軌道長とは別の
レバーであり**実データでの発散が未検証**（合成パネルでは 0 だが、numpyro 既定初期化が本番規模で
発散多発だった前例がある）。0.95 は #356 で適用済みの設定であり、変えるなら実データでの発散を
測ってから別途扱う。

**採用しても月次バッチの窓には入らない（未解決・#530 / #532 へ引き継ぐ）**: `(8, 10)` は総
leapfrog 歩数を `2×(800×1023 + 800×1023)=3,273,600` → `2×(800×255 + 800×1023)=2,044,800` ＝
**37.5% 削減**する。本番規模ローカルの実測 22,176us/step を掛けると **約20.2時間 → 約12.6時間**。
`run_monthly.py` の `BUDGET_MIN["macro_beta"]` は 180分であり、**1.6倍速くなってもまだ桁が違う**。
予算は実測から逆算しない方針（ADR-0040）なので 180分は据え置き、毎月 exit=124 で起票される状態は
継続する（静かに餓死するより良い、という #530 の判断のまま）。#540 は**軌道長のレバーを使い切った**
ことを示すのであって、月次の窓問題を解いてはいない——そちらは #532（9/1 実走で予算値を実測で
埋める）が引き取る。

**測定上の落とし穴（次に測る人へ）**: 最初の格子は実データを 250銘柄へ間引いて回したが、
`select_shared_factors` が **5因子しか選ばず**（本番は 12）、md=9/10 の到達率が 0.000＝軌道が
255歩で自然に U ターンする別レジームに落ちていた。**#540 の前提「1023 に張り付く」が成り立たない
場所で測っており、そこでは md=8 とキャップ無しが同一の軌道になる**（GOTCHAS の「tune を切り詰めると
別レジームへ落ちる」と同型の罠が、今回は銘柄数・因子数で起きた）。表は何事も無かったように並ぶので、
`scripts/bench_macro_beta_report.py::regime_note` が「最も緩い上限のセルの到達率が 1.000 を割ったら
警告する」形で検知するようにした。実データで本番と同じ 12因子が選ばれるのは **500銘柄以上**である。

## Context

M-1（マクロ×リスク-リターン推奨）は現状、**ユニバース全体で単一の β**（BIC 選択も OLS 再フィットも全銘柄プール）を学習し、銘柄固有なのは R1（断面レバレッジ）と R2（実現ボラ）だけだった。これに起因する構造的限界が判明した。

- **判別力の欠如と退化**: walk-forward CV R²≈0.01。§9.6 で自認のとおり、R1 レバレッジが全銘柄でほぼ一定 → 縮小重み w≈1 → μ_shrunk が全銘柄をセクター平均へ収束させ、銘柄差が消える。
- **マクロ特徴量が4つに限定**: 設計ではなく収集失敗（JP10Y=`^JGB` 上場廃止 / TOPIX 取得不可）。さらに**横断モデルではマクロの水準は全銘柄同値＝断面分散ゼロ**で、交互作用にしないと寄与しない——これが「マクロ増量」を阻む根本制約だった。
- **リスク軸の次元非整合**: R1（OLS-SE）/ R2（年率ボラ）/ R3（CV-RMSE）は単位がバラバラなのに、単一 λ で軸を切替可能 → `U = μ − λ·R` が軸ごとに別物（λ の意味が破綻）。
- **doc⇔doc⇔code 衝突**: 散布図・効用に μ_raw を使うか μ_shrunk を使うか、MODELS.md / ガイド / コードで不一致。

「個別銘柄ごとのマクロ感応度」「マクロ増量」「R3 の要否」「効率的フロンティアの逆（売り側）」を同時に解くには、推定単位そのものを変える必要があった。

## Decision

1. **推定単位を per-stock 階層モデルへ**。共有マクロ因子集合を pooled データ上で BIC（`LassoLarsIC`）で一括選択し、その因子への**ローディングを銘柄ごとに推定**してセクター/ユニバース事前分布へ partial pooling する（[[個別マクロ感応度]]）。**因子集合が全銘柄共通**なので μ と銘柄固有リスクが比較可能（commensurable）で、リスク-リターン散布図とフロンティアが成立する。**手法は全体→セクター→銘柄の二層フルベイズ階層モデル**（PyMC・NUTS）：共有因子へのローディングを各銘柄の random slope とし、`銘柄 ← セクター事前 ← ユニバース事前`の超事前で部分プーリングする。MCMC 事後分布から **per-stock 事後平均ローディング**（μ 予測の係数）と**事後SE（R1'）**が自然に得られ、小 n（実効サンプル一桁）の不確実性を正しく伝播する。Vasicek 型・Empirical Bayes も検討したが、表現力と不確実性伝播を最優先してフルベイズを採用（比較は Considered Options 参照）。
2. **特徴量の居場所を分離**。マクロは**主効果**（per-stock で時間変動）。年次/半期ファンダは時系列回帰子ではなく、**ローディングの断面事前分布（上位層）**を説明する。真の四半期ファンダは容量（Supabase 500MB）＋ソース（EDINET 四半期報告書が 2024/4 廃止）＋ point-in-time リーク対策がブロッカーのため **DEFER**。
3. **交互作用項（`fin×macro` / `sector×macro`）を撤去**。異質性は per-stock random slope が担う。`sectors[:10]` の隠れバイアスが消滅する。
4. **マクロ増量はチャネル網羅で**。count ではなく、直交する経済チャネル（金利/期間構造・FX・株式β・クレジット・コモディティ・ボラ/リスク選好・インフレ）で 8-12。BIC 選択は pooled（large-n）で行うため次元爆発に耐性。
5. **リスク軸を再編**。効用軸＝R2（総ボラ）＋**R_macro（[[系統的マクロリスク曝露]]、新設）＝√(βᵀΣ_macroβ)**（β＝per-stock 事後ローディング・ベクトル、Σ_macro＝選択マクロ因子の共分散行列）。これは**マクロで説明されるリターンの標準偏差**ゆえ μ・R2 と同じリターン単位で λ が次元整合し、総リスク ≒ √(系統的² ＋ 固有²) として R2 のマクロ起因成分に分解できる。当初の括弧書き候補 ‖macro loadings‖（L2 ノルム）はリターン単位にならず λ の次元整合が崩れるため**棄却**。**R1'（per-stock 事後SE）＝縮小駆動**、**R3（バケット CV-RMSE）＝表示/足切りゲート**に降格（[[結果リスクと信頼度の分離]]）。
6. **売り側ジオメトリを新設**。[[負の効用]] `D = λ·R − μ`（買い側 U の符号反転）と[[非効率的フロンティア]]（反 Pareto 集合＝支配判定の反転）。売り側で反転する誤差の罠（μ 過大評価が悪い保有を売りから守る）は **R3 足切りゲート**で処理し、μ は再定義しない。
7. **売り候補ランキングへは成分結線**。M-1 producer が per-stock μ・R_macro を出し、sell_ranking に**別メトリックとして**注入（μ:高=売り理由減 / −R_macro:高曝露=売り理由増）。λ は売り重みに吸収。`depends_on`＋graceful-degrade、R3 ゲートは action-label 段。フロンティア/D は M-1 画面の可視化に留める。
8. **対数変換は選択適用**。水準/フロー（売上・資産・時価総額・EPS>0）は log/Δlog 成長、バリュエーション倍率（PER/PBR/配当利回り）は log、負値・有界比率（ROE・自己資本比率・各種 YoY 変化・z-score）は非 log。ターゲットは既に log return。

## Considered Options

- **ユニバース単一 β 維持＋交互作用増強**（却下）: 最小改修だが、CV R²≈0.01 と μ_shrunk 退化の主因が「単一モデル仮定」である可能性が高く、交互作用を増やしても断面分散の制約（マクロ水準＝全銘柄同値）に縛られ続ける。
- **独立 per-stock BIC**（却下・当初案の文字通り）: 銘柄ごとに特徴量も係数も独立 BIC 選択。小 n（52週フォワード＋週次で実効サンプル一桁）で過学習し、銘柄間で因子集合がバラバラになって**フロンティアの μ/R が比較不能**になる。共有因子集合＋縮小ローディングが、柔軟性と比較可能性・サンプル効率を両立する。
- **真の四半期ファンダを前提プロジェクト化**（保留）: capacity レバー（`raw_xbrl_json` drop）＋`period_type`/`filing_date` 列＋J-Quants 有料 Light が必要で、モデル進化をゲートする。per-stock マクロ・ベータは年次ファンダのままでも出せる（ファンダは事前分布側）ため、四半期は後日エンハンスへ分離。
- **R3 を破棄 / R3 を別軸として残す**（却下）: R3 は唯一の out-of-sample 指標で破棄は惜しい。一方で「リスク軸」ではなく信頼度なので、軸ではなく machinery（表示/足切り）として残す第三の道を採用。
- **負の効用を売り特化で再設計**（却下）: `D_sell = λ_R·R_macro + λ_c·(R1'+R3) − μ` は表現力が高いが、新 λ 追加・買い側との対称性喪失・降格した R1'/R3 を罰則として再昇格させる。純ミラー D=−U＋R3 ゲートの方が対称的で再利用が効く。
- **per-stock 縮小の手法（partial pooling の実装）**: 3案を比較。(a) **Vasicek 型 信頼性加重縮小**＝numpy 閉形式・軽量・§9.6 James-Stein の自然拡張で Render 本番でもリクエスト時計算可だが、正規・線形の仮定が強く不確実性伝播が点推定どまり。(b) **Empirical Bayes**＝階層分散をモーメント/周辺尤度で点推定する (a)(c) の中間。(c) **フルベイズ二層階層モデル（採用）**＝全体→セクター→銘柄の階層事前を MCMC（NUTS）で同時推定。事後分布から per-stock 事後平均ローディングと事後SE（R1'）が自然に得られ、小 n の不確実性を正しく伝播する。代償は新規重依存（PyMC／PyTensor のビルドが重い）と推論コストだが、下記の**バッチ分離**で本番ランタイムへの影響を遮断する。表現力と不確実性伝播を最優先して (c) を採用。

## Consequences

- **μ_raw vs μ_shrunk 衝突が自動解消**: μ は pooled loading からの単一予測（縮小はローディング段で完結）になり、別途の μ_shrunk 段が不要。散布図・効用にどちらを使うかの不一致が消える。
- **R1 退化が解消**: 銘柄ごとの時系列回帰が自然な per-stock 事後SE（R1'）を与える。
- **doc⇔code 名称負債の清算が必要**: `_forward_bic`（実体は単一 `LassoLarsIC` パス）の改名、未使用 `vif_threshold` 削除、MODELS.md / ガイドの μ 記述統一、`sectors[:10]` 記述の撤去。
- **sell_ranking が M-1 producer の consumer に**（`depends_on` 追加）。未実行時は `gap_available` 流に graceful-degrade。
- **新たな検証責務**: per-stock × 共有因子集合 × partial pooling の WF-CV、R_macro の定義（標準化ローディングの L2 ノルム等）と λ レンジの再較正。
- **収集タスクが派生**: 新マクロチャネルの取得可否調査（無料ソース制約下）。
- **実行アーキ＝推論バッチ分離（Render 制約からの必然）**: 階層 MCMC は `/api/plugins/{name}/run` の**同期リクエスト実行**では時間的に不可能。よって **PyMC は GitHub Actions の推論バッチ専用依存**とし、本番 Render の `requirements.txt` には載せず `requirements-inference.txt` へ分離する（PyMC 5系＝5.28.x・枯れた安定版を pin）。バッチが per-stock 事後ローディング（平均・SE）・選択因子集合・因子共分散 Σ_macro を **DB に永続化**し、M-1 プラグインは **producer** としてそれを読むだけで μ・R_macro・R1' を出す（`produced_output`／`depends_on` 機構に乗せる）。これにより本番ランタイムは軽量を維持し、収集パイプライン側でのみ MCMC を回す。
- **パッケージ評価（CLAUDE.md 準拠）**: PyMC は重大 CVE 未確認・NumFOCUS 後援でメンテ活発・研究標準で査読者多数。総合判定 ⚠️注意（PyTensor のビルドが重い）。本番非搭載＋バッチ分離で懸念を遮断する前提でユーザー承認済み（2026-06-21）。

実装・調査タスクは GitHub Issues（残タスクの正本）で追跡する。
