# 代表 as-of は中央値・株価鮮度は p50 判定（max を代表値にしない）

## Status

accepted（2026-08-03）。Issue #417（producer の as-of）・#416（買い推奨の株価鮮度）。

## Context

2026-08-02 の本番調査（`daily-incremental` が19日連続 failure）で、**19日古いランキングと今朝の
ランキングが画面上まったく区別できない**ことが分かった。原因は 2 か所にある。

1. **producer の as-of（#417）**: μ̂ は銘柄ごとに「その銘柄の最終週次バー」時点で算出される
   （`build_snapshots` の `is_current = (snap_idx == n - 1)`）。にもかかわらず M-2/M-3/M-4/M-6 の
   4 プラグインは `max(snap_date)` を代表値として `*_scores.snapshot_date` に書いていた。実測では
   **2 銘柄が 2026-07-31・3,677 銘柄が 2026-07-13** で、max は実態より 19 日新しい。
2. **株価鮮度の可視化（#416）**: `/api/stats` は `stock_price_records`（件数）しか返さず、株価の
   as-of 日付を返す API がどこにも無かった。買い推奨タブには鮮度表示が一切なく、`recommend` は
   `date.today()` を as_of にしてモメンタムを計算するため、株価が19日古くてもエラーにならず
   **静かに劣化した値**を返していた。

「モデルを回していないから古い」のではない点が重要で、2026-08-01 に M-2/M-3 は success で
`--persist-scores` を完走してなお `snapshot_date = 2026-07-13` だった。`snapshot_date` は週次株価
グリッド由来であり、**株価が止まっていればモデルをいつ回しても as-of は進まない**。

## Decision

**銘柄ごとに違う日付を 1 個に潰すときは中央値（p50）を採り、`max` は代表値にしない。**

- 算出は `plugins/macro_snapshots.py::representative_snapshot_date` に一本化し、4 プラグインが共有
  する（同一ロジックの 4 コピペが乖離源だった）。偶数個は古い側（lower median）＝保守側へ寄せる。
- `*_scores` に `snapshot_date_min`（最古）と `n_stale`（代表値より古い銘柄数）を加え、**分布であることを
  潰さない**。DDL は `ADD COLUMN IF NOT EXISTS` の非破壊・冪等マイグレーション（既存行は NULL）。
- 各 `results[]` 行に銘柄別 `snap_date` を載せる（`current_snaps` に既にあるため追加コストゼロ）。
- 売り候補ランキングは `mu_asof`（代表値・最古・古い銘柄数）を返す（`database.get_producer_asof`）。
- **株価鮮度も同じ規約に従う**（`database.price_freshness`）。判定軸は p50 の齢（営業日）で、
  5営業日超＝黄・10営業日超＝赤。`max` は参考値として返すだけで判定に使わない。赤のときは
  「この結果で発注しないでください」を明示し実行前に確認を挟むが、**実行はブロックしない**
  （`z_momentum` を外した分析など正当な用途を殺さず、無意識のクリックだけ止める）。

**M-1（`macro_risk_return`）の as-of は返さない。** `macro_beta_meta.snapshot_date` は推論バッチの
**実行日**（`macro_beta_inference.py` が UTC today を入れる）でデータ as-of ではないため、そのまま
見せると株価が止まっていても「今日」と表示され同型の嘘になる。`get_producer_asof` は M-1 に対して
意図的に None を返す。

## Considered Options

- **最古（min）を代表値にする**: 最も保守的だが、上場廃止銘柄など極端に古い 1 社に引っ張られて
  常時「数ヶ月前」表示になり、警告が形骸化する。採らない。
- **p05 を代表値にする**: 外れ値を切りつつ保守側へ寄る中間案。解釈の説明が難しく、`n_stale` と
  `snapshot_date_min` を併記すれば p50 で十分と判断。`price_asof_p05` は補助表示としてのみ採用。
- **鮮度が古いときは実行をブロックする**: 正当な用途（株価非依存の重みでの分析）を殺すため不採用。

## Consequences

- `*_scores.snapshot_date` の意味が「実行時スナップ基準日（max）」から「銘柄別スナップ日の代表値
  （中央値）」へ変わる。既存行は次回モデル実行まで旧意味の値が残り、追加 2 列は NULL。
- `/api/stats` は株価 as-of 分位を返すが、**per-code MAX の全行を毎回転送しない**（DB 側集約＋
  `LIMIT/OFFSET` の分位取得）。行ごとの as-of が要る `recommend` だけが全行を引く。Egress 枯渇
  （2026-07 の実害）を再現させないための経路分離であり、両経路が同じ結果を返すことは回帰テストで固定した。
- 祝日カレンダーを持たないため営業日計算は祝日も 1 営業日として数える＝実際より「古く」出る
  （警告が早めに出る保守側の誤差）。
- 本 ADR の規約は as-of に限らず「集約が実態を隠す」型の罠への一般的な対処であり、#356（`az.summary`
  の丸めで表示桁 == 判定桁になっていた件）と同型。新しい代表値を UI に出すときは、まず分布を見る。
