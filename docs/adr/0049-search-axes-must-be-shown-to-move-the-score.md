# 探索軸は「スコアを動かす」ことを実測してから置く

## Status

accepted（2026-09-02）

## Context

M-1（`macro_risk_return`）の探索空間は 288件だった:

```
use_macro 2 × (use_momentum False 1 + True 5) × min_coverage 4 × max_features 6 = 288
```

2026-09-02 の完走ログ（288件・`exit=0`・513.9分）を `min_coverage` 以外の4軸で群にまとめると、
**72群すべてで群内のスコアが完全に一致していた**（1桁まで同一。`max_features` と
`momentum_window` は同じログの中でスコアを動かしているので、丸めで潰れているのではない）。

つまり **72通りの結果を 288回計算していた。**

### 機構（実測で確定）

`min_coverage` のフィルタは `plugins/macro_snapshots.py` にある:

```python
non_null = sum(1 for v in feat_row if v == v)
if non_null / n_feat < min_coverage:
    continue
```

しかし M-1 は `build_snapshots` を **`macro_nan_ok=False`（strict）** で呼ぶ＝マクロ特徴量が
1つでも欠損した断面を**このチェックの手前で破棄する**。到達する行の充足率は常に厳密に 1.0 になる。

本番データで直接測った（DB へは書かない・2026-09-02）:

| `min_coverage` | 0.0 | 0.3 | 0.5 | 0.7 | 0.9 | 0.95 | **1.0** |
|---|---|---|---|---|---|---|---|
| サンプル総数 | 181,862 | 181,862 | 181,862 | 181,862 | 181,862 | 181,862 | **181,862** |

**充足率 100% を要求しても1行も落ちない。** 「効いていない」であって「効くはずが壊れている」
ではない——`macro_nan_ok=True` で呼ぶ M-2 では同じパラメータが実際に効く。

### なぜ気づかれなかったか

軸を足しても**失敗として現れない**。探索は候補が増えたぶん時間を使うだけで、結果は正しく、
ログも正常に流れる。増えた分は「モデルが重い」という形で計上され、
**マシンの性質として記録される**（ADR-0046 は M-1 を 752分と見積もり専用タスクへ切り出した）。

## Decision

**探索軸は「スコアを動かすこと」を実測で示してから置く。効かないと分かった軸は落とす。**

`plugins/macro_risk_return.py::tuning_search_space()` から `min_coverage` を除く（288 → **72件**）。

### 契約からは消さない

`params_schema()` には残す。M-2 のように `macro_nan_ok=True` で呼ぶモデルでは実際に効く共通
パラメータで、契約から消すと消費側が壊れる。**M-1 で動かしても結果が変わらない旨は
schema の `description` に書く**（UI に「効かないつまみ」が黙って残る方が悪い）。

### 前提を縛る

軸を落とせる根拠は「M-1 が strict であること」**だけ**である。`macro_nan_ok=True` へ変えた
瞬間にこの軸は再び意味を持つが、**軸はもう無いので探索されず、誰も気づかない**
（ADR-0031 と同型）。そこで:

1. 両方の呼び出し箇所で `macro_nan_ok=False` を**明示する**（既定任せにしない＝
   `build_snapshots` 側の既定変更で M-1 が黙って strict でなくなるのを防ぐ）
2. `tests/test_macro_risk_return.py` が **AST で**呼び出しの kwarg を検査する。
   文字列一致にしないこと——docstring の散文（「M-2 のように `macro_nan_ok=True` で呼ぶ」）で
   誤爆する（実際に最初の実装がそれで落ちた）

## Consequences

- 探索は 288 → 72件。実測ペース（`use_macro=True` 2.18分/件・`False` 0.92分/件・いずれも無人）で
  **513.9分 → 約112分**の見込み。**ただし実測は 10/2 の実走まで確定しない**ので
  `BUDGET_MIN["tune:macro_risk_return"] = 900` は動かさない（ADR-0040「予算は実測から逆算しない」）
- **ADR-0046 の Alternatives が1つ無効になる。** そこでは「探索空間を削って窓に収める
  （288→約90件）」を却下しており、理由は「#291 の品質ゲートが別条件の値と比較されるようになる」
  だった。そのゲートは **#594（ADR-0047）が同一パネル上の champion 投入へ置き換えて撤去済み**で、
  さらに今回の削減は結果が完全に同一なので「別条件」ですらない。
  **ADR-0046 の決定（M-1 を専用タスクへ出す）自体は覆さない**——112分でも月次本体の空き
  （Σ863＋マージン30 に対し窓960＝67分）には入らない。折り返すかは 10/2 の実測後に判断する
- champion 投入（ADR-0047）は壊れない。`_project_champion` は **dims にある軸だけ**を
  champion params から抜き出すので、落とした軸は単に振られなくなる
- 他モデルへの影響なし。`min_coverage` を探索軸に持っていたのは M-1 だけ（M-2/M-3/M-6 は持たない）

## Alternatives considered

- **軸を残したまま `build_snapshots` のキャッシュキーから `min_coverage` を外す。**
  同一内容の 1.7GB 断面を4つ持つ無駄（#584 で観測した「階段」の正体）は消えるが、
  **同じ計算を4回する無駄は残る**。ピークメモリだけ下がって所要は変わらない
- **`macro_nan_ok=True` へ変えて `min_coverage` を実際に効かせる。** 母集団の定義を変える
  変更で、ADR-0045「母集団が縮む側は必ず有利に見える」の領域に入る。M-1 は交差項を作るので
  NaN が混入すると OLS が壊れる（`build_snapshots` の docstring が明示）。別の話として扱う
- **`params_schema()` からも消す。** 消費側（UI・`coerce_params`・保存済み params）が壊れる。
  パラメータ契約（CONTEXT.md）から要素を消すのは退役の手続きが要る
