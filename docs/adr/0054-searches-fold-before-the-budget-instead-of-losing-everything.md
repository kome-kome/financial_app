# 探索は予算の手前で自分から畳む（打ち切りに全損させない）

## Status

accepted（2026-09-11）。Issue [#638](https://github.com/kome-kome/financial_app/issues/638)、
実害の観測は [#633](https://github.com/kome-kome/financial_app/issues/633) と
[#587](https://github.com/kome-kome/financial_app/issues/587)、隣接する事象は
[#639](https://github.com/kome-kome/financial_app/issues/639)。
[ADR-0046](0046-steps-that-cannot-finish-get-their-own-task.md) と
[ADR-0040](0040-batch-window-is-split-into-step-budgets.md) が前提にしていた
「`hyperparameter_search` は完走してからしか永続化しない」を**撤回する**（決定自体は覆さない）。
[ADR-0047](0047-tuning-gate-compares-on-one-panel.md) の champion 投入を、投入位置の指定まで狭める。

## Context

`plugins/tuning.py::search()` は全候補を評価し終えてから返り、`hyperparameter_search.py` は
その後で `plugin_tuned_params` への upsert と、best params での最終 `execute_plugin`
（producer スコアの永続化）を行っていた。**途中経過を書く経路が1本も無い。**

一方 `scripts/batch_common.py::Runner.run()` は `step.budget_min` を1秒でも超えた子を
`kill_tree()` で落とす。Windows では `taskkill /F /T` なので**子に猶予は無い**（この強制は
ADR-0040 が意図して置いたもので、緩めると窓の終わりにタスクスケジューラが黙って
プロセスを止め、後続ステップが走った形跡すら残さずに消える）。

結果、予算を超えた瞬間に**そこまでの計算が成果ゼロで捨てられる**。

| 回 | 消えたもの |
|---|---|
| 2026-09-01 月次 `tune:macro_risk_return` | 250分ぶん（`[15/288]` まで） |
| 2026-09-01 月次 `tune:macro_dlm` | 250分ぶん（`[199/294]` まで） |
| 2026-09-09 日中枠 `tune:macro_dlm`（外因・#639） | 285分ぶん（`[255/294]` まで） |

2番目は M-3 の μ̂ が 2026-07-10 のまま **59.5日**固着する直接の原因になった。しかも
気づけたのは #504 の producer 監視が起票したときで、バッチ失敗の Issue は既に閉じていた。

#633 は予算を 400→500分（実測369分に対し約36%の余裕）へ引き上げ、余裕の薄さを CI で縛った。
しかし**これは時間を買っただけ**である。

- 分析パネル（銘柄 × 期）は毎晩の収集で伸びるので、所要は据え置かず伸びる。
- 窓（月次16時間・日中枠8時間）は伸ばせない。日中枠を9時間にすると夜間バッチとの余裕が
  20分になり、それは #618 が隔離した「重い計算の裏で別の重い処理が走る」条件そのもの。
- したがって**いつか必ずまた超える**。

## Decision

**探索は締切の手前で自分から畳み、途中経過を捨てない。** 3つを組み合わせる。

### 1. 締切を親から子へ渡す（環境変数 `FINAPP_STEP_DEADLINE_UTC`）

`Runner.run()` が `started + step.budget_min` を ISO8601（UTC）で子の環境へ入れる。
**渡すのは時刻であって分数ではない**——子が自分の起動時刻から数え直すと、起動の遅れぶんだけ
判定が甘くなる。**予算が無いステップでは明示的に消す**（継承した古い値が残ると、無期限の
はずのステップが親から漏れた締切で勝手に畳み、それは失敗として現れない）。

置き場所が `Runner.run()` なのは、そこが全ステップの通る唯一の場所だからである
（heartbeat・予算打ち切りと同じ理由）。子スクリプト側の opt-in にすると登録漏れが構造的に起きる。

予算の数字を argv へ書き写さない。唯一の源は `Step.budget_min` のまま。

### 2. 締切の手前で探索を畳む（案C）

`search()` は候補を1件評価するごとに実所要を記録し、**観測した最大値**を次の1件の見積りとする。
`現在時刻 + 見積り > 締切` なら残りを切って抜け、`config["truncated"]=True` を立てる。
最大値を使うのは保守側で、候補の所要にはばらつきがあり平均で見積もると最後の1件で超える。
**失敗した候補の所要も数える**（契約違反で即返る候補ばかり見ていると見積りが0に張り付く）。

**1件目だけは締切を見ずに必ず評価する。** 見ると、締切を既に過ぎて入ってきた回で有効な
スコアが0件になり `ValueError` へ落ちる。1件目は champion なので、これは最低でも現状維持を意味する。

`hyperparameter_search` が `search()` へ渡す締切は `deadline − FINAL_RESERVE_MIN`（15分）。
`search()` を抜けた後に upsert と最終 execute が残るためで、**実測**は `tune:macro_dlm` が
3分未満（2026-09-10・全体303.8分）、`tune:macro_gbdt` が4.4分未満（2026-09-08・全体179.4分）。
約3倍の余裕を採った。日中枠の予算445分に対し3.4%で、実際に消費するのは畳んだ回だけ。

### 3. 候補ごとに暫定ベストを保全する（案A）

`search()` は `on_progress` コールバックで、候補1件ごとにその時点の結果（戻り値と同じ形）を渡す。
`hyperparameter_search` は `persist=True` のとき、**暫定ベストが改善した回だけ**
`plugin_tuned_params` へ書く。これは #639 のような**外からの強制終了**（OS 再起動・電源断）への
保険で、そちらは案C では守れない。producer スコアの更新はここでは行わない（1回が数分かかる）。

### 4. champion は候補列の先頭へ固定する

ADR-0047 は champion（本番稼働中の params）を候補プールへ入れることで
`best >= champion` を構造的に成立させた。しかし**先頭でなければ、途中で止めたときにその性質が
成立しない**。従来の実装は「既に含まれていれば追加しない」だったので、grid 探索では champion が
候補列の中間に埋まり、そこで畳むと「まだ champion を測っていない」区間ができる。

先頭へ移せば、2件目以降のどこで止まっても「暫定ベスト ≧ 同一パネルで測り直した champion」が
必ず成立する。**畳んだ結果を本番へ採ってよい根拠は「比較して勝ったから」ではなく
「探索の構造上そうなるから」**であり、ADR-0047 の論拠がそのまま使える。

### 5. 何件まで見た結果かを行に残す

`plugin_tuned_params` に `n_combos_planned`（計画した候補数）を足し、`n_combos` の意味を
**実際に評価した候補数**へ変える。完走した回では両者が一致するので既存行の解釈は変わらない。
畳んだかどうかは `n_combos < n_combos_planned` から導ける。**空間の一部しか見ていない結果を
champion と比べることになる以上、何件見たかは比較の条件そのもの**である。

## Consequences

- **予算超過が全損ではなくなる。** 畳んだ回でもパラメータと producer スコアが揃うので、
  μ̂ の固着（#633 の 59.5日）はこの経路からは起きなくなる。
- **予算を薄くしてよい理由にはしない。** 畳むのは最後の手段で、#633 が引き上げた予算と
  `tests/test_run_monthly.py::TestTuneBudgetsMatchTheMeasurement`（予算 ≥ 実測 × 1.25）は
  そのまま残す。畳んだ回は探索空間の一部しか見ていない。
- **「畳んだ」は成功のログに埋もれさせない。** exit は 0 のままだが WARNING を出し、
  行にも `n_combos < n_combos_planned` として残す。
- **grid 探索の候補評価順が変わる**（champion が先頭へ来る）。値そのものは候補ごとに決まるので
  結果は変わらないが、共有スナップショットキャッシュの構築順が変わり、構造パラメータの並び次第で
  スナップショット構築が1回余分に走りうる。1回ぶんのコストとして許容する。
- **環境変数の名前が2箇所にある**（`scripts/batch_common.ENV_DEADLINE` と
  `hyperparameter_search.ENV_DEADLINE`）。root 側から `scripts/` を import する向きは前例が無く
  作らないため。**ずれても例外は出ず、締切が黙って渡らなくなるだけ**なので
  `tests/test_hyperparameter_search.py` が2つの定数を照合する（`launch.py` の DB target 既定を
  `tests/test_db_target.py` が照合しているのと同じ形）。
- 既存行の `n_combos_planned` は NULL のまま（完走前提だった世代）。次回の探索実行で埋まる。

## Considered Options

### 案A 単独（逐次永続化だけ）

パラメータは内外どちらの強制終了でも残るが、**producer スコアは探索完了後の最終 execute で
しか更新されない**ため、本 Issue が実害として挙げた μ̂ の 59.5日固着は直らない。案C と併用する
形で採った。

### 案B: 中断再開（評価済み候補を残して次回続きから）

**採らない。** 再開してよいかの判定は `_data_fingerprint()`（週次株価の最終週・行数・世代印＋
マクロ最終日）でしか行えないが、日中枠は平日1日1件で、実行と実行の間には必ず夜間バッチ
（JST 17:20 の収集）が挟まる。指紋はほぼ毎晩変わるので、翌営業日の再開判定は常に
「世代が違うから捨てる」に落ち、器だけが残る。パネル世代をまたいだ評価値の混在は
ADR-0047 が潰した問題の再来でもある。

なお #639 が入れた in-flight マーカー（`app_settings.daytime_inflight`）は案B の器として
そのまま使えるが、上記のとおり中身を入れる意味が無い。

### 予算をさらに引き上げる

#633 で一度やった手であり、パネルが伸び続ける以上いつか必ずまた超える。日中枠を9時間へ
広げる案は夜間バッチとの余裕を20分にし、#618 が隔離した並走条件そのものを作る。
