# Egress はクライアント側で常時計測し、プロセス単位のサーキットブレーカで止める

## Status

accepted（2026-08-13）。Issue #478 の設計決定。#477（2026-08 の restricted）と、その前身である
2026-07 の超過（Issue #355 で `scripts/_cache.py` を導入した回）への恒久対策。
計測の正本については [ADR-0032](0032-statement-timeout-raised-per-statement.md) と同じ
「上書きは局所・既定は変えない」原則を踏襲する。

## Context

Supabase 無料枠の Egress は 5GB/月。**2回続けて超過した**。

| 時期 | 実績 | 結果 | 打った手 |
|---|---|---|---|
| 2026-07 | 61.2GB（1224%） | organization 全体が restricted（402） | `scripts/_cache.py`（#355）＝検証スクリプトのローカル pickle キャッシュ |
| 2026-08 | 7.312GB（146%） | 同上。**負荷を止めても自然回復せず**、復旧は課金サイクル切替の 2026-08-18 | `daily-incremental` の schedule 停止（#477） |

2回目が重いのは、**1回目の対策を入れた後に再発した**こと、そして
**再発の原因が最後まで特定できなかった**ことにある。月 9.5GB のうち帰属が判明しているのは
夜間バッチ 1.98GB（#446 実測）だけで、**残り 5GB 超が未特定**のまま 8/18 を待っている。

特定できない理由は、原因が難しいからではない。**測る仕組みが `scripts/` 配下にしか
無かった**からである。当時の可視化は `scripts/_cache.py` の `[cache] HIT/MISS` だけで、
次の経路は**完全に無計測**だった。

- 夜間バッチ本体（`nightly_scores.py` / `hyperparameter_search.py` /
  `recommend_factor_premia.py` / `macro_beta_inference.py`）
  — いずれも `shared_snapshot_cache()`（プロセス内のみ）を使い、`scripts/_cache.py` は使わない
- `routers/` の全 API（`/api/backtest/model-comparison` は1クリックで M-1/M-2/M-3 をフル実行する）
- `collector*.py` の読み出し経路

つまり「誰が食ったか」を事後に答える手段が構造的に存在しなかった。
`Egress per day` のダッシュボードは日単位の合計しか出さず、2026-08-09 の 1.2GB スパイクが
どのジョブのものかは今も分からない。

これは #438（Yahoo の静かな配信停止）や ADR-0031（heavy を足したが自動実行が無い）と
同型の欠陥である——**failure を出さない種類の異常は、通知では原理的に拾えない**。
超過が可視化されるのは restricted になった後だけで、そのときには既に手遅れになっている。

## Decision

1. **Egress はクライアント側で常時計測する。** `db_egress.py` が `engine` の
   `after_cursor_execute` にリスナを1本張り、**全プロセス（GHA バッチ・ローカル CLI・Render）**で
   「どのテーブルから何行・何列を引いたか」を台帳に積む。psycopg2 の既定カーソルは
   クライアント側バッファなので、このフックの時点で行は既に転送済み＝`cursor.rowcount` が
   そのまま転送行数になる。**結果を消費しないので既存の挙動には一切干渉しない。**

2. **計測は二階建てにし、正本を取り違えない。** 正本は従来どおりサーバ側
   `sum(octet_length(列::text))`（#446 の測り方）。台帳は「行数 × 較正済み B/行」の**推定**であり、
   役目は (a) 全経路の帰属を常時残すこと、(b) ブレーカを踏むこと の2つに限る。
   較正値には `measured_on` と `source_issue` を**必須フィールド**として持たせ、
   出所の無い数字を混ぜられないようにする（CI で検証）。未較正の組み合わせは
   12 B/列/行 の既定を使い、**保守側＝多めに見積もる**（過小評価はブレーカを無力化する）。

3. **計上の門は「文が SELECT で始まるか」ではなく「結果セットを返したか」**
   （`cursor.description is not None`）。`INSERT ... RETURNING` は行が返る＝Egress なので
   文字列判定では取り落とす。逆に INSERT/UPDATE/DELETE 本体は description が None となり
   自動的に外れる（ingress は無料）。

4. **rowcount が取れない呼び出しは `unknown` バケットへ隔離し、0 に丸めない。**
   SQLite は SELECT の `rowcount` が常に -1 で、テストは全件 SQLite で走る。
   0 に丸めると「引いていない」と区別できなくなる（#438 の静かな故障と同型）。
   **CI では実数の計上が一度も起きない**という事実を、テストの側でも明示する。

5. **プロセス単位のサーキットブレーカを既定で有効にする。**
   `FINAPP_EGRESS_ROW_LIMIT`（既定 3,000,000 行）/ `FINAPP_EGRESS_MB_LIMIT`（既定 400MB）を
   超えたら `EgressBudgetExceeded` を送出する。既定値は既知の最大実行（夜間バッチ ≒ 1.39M 行 /
   67.7MB）の約2倍。GHA では例外＝failure ＝ `notify-failure.yml` が Issue を自動起票するので、
   **ブレーカは自分で自分を報告する**。50% / 80% で警告を1行出す。

6. **上限の引き上げは局所に限る。** `egress_budget(mb=..., rows=...)` コンテキストマネージャで
   その区間だけ差し替え、抜けるとき必ず戻す（ADR-0032 の `db_timeouts` と同じ書き味）。
   プロセス全体の既定を書き換える口は用意しない。緊急解除は `FINAPP_EGRESS_ENFORCE=0` だが、
   **計測は続く**（止めるのは送出だけ）。

7. **ワークフローには帰属ラベルを持たせる。** DB へ繋ぐ全 yml の `env` に `FINAPP_JOB` を置く。
   `full-pipeline` は collect / finalize、`tune-hyperparameters` は matrix のモデル名まで分ける
   （別プロセス＝`shared_snapshot_cache()` を跨がないため、転送量の性格が違う）。

## Consequences

- **良い点**: 「誰が食ったか」に常時答えられる。`[egress] summary` が1実行1行で run ログに残り、
  `python -m scripts.egress_report` がジョブ別・テーブル別に積み上げる（DB に繋がないので
  ロールアップ自体は Egress を使わない）。8/18 の復旧後、最初の1サイクルで未特定の 5GB の
  帰属が確定する見込み。ブレーカは 2026-08-09 の 1.2GB スパイクのような暴走を
  「その日のうちに例外＋自動起票」へ変える。
- **良い点**: `docs/DEPLOYMENT.md` の cron 占有表に「1回あたり Egress」列が付いた。
  この列が無かったために `tune-hyperparameters` の matrix 3並列（1日で約200MB）が
  Egress 設計の表から漏れていた。**時刻の非重複と転送量は独立に効く。**
- **代償**: 全クエリでリスナが1回走る（正規表現1本＋辞書更新）。ネットワーク往復に対しては
  無視できるが、ゼロではない。台帳はプロセス単位の状態なので、スレッドを跨いで積む
  （`execute_plugin` が `asyncio.to_thread` を使うため lock で守る）。
- **代償**: 既定でブレーカが有効なので、**正当に重い一回性の処理が初回は落ちうる**。
  落ちたら理由を確かめた上で `egress_budget()` で局所的に引き上げる。無条件に
  `FINAPP_EGRESS_ENFORCE=0` を置くのは、安全網を恒久的に外すことなので採らない。
- **限界**: これは**測ることと止めること**であって、**転送量そのものを減らしてはいない**。
  夜間バッチが毎晩 1,282,436 行の週次株価を引き直している（増分は約4,400行＝転送の 99.7% が
  不変データの再送）という構造は手つかずで、別 Issue（差分ロード基盤）に残る。
  ADR-0032 の「これは『2min では足りない』への対処であって遅さそのものを直してはいない」と
  同じ性格の限界であることを明記しておく。
- **限界**: 較正値は 2026-08-06 の実測1点に依存する。**8/18 の復旧後に
  `octet_length` で取り直し、推定との残差を記録すること**（#459 の列絞り後の実測も同時に取る）。
- **検証**: `tests/test_db_egress.py`（テーブル名抽出・unknown 隔離・予算超過の送出・
  局所上書きの復元・較正値の出所・engine 統合・本番 engine への取り付け）。DB へは繋がない。
  **実数の計上は SQLite では原理的に検証できない**ため、実 PostgreSQL（ローカルミラー）での
  確認を別途行う。

## Considered Options

- **Supabase Management API で使用量を監視する（#478 改善案4）**: 正確な総量が取れるが、
  (a) Management API の PAT が未発行、(b) **総量しか分からず帰属が出ない**——
  「9.5GB 使った」は既にダッシュボードで分かっており、答えが要るのは「誰が」の方。
  台帳と排他ではないので、PAT 発行後に閾値監視ジョブとして追加する（別 Issue）。
- **`scripts/_cache.py` の HIT/MISS 可視化を拡張する（#478 改善案2・実装済み d70e88c）**:
  検証スクリプトの範囲では有効だが、**未特定の 5GB が居るのは `scripts/` の外**である可能性が
  高い（夜間バッチ本体・`routers/`・collector はこの機構を一切通らない）。
  範囲を広げるには全呼び出し元へ手で `cached()` を巻く必要があり、巻き忘れが黙って
  無計測になる。engine 側の1箇所で全経路を捕まえる方が構造的に漏れない。
- **`echo=True`（SQLAlchemy の SQL ログ）で事後解析する**: 行数もバイト数も出ないうえ、
  ログ量が本番運用に耐えない。常時有効にできないものは「気づけない異常」の対策にならない。
- **バイト数をカーソルから正確に取る**: psycopg2 はソケットのバイトカウンタを公開しておらず、
  行を文字列化して測ると 128 万行に対して無視できない CPU を払う。
  **行数（正確・無料）× B/行（較正済み・推定）** の分解にして、正確さが要る場面は
  正本の `octet_length` に委ねるのが費用対効果で勝る。
- **ブレーカを既定 OFF にして計測だけ入れる**: 「まず測って、様子を見てから止める」は
  一見穏当だが、**2回とも restricted になるまで誰も気づかなかった**という実績がある。
  気づける仕組みが無い状態で警告だけ足しても、次の超過は同じ形で起きる。
  既定 ON ＋ 局所的な引き上げ口、を採る。
